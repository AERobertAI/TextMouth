## The user's request, in their words (October 30, 2026)

> "for new features I did want a optional library view which just shows "Feeds" loaded. in optional I want a settings section that allows reorganizing and changing which views show up as available in the Library, for settings of always, when applicable (like the reading list would show up only when there are episodes or reading list items) and allow moving up and down the views... then I want the ability to make custom views for that would basically act as filter or shortcuts for example for showing all books that are unopened and sorted in descending order or feeds with only new items..... but with more customization... the built in views should use the same system and be customizable."

So, four parts:
1. **A Feeds view:** a new built-in view of the Library window that lists the feeds alone (their rows, as the Feeds section shows them today).
2. **A settings section** that lists the Library's views in order, where each view's visibility is chosen ("Always", "When applicable", and a way to hide it), and Move Up and Move Down reorder them. "When applicable" shows a view only while it has something to list: the Reading List only while it holds books, episodes, or articles; Feeds only while there is a feed.
3. **Custom views:** views the listener makes, each a saved filter and sort over the library ("all books that are unopened, sorted in descending order", "feeds with only new items"), "with more customization".
4. **One system:** the built-in views (Folders, All Items, Unopened, Recently Opened, Reading List, and the new Feeds) are entries of the same list, and customizable through it.

The user is a VoiceOver and braille user. Everything in this feature must be operable from the keyboard, spoken, and readable on a braille display, with every wording pinned by a test.

### What the design must settle
1. **What exists:** every place that depends on the category, in a table (file:line, what it decides), so no place is missed when categories become views.
2. **The model.** A view definition: a permanent id; its name; whether it is built in; its visibility; its place in the order; and, for a filter view, its filter and sort. Name the Swift types so they cannot be confused with the SwiftUI `LibraryView` struct (for example `LibraryViewDefinition` or `LibraryShelf`; your choice, used everywhere). Folders (one folder at a time, with its breadcrumbs and manual order) and the Reading List (its own order, its options bar) stay special kinds inside the same list; say exactly what of each is customizable.
3. **Built-in views as presets of the same system** where they can be: All Items (every book), Unopened (never opened, with the feeds that have new items), Recently Opened (the ten opened last, newest first), Feeds (the feeds). Each built-in view can be changed through the same editor as a custom one where that makes sense (its name, filter, sort, limit), and has Restore Default. Say which of a built-in view's parts stay fixed and why.
4. **The filter language for custom views.** Useful, and buildable tonight. At least: what the view lists (books, episodes, articles, feeds, in any combination); format (EPUB, PDF, audiobook, plain text, Markdown, HTML, DAISY, braille, and the others `BookFormat` has); folder (a chosen folder, with or without the folders inside it); reading state (unopened, started and not finished, finished, as Books Finished counts); in the reading list or not; added within the last N days; opened within the last N days; title or author contains; and, for feeds, has new items, subscribed or unsubscribed. Whether the conditions must all match or any may. The sort (field and direction) and an optional limit ("show at most N"). Say how each condition is decided from today's data (`Book`, `Feed`, `FeedItem`, `ReadingStats.finishedBookIDs`, the reading list), and leave out any condition that would need new stored data, as a follow-up.
5. **Visibility.** "Always", "When applicable", and hidden (pick the word the settings show: "Never" or "Hidden"). What "applicable" means for each built-in view and for a filter view (it lists at least one row). At least one view is always shown (say which, and how the settings prevent hiding the last). What a window does when the view it shows stops being applicable or is hidden while shown, without moving VoiceOver's focus from under the listener or dropping them somewhere silently: say what is announced and where they land.
6. **The window's picker.** Today a segmented picker of five segments ("View", spoken "Library category"). With custom views it may not fit: decide (segmented while it fits and a pop-up beyond, a pop-up always, or another accessible control), and how VoiceOver and a braille display read it. A hosted view whose width outgrows its window can crash the test host (AGENTS.md lesson): the design must keep the picker's width bounded. Keyboard: whether views get Command-1 to Command-9 or menu items, after checking every existing shortcut (`KeyboardShortcut.swift`, the Shortcuts tab's actions) for conflicts.
7. **The settings section.** Where it goes (a new Settings tab, such as "Library", or a section of an existing tab), and its controls: the ordered list of views, each row one element that VoiceOver reads with its name, kind, visibility, and position ("Reading List, built in, when applicable, 5 of 7"); a visibility pop-up per view; Move Up and Move Down (buttons for the selected view and VoiceOver actions on the row, each announcing the new position); New View…, Edit…, Duplicate, Delete (custom views, with a confirmation), and Restore Default (built-in views). The editor sheet: name, the conditions, the sort, the limit, and a live count of what the view lists now ("Lists 23 books and 2 feeds"). Fit it to the Settings window (`SettingsTabFitTests`).
8. **Storage and migration.** Where the definitions live (`config.json` beside the other preferences, or `library.json` beside the sorts), with the reason; the key and JSON shape; how a view's sort is stored (today a category's sort lives in `Library.folderSortSettings` under a reserved key, and `BookFolder.reservedNames` keeps folders from taking those names); what an older TextMouth does with the new key (does it keep it, drop it on the next save, or refuse the file?); whether this is a PATCH or MINOR change under the version policy (`docs/developer/building.md`, "Versions"). An existing user's first launch must show exactly today's five views in today's order with today's sorts, and the new Feeds view placed and shown as you recommend.
9. **Every listener-facing wording:** labels, values, hints, announcements, the window title ("Library: <view> (<sort>)"), Speak Info and the summary line in a filter view, the empty-view sentence, and the editor's errors.
10. **Questions for the user**, each numbered, with its context in a sentence or two and a recommended answer. The team builds the recommended answers tonight, so the user only answers where they want something different. Among them: the Feeds view's default visibility and place (the user called it "optional"); the Reading List's default visibility (today it is always shown); the word for hidden; the picker's form; where the settings live.
11. **The build plan:** tasks in order, each one or two commits with its files, tests, and which can run in parallel without touching the same regions. The model and its tests first, with no change in behavior; then the window reading views instead of categories; then the settings; then custom views and the editor; then the Feeds view if it does not fall out earlier.
