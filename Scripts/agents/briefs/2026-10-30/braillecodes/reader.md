# Task `reader`: the BRF and BRL reader takes a braille file code

Team `braillecodes`, lead `braillecodes-lead`. Your slug is `braillecodes-reader`, your branch `braillecodes/reader`, made from `team/braillecodes`. Read `Scripts/agents/briefs/2026-10-30/teams-common.md`, "The worker's part", first, and follow it.

## Background

`TextMouth/Parsers/BrailleFileCode.swift` (on the team branch) is the catalog of braille file codes: `BrailleFileCode.northAmerican` (the default), `.eurobraille`, and `.unicode`, each with a `kind`: `.sevenBit(SevenBitBrailleTable)` (`dots(forByte:)` gives a byte's cell, aliases included, or nil) or `.unicodePatterns`; and a `characterName` for refusals ("braille ASCII", "Eurobraille", "a Unicode braille pattern"). Read that file whole (it is short). The design is `BRAILLE-CODES-RESEARCH-2026-10-25.md`, sections 8.5 and 8.7 (the reader's paragraph); you need nothing else from it.

`TextMouth/Parsers/BrailleFileReader.swift` reads a BRF or BRL in North American Braille ASCII only: `read(_:as:)` (line 277), `pages(fromASCII:kind:)` (lines 294-330), and `ASCIIScanner` (lines 332-478), which asks `BrailleCells.cell(forASCII:)` for each byte (line 386). Its refusals are `BrailleFileError` (lines 186-255). Every existing braille book records no code and must read exactly as before: `BrailleSampleGoldenTests` pins the samples' text, and it must pass unchanged.

## What to change

1. **Entry points.** `read(_ url: URL, as kind: BrailleFileKind, code: BrailleFileCode = .northAmerican)`, and a new `static func pages(fromText data: Data, kind: BrailleFileKind, code: BrailleFileCode) throws -> BrailleFilePages`, which does what `pages(fromASCII:kind:)` does today, in the code given (a `.pef` kind still reads a PEF, whatever the code). Keep `pages(fromASCII:kind:)` as a one-line forward to it with `.northAmerican`, documented as reading North American Braille ASCII, as before; the tests use it.
2. **The scanner** (rename `ASCIIScanner` to `TextScanner`) takes the code. Everything structural stays as it is, for every code: a UTF-8 byte order mark at the very start is dropped, a final Ctrl-Z is dropped, CR, LF, and CR LF end a line once, a form feed ends a page in a BRF and is nothing in a BRL, a tab is one blank cell, lines are counted as today, and the form-feeds-between-text rule (lines 338-350, 422-440) is unchanged. Only what a cell is changes:
   - **A seven-bit code:** a byte is the cell `table.dots(forByte:)` gives. Hoist the table out of the per-byte path (the scanner keeps it as a stored property), so the 32 MB worst case stays a lookup per byte. North American Braille ASCII therefore reads exactly as today, and Eurobraille reads its 64 characters, its capitals form, and DEL.
   - **Unicode braille patterns:** the ASCII space, 0x20, is one blank cell (some tools write the space between words); the three bytes `E2` `A0...A3` `80...BF` are the pattern U+2800 to U+28FF, whose cell is `((b2 & 0x03) << 6) | (b3 & 0x3F)`; a pattern past U+283F (dots 7 or 8) throws `BrailleFileError.eightDotBraille` (the PEF's existing sentence, "This file is eight-dot braille, which TextMouth does not read."). Check that both continuation bytes are there before reading them: a sequence cut short by the end of the file is refused, never read past the buffer.
   - **The blank cell is no text** for the form-feed rule in every code (`noteText()` only for dots other than 0), as today.
3. **Refusals**, in `BrailleFileError` (lines 186-255). The sentence a listener hears after "Reading its text failed: ":
   - A seven-bit code meets a byte that is no cell. When `found(at:in:)` (lines 442-477) gives `.byte(_)` (a byte above 0x7F that begins no valid UTF-8 character), throw a new case `eightBitBraille`: "This file looks like eight-bit computer braille, which TextMouth does not read." (research 8.5; such a file is eight-bit computer braille in a code page TextMouth cannot read). Otherwise throw, for North American Braille ASCII, today's `notBrailleASCII(found, line:)` with today's words ("Line 3 holds “é”, which is not braille ASCII."), and for any other code a new case `notInFileCode(Found, line: Int, characters: String)`: "Line 3 holds “é”, which is not Eurobraille." (the code's `characterName` after "which is not"). Both sentences are made by one private function, so the words are written once.
   - The Unicode code meets a byte that is neither structural, nor the space, nor the start of a braille pattern: `notInFileCode(found, line:, characters: "a Unicode braille pattern")`, `found` named as `found(at:in:)` names it (a byte that begins no valid UTF-8 stays `.byte`: "Line 2 holds the byte 0xE9, which is not a Unicode braille pattern.").
   - A new case `unknownFileCode(String)`: "TextMouth has no braille file characters named “x-code”." (the stored id in curly quotes, as `BrailleTranslator.Failure.unknownTable` names a table, `BrailleTranslator.swift` line 78). Nothing in this task throws it: the task that passes a book's stored code to the reader does, for an id `BrailleFileCode.code(forStored:)` does not know.
   - Every sentence is pinned by a test, exactly.
4. **Certain detection** (research 8.5): `static func certainCode(of prefix: Data) -> BrailleFileCode?` and `static func certainCode(ofFileAt url: URL) -> BrailleFileCode?`, which reads at most the first 65,536 bytes (as `pefMetadata(of:)`, lines 508-527, reads its prefix) and never throws (an unreadable file gives nil). It gives `.unicode` when the first character of the prefix that is not a byte order mark at the start, a line end, a form feed, a tab, or a space is a braille pattern U+2800 to U+28FF (bytes `E2` `A0...A3` `80...BF`, all three in the prefix); otherwise nil, and nil for an empty or all-blank prefix. It never guesses among seven-bit codes: nothing else is certain (research 7.2). An import calls it in a later task.
5. Comment every function and non-obvious block, and update the type's and functions' doc comments (lines 257-262, 272-283, 292-299, 332-333, 370-373): BRF and BRL files are read in the code given, North American Braille ASCII when none is.

## Tests

1. Both codes read every printable character 0x20 to 0x7E; they differ on DEL, which North American Braille ASCII refuses ("Line 1 holds the control character U+007F, which is not braille ASCII.", today's words) and Eurobraille reads.
