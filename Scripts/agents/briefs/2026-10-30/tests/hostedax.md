# Task `hostedax`: read hosted SwiftUI views as VoiceOver does, so the always-skipped accessibility tests can run

Slug `tests-hostedax`, branch `tests/hostedax` from `team/tests`. Read `_common.md` beside this file first. This task is a spike first: step 1 decides what the rest is.

## Why
33 tests skip on every run, with "SwiftUI exposed no button/accessibility elements/text ... without an assistive app" (or "in this run"), in 25 classes. 22 of them first wait 5 seconds in `withHostedView(_:until:)` (`TextMouthProductionTests/AccessibilityTestSupport.swift` lines 38-68), so the suite spends about 110 seconds of every run waiting for elements that never come. They read the hosted view IN-PROCESS (`accessibleControls(in:)`, lines 266-286, and `accessibilityElements(labelled:in:)`, lines 132-141), and SwiftUI builds the accessibility elements of its own texts, buttons, toggles, and rows only for a request that comes from an accessibility CLIENT, through the accessibility server.

The lead measured this on this Mac tonight with a standalone probe (a SwiftUI `Text` and `Button` in an `NSHostingView`, no TextMouth involved):
- In-process, through `accessibilityChildren()` or the legacy `accessibilityAttributeValue(_:)`: no button and no text, with VoiceOver running and the process trusted for accessibility, before and after every switch tried (`AXEnhancedUserInterface`, `AXManualAccessibility`, the private `_AXSSetAutomationEnabled` and `_AXSApplicationAccessibilitySetEnabled`, which macOS has).
- As a client of its own process (`AXUIElementCreateApplication(getpid())`, read on a BACKGROUND thread while the main thread turns its run loop, after `NSApp.finishLaunching()`): the window is not listed while it is never ordered in; once it is ordered in (`alphaValue = 0`, off every screen, `orderFrontRegardless()`, never key, from an app that does not activate) the client sees `AXWindow > AXGroup > AXStaticText (value "Probe text"), AXButton (description "Probe button")`. SwiftUI's `accessibilityLabel` reaches the client as `AXDescription`, a hint as `AXHelp`.
- VoiceOver, running all along, said nothing about the probe's window (checked with `vo watch`).
- Unknown: whether the TEST HOST (TextMouth.app, launched by xcodebuild) is trusted for accessibility (`AXIsProcessTrusted()`); the probe was, as a child of the lead's shell. Without trust the client calls fail with `kAXErrorAPIDisabled` (-25211).

## Step 1: the spike (one build)
1. New file `TextMouthProductionTests/AccessibilityClientSupport.swift` (run `xcodegen generate`), holding:
   - `struct ClientAccessibilityElement`: `element: AXUIElement`, `role`, `subrole?`, `label` (AXDescription), `title` (AXTitle), `value` (AXValue when it is text, else ""), `valueDescription` (AXValueDescription), `hint` (AXHelp), `children`; plus `descendants` (depth first, self included), `elements(role:)`, `elements(labelled:)`. Every value read is bounded: depth at most 40, at most 2,000 elements per read.
   - `extension XCTestCase { @MainActor func readAsAccessibilityClient(_ hostingView: NSView, timeout: TimeInterval = 10) -> ClientAccessibilityElement? }`: gives the hosting view's window a title unique to this read, orders it in as above (and orders it out again before returning, its alpha and frame put back), then reads on `DispatchQueue.global()` while the main thread runs `RunLoop.main.run(until:)` in 10 ms turns until the read is done or `timeout` passes. The window is found among the application element's `kAXWindowsAttribute` by that title. Returns nil when it is not found.
   - `@MainActor func pressAsAccessibilityClient(_ element: ClientAccessibilityElement) -> Bool`: `AXUIElementPerformAction(element.element, kAXPressAction as CFString)` on a background thread, the main thread turning its run loop meanwhile; true on `.success`.
   - `enum AccessibilityClient` with a once-per-run verdict, like `HostedWindowAccessibility` (lines 294-330): `AXIsProcessTrusted()` AND a probe, a SwiftUI `Button("Accessibility client probe") {}` hosted as `withHostedView` hosts, is found with role `AXButton` and that label. One message for every skip: `"This test host cannot read hosted SwiftUI views as an accessibility client (it needs Accessibility permission)"`. `@MainActor func skipUnlessAccessibilityClientReadsHostedViews() throws`.
   - Never `makeKey`, never activate the app, never use `OffscreenTestWindow` here (it ignores `orderFrontRegardless`).
2. New test class `AccessibilityClientSupportTests` in the same file: `testTheProbeButtonIsReadAsAClientReadsIt` prints one line, `ACCESSIBILITY_CLIENT: trusted=<Bool> probeFound=<Bool>`, then calls the skip helper, then asserts the probe's label, role, and hint (give the probe `.accessibilityHint("Accessibility client probe hint")`) and that pressing it runs its action once (a counter, waited for with `waitUntil`).
3. Before the run, start a read-only VoiceOver listener, so we know whether ordering test windows in makes VoiceOver speak (the user is a VoiceOver user, VoiceOver is on, and no test may make a sound): `~/.claude/skills/vo-control/bin/vo watch --duration 1500 --json > <scratchpad>/tests-hostedax-vo.jsonl 2>&1` in the background. After the run, report ONLY lines whose phrase mentions "probe", "Hosted", "TextMouth", or "window" (`grep -iE`), and delete the capture file (`rm` with its literal path). Send no other `vo` command: never change VoiceOver's state.
4. Run `AccessibilityClientSupportTests`. Grep the log for `ACCESSIBILITY_CLIENT:`.
5. Commit, and post the result to `tests-lead` at once (`bbs post tests-hostedax --to tests-lead --topic "hostedax spike: trusted=... probeFound=... VO said: ..."`), then WAIT for the lead's answer (`bbs watch tests-hostedax --timeout 600`, repeat) before step 2. The lead decides step 2 from the result.
