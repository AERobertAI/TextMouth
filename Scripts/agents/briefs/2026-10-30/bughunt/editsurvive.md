# bughunt-editsurvive: an Edit Text edit survives adding a book back and importing its package

Worker slug `bughunt-editsurvive`, branch `bughunt/editsurvive` (from `team/bughunt`). Read `README.md` beside this file first. Two fixes, one commit each, each with its tests; commit 2 before commit 1 if you find it easier, since 1 relies on 2. Both were verified by the lead by reading. The user's own data must survive: these are the user's hand edits.

## 1. A package whose record holds a taken Edit Text edit cannot be imported, nor added back
`FileImportService.readableContent(of:run:...)` (`TextMouth/Services/FileImportService.swift:1596-1622`) calls `MarkdownCacheService.generateReportedCacheAnalyzeAndStamp`, whose `writeCache` (`TextMouth/Services/MarkdownCacheService.swift:211-221`) throws `EditedTextKept` when the book's record says content.md holds the user's taken edit (B12, `BookTextEditSessions.holdsTakenEdit`). `readableContent` does not catch it, so opening from Finder a `.tmb` of an edited book that the library does not list (from a backup, another Mac, after the book was deleted) fails: "Could not import “X.tmb”. Reading its text failed: TextMouth kept the text you changed in X. Choose Redo Text Extraction to read the book's file again." (`FileImportService+Packages.swift:143-160` copies the record, `editedText` with it, `Book.swift:1292`). A reinstatement whose own record is valid takes the same path (`+Packages.swift:323-324` → `:288`). The launch repair already treats this as no failure (`LibraryViewModel+Migration.swift:981-985`): the edit stands.

Fix: when the text is an import of an existing book's package (a package import and a reinstatement; find the parameter or the call sites that say so, and do not change a fresh file's import), an `EditedTextKept` from the cache step means: keep content.md as it is, keep the edit's record (`editedText`, `textCacheFingerprint`), and index the content.md the package holds, exactly as the reader's load reads a book whose edit stands (find that path: grep `holdsTakenEdit` and the content index's analysis of an existing content.md, such as `BookContentAnalysisService`; reuse it, do not write a second reader). The import then goes on as for any package.

Test, in `TMBPackageImportTests` (grep how it builds a valid package in a temporary folder outside the library): a package whose record holds `editedText` matching its content.md (build the record as Edit Text leaves it: grep `editedText` in `BookTextEditing.swift` and in the tests, such as `BookTextEditTests`, for how a taken edit is recorded) imports; the published content.md equals the edited text byte for byte; the imported book's `editedText` is kept.

## 2. Adding back a book removed with Remove from Library Only writes its file's text over the user's edit
Remove from Library Only writes a removal marker (`TextMouth/Models/RemovedFromLibraryMarker.swift:19-64`, made by `init(book:removedAt:)`), deletes bookInfo.json (`LibraryPersistenceService.swift:1212`), and leaves content.md, the edit, in the package. Opening the package again reinstates the book from its marker (`FileImportService+Packages.swift:268-300`, `reinstate`; `reconstructedBook`, `:400-439`), which carries the braille table and the text encoding but not the edit: the book has no `editedText` and no `textCacheFingerprint`, so `writeCache` sees no taken edit, `keepTextSavedWithoutSession` (`BookTextEditing.swift:792-798`) returns at once with no fingerprint, and content.md is replaced from the book's file. The edit is gone, with no `content.md.edited-` copy; `docs/user/editing-book-text.md:15` promises the opposite.

Fix:
1. The marker also carries `editedText` and `textCacheFingerprint`, as optional fields decoded leniently exactly as `textEncodingSource` is (`@LenientOptional`, `:52`), set by `init(book:)`, so an older marker without them still decodes and a TextMouth that predates them ignores them. `reconstructedBook` gives them to the book, so B12's protection, and fix 1's import path, apply to the reinstated book: the edit stays in content.md and in the book's record.
2. The previous-record snapshot a failed reinstatement puts back (`:282-285`) also covers content.md, so a reinstatement that fails after writing content.md leaves the edit as it was.
3. The marker is part of the on-disk format: update the marker's pins in `OnDiskContractTests` in the same commit, adding the two keys (the lead approves this change to an existing test; do not change any other pin), and say so in the commit message.

Test, in `RetainedPackageImportTests` (grep `makePackage(title:)` and `removeFromLibraryOnly` there): a package with edited content.md bytes and `editedText` plus a fingerprint recorded for them; Remove from Library Only; then `importTMBPackage(identifyTMBPackage(at:))`; content.md still holds the edited bytes, and the imported book's `editedText` is not nil. A marker written without the two keys (an older one: write its JSON by hand) still decodes and reinstates as today.
