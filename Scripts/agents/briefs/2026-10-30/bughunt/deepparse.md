# bughunt-deepparse: markup nested past any real page never reaches SwiftSoup's own recursion

Worker slug `bughunt-deepparse`, branch `bughunt/deepparse` (from `team/bughunt`). Read `README.md` beside this file first. One fix, two or three commits (the scanner with its tests; the shared parse and its callers; perhaps the fragment parse), each with its tests.

## The bug (measured by bughunt-navdepth, board #4460, and checked by the lead against the code)
The team branch already stops TextMouth's own HTML walkers from recursing without bound (`HTMLNesting` in `TextMouth/Parsers/HTMLReadingText.swift`, 62e647d4; the navigation walkers, task navdepth). SwiftSoup 2.13.9 itself still recurses once per ancestor in two places:
1. **Parsing.** An end tag SwiftSoup closes through `generateImpliedEndTags(name)` (`</li>`, `</p>`, `</dd>`, `</dt>`, `</h1>`…`</h6>`) and every other end tag (`</span>`, unknown tags) calls `markStructuralChange`, whose `Node.markSourceDirty` recurses up the parents and calls the recursive `Node.ownerDocument()`: about 200 bytes a level in a debug build. 2,000 nested `<ol><li>` closed level by level need 803 KiB of stack to parse; 20,000 need 7.5 MB and 336 seconds.
2. **Attribute reads.** `getAttributes()?.asList()` (which `PublicationSemantics.hasEPUBType` calls for every `nav`, `section`, `div`, and `article`) on an element 2,000 levels deep with attributes needs 381 KiB, since materializing its attributes marks the parents dirty, recursively.

So a feed's item, a fetched article, an EPUB chapter or navigation document, a DAISY NCC or text file, an HTML book, a web archive, or textutil's HTML of a document, nested about 2,600 levels deep in those shapes, still overflows the 512 KiB stack of the worker threads imports and feed refreshes run on, and ends TextMouth; a feed does it again at every launch that refreshes it. `</div>`, `</ol>`, `</nav>` (implied end tags without a name) and `</a>` do not recurse, which is why the team branch's 10,000-`<div>` tests pass.

## What to build
1. **A scanner of nesting, without SwiftSoup.** In `HTMLNesting` (`TextMouth/Parsers/HTMLReadingText.swift`), a function that reads markup's UTF-8 bytes once, in a loop, and says whether its elements may nest deeper than a limit, **1,000 levels** (one named constant beside `deepestLevel`, with a comment: SwiftSoup's own recursion needs about 200 bytes a level in a debug build, so 1,000 levels stay far inside a 512 KiB stack; no real page comes within a tenth of it). It counts an opening tag as one level deeper and an end tag as one level shallower (never below zero), and it must never undercount a real nesting that SwiftSoup would build, while it may overcount a little:
   - no level for void elements (`area`, `base`, `br`, `col`, `embed`, `hr`, `img`, `input`, `link`, `meta`, `param`, `source`, `track`, `wbr`), for a tag ending `/>`, for comments (`<!--` to `-->`), doctypes and other `<!`/`<?` constructs, and CDATA sections;
   - no level for the elements SwiftSoup closes when a sibling of their kind begins (`p`, `li`, `dt`, `dd`, `option`, `optgroup`, `tr`, `td`, `th`, `thead`, `tbody`, `tfoot`, `rb`, `rt`, `rp`, `colgroup`, `caption`), since a long chapter of unclosed `<p>`s nests nothing; their end tags then subtract nothing either;
   - the text of `script`, `style`, `textarea`, `title`, `xmp`, `iframe`, `noembed`, `noframes`, and `plaintext` is skipped to its end tag (found without regard to case), so `if (a<b)` in a script is no tag;
   - attribute values in quotes may hold `>`; a tag name is read without regard to case.
   It stops as soon as the limit is passed, so it costs one pass at most.
2. **One shared parse.** Beside it, `HTMLNesting.parse(_ html: String, baseURI: String = "") throws -> Document` and, if any caller needs it, a body-fragment twin: markup within the limit is parsed exactly as now (`SwiftSoup.parse`, or `parseBodyFragment`); markup past it is read as its words alone: every tag replaced by a space (with the same loop's rules for what a tag is), the result wrapped in one `<p>` and parsed, so SwiftSoup decodes its character references and builds a flat document, with one `DiagnosticLog` event per document (a new tag, such as `HTML_TOO_DEEP`, naming only the markup's length and that it was read as plain words; never its text). Every word is kept; no heading, list, link, or page of such markup is.
3. **Every caller of SwiftSoup that reads untrusted markup uses it.** `grep -rn "SwiftSoup.parse" TextMouth` finds 18 calls in 10 files (`HTMLToMarkdownConverter`, `HTMLParser`, `EPUBParser+Navigation`, `DAISYParser`, `DAISYParser+NCCParser`, `DAISYParser+PackageInventory`, `TextutilDocumentReader`, `FeedTextConverter`, `FeedEpisodeImporter`, `FeedDiscovery`). Replace each with the shared parse, keeping its base URI or parser choice (an XML parser call, `Parser.xmlParser()`, keeps that parser: give the shared function a parser parameter if one needs it, rather than leaving that call out). Change nothing else in those files: other bughunt tasks have open work in `EPUBParser+Navigation.swift` and `DAISYParser+NCCParser.swift` (navdepth) and `FeedEpisodeImporter.swift` is untouched by anyone; if your branch's base lacks navdepth's changes, keep your edits there to the one line of each call, so the lead's rebase is clean.

## Tests

- The scanner, in `LegacyHTMLToMarkdownTests` or a new class beside it (a new file needs `xcodegen generate` and its `project.pbxproj`): 1,500 nested `<ol><li>` closed level by level is past the limit; 1,500 unclosed `<p>` is not; a 2,000-element `<script>` of `a<b` comparisons is not; a 500-deep nesting is not; comments, a doctype, `<br/>`, and quoted `>` in attributes count nothing.
