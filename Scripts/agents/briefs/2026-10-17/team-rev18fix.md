## FR19's next episode (REV18a; merge b1c4d1cc)
1. **medium.** `ReaderViewModel+EpisodeDownload.swift:97` (with `ReaderViewModel+GoingOn.swift:52-72`, `ReaderViewModel+Playback.swift:127`): the wait for the next episode outlives every later end decision. `goOnWithNextEpisode` checks only `restsFinishedAwaitingTheNextEpisode`, never the sleep timer, and `goOnPastThisBook` never clears `nextEpisodeWait` (not in its nothing, book, or sleep-timer branches, nor in `playFromTheEnd`'s Stop case). Episode A ends, "Downloading the next episode: B"; the listener starts a 30-minute sleep timer in A's window, `play()` runs `playFromTheEnd`, which says "Finished: A. Next book not started because of the sleep timer."; B's download then finishes and B starts anyway. The same after Feed Info is set to Stop and Play is pressed. Fix: clear `nextEpisodeWait` at the top of `goOnPastThisBook` and in `playFromTheEnd`, and have `goOnWithNextEpisode` refuse, saying `nextBookNotStartedNote`, while `sleepTimerEndsListeningHere` is true.
2. **medium.** `ReaderViewModel+EpisodeDownload.swift:56`: `restsFinishedAwaitingTheNextEpisode` looks only at this reader, so a download that takes minutes still hands over after the listener has started another book (B's `play()` pauses every other reader through `NowPlayingService.prepareForPlayback`), and a failed download's "The next episode could not be downloaded, so playback stopped" is spoken over the other book. Fix: before handing over or announcing, check that no other reader has become the playing or focused owner since A ended (for example, that A still holds the media focus).
3. **low.** `FeedDownloadManager.swift:288-295` (called from `ReaderViewModel+EpisodeDownload.swift:33`): the end-of-episode request asks again with `opening: false`, as does every Play during the wait, which takes B from its place in the queue and appends it at the back, behind a refresh's downloads. Fix: put the waiting request at the front of the queue, and never move back a request already queued.
4. **low.** `ReaderViewModel+Predownload.swift:45`: `!item.state.isTransient` also excludes `.waiting` (an item the newest-N rule put off for a network with data limits or for room), so nothing is fetched at ten minutes left. Fix: guard on `!item.state.isDownloading`.
5. **low.** `LibraryViewModel+Succession.swift:78` (with `ReaderViewModel+Playback.swift:48`): with Skip finished off, a finished next book is handed over still resting at its end, and its autoplay `play()` goes to `playFromTheEnd()`, which runs that book's end rule again instead of playing it ("Starting: 2", then "Starting: 3", none of 2 heard). The reading list's Skip Finished Books off behaves the same way today. Fix: when a hand-over lands on a finished book because skipping is off, move it back to its beginning first, as Stop and Play Starts Over does; cover the reading list too.
6. **The user's question 19** (`humanQuestions/2026-10-16.md`, recommended answer, built as the night's other answers were): when the listener cancels the download the end of an episode is waiting on, say "Download cancelled, so playback stopped." `FeedDownloadManager.cancel` sends no event today (the feedopts team's follow-up), so the reader waits silently until it closes.
7. **The fixes team's follow-up:** `ReaderViewModel+Playback.swift`'s `continueWaitingPlay()` (about line 1608) and `startChapterAfterPause()` (about 2262) still test only `isWhereAmISpeaking`, the bug team fixes closed elsewhere: use `isWhereAmISpeakingOrSoundingItsEnd`.

## The Ogg header reader (REV18b; merge ba99a1dc)
8. **low.** `OggHeaderReader.swift:116-124` (with `streamStart` at :278-301): the length comes from the last page's granule alone; a stream may start at a nonzero granule (Vorbis I spec A.2, RFC 7845 for Opus), so such a file reads long (a 30-minute episode recorded from an Icecast stream an hour in reads as 5,400 s), and `OggAudioConverter.check` then refuses afconvert's true 1,800 s, so the import fails, or a library book fails at every launch. Fix: keep the first audio page's granule and subtract the stream's start offset (that granule less the page's own samples, as libvorbisfile and opusfile do).
9. **low.** `OggHeaderReader.swift:280-297`: the stream is fixed to the first page's serial, so a file whose first start page belongs to another stream (an Ogg Skeleton "fishead", which ffmpeg2theora writes) reads as unreadable, though the comment at :286 says multiplexed files work. Fix: look through the leading start-of-stream pages (type 0x02), take the first whose first packet `identify` accepts, and assemble only that serial's packets. Test with synthetic byte streams only: **never open, play, probe, or decode a real Ogg file** (October 14).

## Saving and the test tools (REV18c; merges 8069c758 and ed095edc)
10. **low.** `LibraryPersistenceService.swift:485-486` (the same at 536-540 for feed indexes): after a write throws, the memory keeps the older bytes though the file's state is then unknown, so a later save whose bytes equal them is skipped, counted a success, and clears the checkpoint journal (an SMB rename that landed but reported failure, then an undo). Fix: forget the remembered bytes when a write throws, in one `OnDiskMemory` helper both callers use.
11. **medium.** `TextMouthProductionTests/DiskImageDrill.swift:327-329`: `fillToCapacity` writes zeros until ENOSPC without checking the image is still attached; after a detach, the mount point is an empty folder on the Mac's own disk, so a concurrent drill's sweep could make it fill the startup disk. Fix: before writing, `guard isAttached`, and refuse unless `fstat(descriptor).st_dev` is the mounted volume's device.
12. **low.** `DiskImageDrill.swift:190-203` and 262-276 (`sweepLeftovers`, called at `StorageDrillTests.swift:30`): the sweep force-detaches the drill images of any `TextMouthTests-*` sandbox, a running one included. Fix: skip a `TextMouthTests-<pid>` sandbox whose pid is alive and is not this process.
13. **low.** `Scripts/test/storage-drill.sh:54-55, 83-85`: options pass through to `run-area.py`, which returns 0 for `--dry-run`, `--list`, and `--clean` without running a test, and the script prints "Storage drill: PASSED". Fix: print PASSED only when the log shows tests executed (N > 0); the same check in every wrapper script that prints PASSED.
