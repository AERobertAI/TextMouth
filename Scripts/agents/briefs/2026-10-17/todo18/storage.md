## A. A full disk, said in plain words (commit 1)

**Why.** When a copy fails for lack of space, the system's sentence names the hidden staged package, an internal name the listener never chose, and VoiceOver reads it out: `Could not import “Salt Quay Diary.txt”. Copying it into the library failed: “Salt Quay Diary.txt” couldn’t be copied to “.import-1F2D…-….tmb” because there isn’t enough space.` The drill pins that wording today (`StorageDrillTests.swift:96-116`) with the UUID masked.

**Code.** `TextMouth/Services/ImportFailure.swift`: `struct ImportFailure` (line 66), `reason` (76: `"\(step.activity) failed: \(underlying.localizedDescription)"`), `errorDescription` (81: `Could not import “<file>”. <reason>`), `logLine` (88), and `static func reason(for:)` (102). Every import path throws an `ImportFailure`, so one change there words every step. The drill's own recognizer of a full disk is `StorageDrillTests.isOutOfSpace(_:)` (line 298): Cocoa `NSFileWriteOutOfSpaceError` or POSIX `ENOSPC`, looked for at every depth of `NSUnderlyingErrorKey`.

**Required.**
1. In `ImportFailure.swift`, one documented recognizer `static func isOutOfSpace(_ error: any Error) -> Bool` (the drill's logic, moved; domain `NSCocoaErrorDomain` code `NSFileWriteOutOfSpaceError`, or `NSPOSIXErrorDomain` code `ENOSPC`, at any depth of `NSUnderlyingErrorKey`), and one documented constant for the words: `There isn’t enough free space on the disk.` (a right single quotation mark, U+2019, as the system's own sentence uses; the sentence ends with a full stop).
2. A failure whose underlying error is out of space has the reason `<activity> failed: There isn’t enough free space on the disk.` instead of the system's sentence, so the alert reads `Could not import “Middlemarch.epub”. Copying it into the library failed: There isn’t enough free space on the disk.`. `errorDescription`, `logLine`, and a ZIP batch's list (they all build on `reason`) read the same. `ImportFailure.reason(for:)` gives the plain sentence for a bare out-of-space error too. Every other error keeps `localizedDescription` exactly as now.
3. In the drill, `testAFullDiskRefusesTheImportAndChangesNothing` (line 90): pin the new full message on purpose, drop the UUID mask (the message no longer holds an id), assert that the message contains no `.import-`, rewrite its doc comment (lines 83-89, "in the app's own words, with the reason the system gives") and the comment above the old assertion, and use `ImportFailure.isOutOfSpace` in place of the private helper, which you delete (one recognizer, not two).

## B. Sweep what a move leaves on a volume that vanished (commits 2 and 3)

**Why.** A data-directory move copies into a hidden folder beside its destination, `<parent of the destination>/.TextMouth-migration-<UUID>` (`DataDirectoryMigrator.prepareMigration`, `DataDirectoryMigrator.swift:300-336`; the name is built at 321-322 from `stagingNamePrefix`, line 295), and `defer { try? fileManager.removeItem(at: staging) }` (323) deletes it when the move ends. When the destination's volume is unplugged mid-copy, that removal fails silently, and when the volume returns the half-copied library, as large as the library, stays on it for good: the drill prints it (`STORAGE_DRILL_NOTE: the vanished move left … hidden staged copy`, `StorageDrillTests.swift:182-217`). Nothing else in the app removes it (`grep stagingNamePrefix` finds only the creation and tests). A force-quit mid-move leaves one too.

**Design (fixed; the point is that nothing but a folder this move itself made is ever removed).**
- A small journal on this Mac, in the app's machine-local folder (`MachineLocalPaths`, `TextMouth/Models/CloudStorageContract.swift:573`; add one documented `static var` beside `keptBooks` at 635, e.g. `moveLeftovers`, a JSON file `Move Leftovers.json`), lists the staging folders moves have begun and not yet cleaned up: each entry an absolute path and the date it was noted, written atomically, the newest 20 kept. An unreadable or hand-damaged journal reads as empty; it never throws and never crashes.
- New file `TextMouth/Services/MigrationStagingLeftovers.swift`, `enum MigrationStagingLeftovers` (comment every function; no `@unchecked Sendable` and no `nonisolated(unsafe)`: use `OSAllocatedUnfairLock`, so `UncheckedConcurrencyPolicyTests` stays green):
  - `isStagingName(_:)`: exactly `DataDirectoryMigrator.stagingNamePrefix` followed by a string `UUID(uuidString:)` accepts, nothing else (mirror `ImportStaging.isStagedPackageName`, `ImportStaging.swift:~165`).
  - `note(_ staging: URL, at now: Date = Date())`: records the folder in the journal and marks it in use by this process. `prepareMigration` calls it right after it computes `staging` (line 322) and before anything is created.
  - `forget(_ staging: URL)`: takes the folder out of the journal and out of use. `prepareMigration` calls it right after `publish(...)` (line 334) returns: the folder was renamed into place, so nothing is left to clean up.
  - `discard(_ staging: URL, fileManager:)`: replaces the `defer` at 323, which then runs after every exit (it finds nothing to remove after a publish). It tries to remove the folder with the given `fileManager` (so the test doubles that exist, `InterruptingFileManager` in `DataDirectoryMigrationTests.swift:933` and `CopyRecordingFileManager` in `DataDirectoryCopyTests.swift:359`, still work), marks it no longer in use, and **forgets it only when the removal succeeded**. A removal that fails, for any reason, keeps the note: when the destination's volume has been unplugged, the folder cannot be seen or removed, and "not there" cannot be told from "gone" (a mount point left on this Mac's disk keeps its parent folder, so even the parent's presence proves nothing). When the folder was still there and would not go, log `MIGRATION_STAGING_LEFT: <name>: could not be removed: <reason>`.
  - `sweep(fileManager:now:)`: for each journalled entry, in this order: drop it if its last component is not `isStagingName` (a hand-edited journal can never make it delete anything else); skip it while this process is using it; if nothing exists at the path, keep it (the volume may be away) until it is 30 days old, then drop it; if the path is not a real directory (a regular file, or a symbolic link, which is never followed), drop the entry and touch nothing; otherwise remove the folder, and on success forget it and log `MIGRATION_STAGING_REMOVED: <name>: left by an interrupted move`, on failure keep it and log `MIGRATION_STAGING_LEFT`. Log names with `DiagnosticLog.loggablePath`, never absolute paths.
  - `sweepInBackground(isHostedTest:)`: runs `sweep` on `DispatchQueue.global(qos: .utility)`; never under hosted tests. Mirror `OrphanedConversionSweep.sweepInBackground` (`OrphanedConversionSweep.swift:98-112`).
- Commit 3 wires the launch: one line in `AppDelegate.applicationDidFinishLaunching` after `OrphanedConversionSweep.sweepInBackground()` (`TextMouth/App/AppDelegate.swift:66`), with a comment.

**Tests**, new class `TextMouthProductionTests/MigrationStagingLeftoversTests.swift` (a new file: run `/opt/homebrew/bin/xcodegen generate` and commit the regenerated `TextMouth.xcodeproj/project.pbxproj` with it; leave `Scripts/test/areas.conf` to me). Work in sandbox folders (`makeSandboxDirectory(_:)`), never `~/.TextMouth`; the journal is under the sandboxed `MachineLocalPaths.root`, and every test removes it when it ends. Cases:
- `isStagingName`: the exact form passes (upper and lower case UUID); the prefix alone, a bad UUID, an extra suffix, no leading dot, and a name that merely contains the prefix all fail.
- A real `prepareMigration` between two sandbox folders (copy the set-up of the staged-leftovers tests in `DataDirectoryMigrationTests.swift` ~800-830): afterwards the journal is empty and no staging folder is left; a failed or cancelled move that created its folder leaves the journal empty too (its removal succeeded).
- A removal that fails: a `FileManager` double whose `removeItem` throws for the staging folder once. The folder and the note stay; `sweep` then removes the folder and forgets the note.
- The volume away: a note whose folder cannot be seen (its parent does not exist, or exists empty, like a mount point) survives `sweep` untouched, and is dropped only once it is older than 30 days (pass `now:`); make the folder appear (the volume returns) and the next `sweep` removes it and forgets the note.
- Never more than it was told: a journal entry naming a user's folder (`Archive`), one named `.TextMouth-migration-notauuid`, a regular file named like a staging folder, and a symbolic link named like one (to a folder holding a file) are all left alone, the invalid entries dropped, and the link's target intact.
- A folder in use by this process is skipped; two threads noting and discarding at once do not lose an entry.
- A corrupt journal (garbage bytes, a JSON object instead of the expected shape) reads as empty, and the next `note` rewrites it well.
- The 20-entry cap keeps the newest.
In the drill, `testAMoveWhoseDestinationVanishesLeavesTheSourceComplete` (line 182): after `image.attach()`, assert the hidden staged copy is on the volume (today it only prints a note; earlier drill runs found exactly one, and if that is not reliable, assert what is and say so), call `MigrationStagingLeftovers.sweep(fileManager: .default)`, and assert none is left and the journal is empty; keep the printed note if it still adds something, else remove it. Update the test's doc comment.
