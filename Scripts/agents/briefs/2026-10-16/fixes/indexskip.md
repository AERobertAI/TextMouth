## The problem (confirmed on `team/fixes` by the lead)
`LibraryPersistenceService.writeIndexFile(_:)` (`TextMouth/Services/LibraryPersistenceService.swift` about 432 to 451) writes the whole library, about 900 KB, with `encodeAndWrite(_:to:)` (465 to 468: `encodedIndex(library).write(to: url, options: .atomic)`) at every checkpoint deadline while an episode plays, even when nothing in it changed. The TODO (line 3354) asks for it to be skipped when unchanged, "sharing" the code the feed indexes already use.

That code is in the same file: `writeFeedIndexes(of:)` (about 494 to 518) keeps, per feed, the bytes this process last read or wrote (`FeedIndexesOnDisk`, 104 to 110, held in `feedIndexesOnDisk`, 101; seeded at load by `loadFeedShelf(fromPackages:reader:)`, about 530 to 545, from each index's read bytes), and skips a feed whose freshly encoded bytes equal them while its file still exists (503 to 505); it starts over when the data directory changes (`rootPath`, 496 to 498). `FeedIndexFiles.encoded(_:)` (`Services/Feeds/FeedIndex.swift` about 76) makes the bytes deterministic with `.sortedKeys` and a fixed row order, "so a save that changed nothing of a feed writes nothing for it". Its test is `FeedItemIndexFileTests.testAnUnchangedIndexIsNotWrittenAgain` (about line 161): read it first.

## What to build
1. **One shared helper, not a copy.** A small value type that remembers, per key, the bytes this process last read or wrote of a file in one data directory (`rootPath`), decides "unchanged" the way line 503 does (the bytes equal and the file exists), and starts over when the root changes. Put it in `TextMouth/Services/SavedFile.swift` (a nested type there; this adds no file, so `project.pbxproj` stays as it is), documented, generic over its key. Both `writeFeedIndexes(of:)` and library.json's write use it; `FeedIndexesOnDisk` goes away. The feed indexes' behavior must stay exactly as it is, including `loadFeedShelf` seeding the memory from the bytes it read and the `rowCount == 0` rule for a feed with no folder (508 to 510), which still records the bytes without writing. **Do not edit anything under `TextMouth/Services/Feeds/`** (team feedopts owns it): this file's two call sites are all you change.
2. **library.json uses it.** `encodeAndWrite` (or its caller) encodes once, then skips the write when the helper says the bytes are those last read or written of library.json in this data directory and the file exists; otherwise writes atomically as now and remembers the bytes. Remember them only after the write succeeded (a failed write must be tried again by the retry, `retryIndexWrite`). It must still run `failureCenter.recordSuccess(.libraryIndex)` and the checkpoint-journal clear in `writeIndexFile` when it skips: the index IS saved, which settles an earlier failed write and holds every checkpoint so far. Log a skipped write as a debug TRACE line at most (`DiagnosticLog.trace`), never an event, so frequent checkpoints do not flood the log.
3. **Seed it from the load.** Where library.json is read at launch (`load()`, about 1230, through `loadLibraryIndex()` and `readIndex(at:)`, about 1238 and 1275; the "valid index round trips" test is `LibraryIndexPersistenceTests.testValidIndexRoundTripsUnchanged`), remember the bytes read, as `loadFeedShelf` does for the feed indexes, so the first save after launch also writes nothing when nothing changed. Do not remember bytes of an index that was unreadable, preserved, or left alone (recovery, `indexWriteHold()`): those paths must behave as today.
4. **Determinism.** The skip works only if equal libraries encode to equal bytes. `encodedIndex(_:)` (472 to 476) uses a plain `JSONEncoder`. Check whether encoding the same `Library` twice, and a `Library` decoded from its own bytes then encoded, give identical bytes; look for dictionary fields in `Library` and `Book` Codable code. If any can reorder, add `.sortedKeys` to that encoder (as `FeedIndexFiles.encoded` does) and say so. Readers do not care about key order.
5. **Comments.** Document the helper, update `writeIndexFile`'s and `writeFeedIndexes`'s doc comments (the "one write path" paragraph, the memory comment at 98 to 103), and say why a skipped write still counts as a save.
