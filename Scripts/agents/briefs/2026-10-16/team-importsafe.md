## The findings (REV17b's words, lightly cut)
1. **high, data loss.** `TextMouth/Services/FileImportService.swift:797` (with :71, :83, and `TextMouth/ViewModels/LibraryViewModel+Import.swift:602`): Import Folder…'s folder-of-tracks branch returns an `ImportedBook` with `isFromPackageFolder` false, so `mayDeleteOriginal` is true, and "After Importing a Book" then acts on the whole source folder, though only the audio files and the manifest were copied. With Delete After Import, or Ask Each Time answered Yes, importing `~/Audiobooks/Night Ferries` (tracks, cover.jpg, lyrics.txt, a Bonus/ folder) trashes the whole folder, or removes it for good when Move to Trash is off. The loose-DAISY-folder case is guarded by `testPackageImportNeverDeletesOrOffersToDeleteItsFolder`. Fix: mark the folder branch's result as from a folder (the existing flag, or a clearer one if the flag's name would mislead), so a folder import never deletes or offers to delete its folder, with a folder twin of that DAISY test (and one for Ask Each Time never asking).
2. **low, but it feeds 1.** `FileImportService.swift:985`: `isFolderOfTracks` counts audio anywhere beneath the folder, but `BookFormat.detect` looks only at the top level, so a parent folder of DAISY book folders (which `isDAISYDirectory` documents as "not itself a book", and which used to be refused) now imports as one audiobook of every book's audio files, gigabytes, in name order. Fix: refuse a folder in which `DAISYParser.packageEntryPoints` finds a book in a subfolder, with the existing "holds no DAISY book" message (read it; if it misleads here, say so in your report rather than inventing new words).
3. **medium, a hand edit lost.** `TextMouth/Services/BookManifestEditing.swift:297` and :227 (result dropped at `TextMouth/ViewModels/LibraryViewModel+ManifestEdits.swift:208`): `keepTitleAndAuthor` writes a Book Info title or author into the manifest only when the folder and manifest are on this Mac and the manifest is a JSON object; otherwise it returns false and nothing records or retries the edit (`updateBookMetadata` passes no `written:`). Later the manifest's old title is taken back (`take`, `setTitleAndAuthor`), and the user's edit is silently lost: for example a retitle while the manifest is evicted to the cloud, or while manifest.json has a typo. Fix: when the write is skipped or throws, keep the row's value pending and write it into the manifest (as `keepHandEditedTitleAndAuthor` does for older edits) before the next look compares, instead of adopting the manifest's.
4. **low.** `BookManifestEditing.swift:693` with `TextMouth/Models/ChapterPauses.swift:23` and `TextMouth/Parsers/AudioManifest.swift:309` (the same comparison at `ReaderViewModel+ManifestEdit.swift:36`): `ChapterPauses.none` (an empty list) is not equal to the all-zero list `betweenTracks` returns once any manifest exists (REV17b compiled the real struct: `equal: false`), so TextMouth's own generated manifest is taken as an edit: "Manifest updated" and a rebuilt reader for a book that did not change. Fix: compare effective pauses (treat none as all zeros, for instance by normalizing an all-zero list to none in one place).
5. **low.** `BookManifestEditing.swift:559-587` (`take` at :758, `analyzeAudio` at :778) against the guard at :651: the Edit Manifest session check has no "a track is only in the cloud" guard like `look`'s, and `take` is not wrapped in `withoutDownloading`, though its own comment says nothing is downloaded, so saving a manifest edit for a cloud book whose tracks are evicted downloads all of them unasked. Fix: return `.inCloud` from `check` when any track is dataless, as `look` does.
