# Task brief: editbaselines — an editor's save changes and marks only what the user changed

Slug `editbaselines`; branch `fix/hand-edit-baselines`. Read `common-evening.md` beside this file first. Launch after `fix/october-7-followups` has merged (it edits the reader's `bookInfoSheet` and the reader's view model).

## Why
FR06 (merge 065ec6a0) records which metadata fields the user edited by hand, so the launch metadata refresh never replaces them. A read-only review on October 7 evening (TODO-2026-09-04.md, entry REV07, library finding 3) found that an editor's save compares with the wrong baseline, and the orchestrator confirmed a second, older problem in the same path:
- The simple Book Info sheet (Views/Library/LibrarySheetViews.swift about lines 60-75) calls `updateBookMetadata(updated)` with no `editedFrom:`, so `LibraryViewModel.updateBookMetadata(_:editedFrom:)` (LibraryViewModel+BookOperations.swift about lines 600-625) compares the save with the row **as it is now**. A field another window or the launch refresh changed while the sheet was open is marked "edited by hand", and a title whose only change was the sheet trimming spaces (a title taken from a file named "Notes .txt") is marked too.
- `updateBookMetadata` applies **every** editable field of the editor's copy (`applyEditableMetadata(from:)`) over the row, so a sheet opened before another change writes its stale copy back over that change.
- The reader's EPUB and audio saves (ViewModels/ReaderViewModel+Bookmarks.swift about lines 280-315) pass the reader's current `epubMetadata`/`audioMetadata` as what the editor opened with, but `showEditedMetadata()` (ReaderViewModel+LibraryUpdates.swift about lines 163-169) re-merges those while the editor is open. A change that lands meanwhile becomes a false hand edit and is reverted. Example: the first launch's refresh replaces "Unknown Author" while that book's editor is open; the user fixes the title; the save marks the author and puts Unknown back, permanently.
- Older still: saving Book Info for a book whose file is only in the cloud turns an unknown EPUB publisher and date into empty strings (LibraryBookInfoLoader.swift about lines 146-147 shows "" for them, and the save at LibraryViewModel+BookOperations.swift about lines 669-670 stores it), and the audio editor does the same for album, genre, and year. The app then treats "" as a deliberate clearing that hides the file's values.

## Items, one commit each, each with its tests
1. **Apply and mark only what the user changed.** A save carries what its editor opened with; `updateBookMetadata` applies to the **current** row only the fields whose saved value differs from the opened value, and marks exactly those. Every caller passes what its editor opened with: the simple sheet captures its fields when it opens; `MetadataEditorView` keeps the values it opened with and hands them to `onSave`, and the reader passes that snapshot rather than its current `epubMetadata`/`audioMetadata`. Tests: a field changed elsewhere while an editor is open is neither marked nor overwritten; a field the user changed is applied and marked; a trimmed-only title is not marked.
2. **An unknown value stays unknown.** A field the editor showed empty because nothing was known (a cloud-only book's EPUB publisher and date, an audiobook's album, genre, and year) and that the user left empty is saved as unknown (nil), not "", so the file's values still show later. Tests for both editors.
