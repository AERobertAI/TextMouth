## The reading list
<!-- id: reading-list; keys: playlist, queue, Continue to Next Book, Add to Reading List, Remove from Reading List, Next in Reading List, Library menu, finished books; src: TextMouth/Models/ReadingList.swift, TextMouth/Models/ReadingListCommand.swift, TextMouth/Models/ReadingListWording.swift, TextMouth/Models/ReadingListPlace.swift, TextMouth/Models/Library.swift, TextMouth/Models/LibrarySortState.swift, TextMouth/Models/ImportDecision.swift, TextMouth/Models/LibraryInfoWording.swift, TextMouth/Models/KeyboardShortcut.swift, TextMouth/ViewModels/LibraryViewModel+ReadingList.swift, TextMouth/ViewModels/LibraryViewModel+SortAndOrder.swift, TextMouth/ViewModels/LibraryViewModel+Import.swift, TextMouth/ViewModels/LibraryViewModel+Duplicates.swift, TextMouth/ViewModels/LibraryViewModel.swift, TextMouth/ViewModels/LibraryListCache.swift, TextMouth/ViewModels/ReaderViewModel+ReadingList.swift, TextMouth/Services/ReadingStatsService.swift, TextMouth/Views/Library/ReadingListOptionsBar.swift, TextMouth/Views/Library/LibraryView.swift, TextMouth/Views/Library/LibrarySubviews.swift, TextMouth/Views/Library/LibraryInfoRow.swift, TextMouth/Views/ContentView.swift, TextMouth/App/MenuCommands.swift, TextMouth/ViewModels/ReaderViewModel.swift, TextMouth/Views/Library/LibrarySheetViews.swift -->

The reading list (FR09): books from any folder, in an order the user arranges, and what a book opened from it does when it ends.

- Owner: Library.readingList, a ReadingList (Models/ReadingList.swift), saved in library.json with the rest of the index: the books' IDs in reading order, each once, and three options, continuation (ReadingList.Continuation: playBookBelow, the default, playBookAbove, or stop, saved by its raw value, never by the words the options bar shows) skipsFinished (true until cleared), and removesFinished (false until set: a finished book on the list leaves it).
  It is read leniently: an ID that can't be read is skipped, one listed twice is kept where it first appears, an option missing or unknown reads as its default, and a list that can't be read at all is left empty, so it never makes the index unreadable.
- Who may write it: LibraryViewModel+ReadingList, every change through editReadingList(_:), which edits the list as the window shows it, any ID naming no book left out, and makes a change one change of library and one save, and a request that changes nothing no save: addToReadingList and removeFromReadingList, whose announcing forms serve a row's, a selection's, the edit-mode bar's, and the Library menu's commands and say what they did, or why nothing changed, in ReadingListWording's words, each through LibraryView's changeReadingList(_:with:), which at the Reading List also takes the books taken off the list out of both selections, so the edit-mode bar counts the books still shown; moveInReadingList and reorderReadingList, for Move Book Up and Down and a drag; and setReadingListContinuation, setReadingListSkipsFinished, and setReadingListRemovesFinished, for the options bar. removeFinishedBookFromReadingList(_:) takes a just-finished book off the list when removesFinished is on, through removeFromReadingList(_:), silently: LibraryViewModel.observeFinishedBooks(of:), which startLibrary starts, hears ReadingStatsService.markBookFinished's .bookDidFinish, which is posted for every end it is told of and not for a rewind's replay, and receives it on DispatchQueue.main, so the removal never comes within the telling.
  Two things order the removal.
  A reader of a book from the list asks readingListContinuation(after:) in the turn it tells the end, and that answers only for a book still on the list, so the finished book is still there to be asked about.
  And a reader that reads its book from the list holds it at its end (ReaderViewModel.holdFinishedBookOnReadingList(), made before the end is told, counted in LibraryViewModel.readingListHoldCounts): the book is still the list's for that reader, whose replayed end, Play at the end, and Next in Reading List all ask the list, and the list overrides the book's own end rule (the user, October 7, 2026).
  While a hold stands, a finished book is noted (finishedBooksAwaitingRelease) and stays; the reader releases the hold (releaseFinishedBookOnReadingList(), then LibraryViewModel.releaseFinishedBookFromReadingList(_:)) when it goes on to another book through the list (continueThroughReadingList(to:), openFromReadingList(_:)) or closes (close()), and the book leaves then.
  A book no reader holds, finished elsewhere such as a feed item marked played, leaves one turn after the telling.
  The reader then reads its book as any book (ReaderViewModel.followReadingList(in:)).
  Turning the option on takes off none of the books already finished.
  An older TextMouth ignores the key and reads the option as off, and drops the key at its next save of library.json (a playing book saves within five minutes), which turns the option off for every Mac sharing the library.
  An import made at the Reading List (ImportRequest.addsToReadingList, set through the addingToReadingList: parameter of importFiles, importDAISYFolders, importZipAsync, importSingleFileAsync, and createBookFromText) adds its books to the list's end at every place its books join the library, a ZIP batch's together, through addImportedBooksToReadingList(_:request:), which announces ReadingListWording.importedAnnouncement(added:folderPath:), naming the folder the books went to, or LibraryFolderOption.rootLabel; a book already in the list stays where it is, and nothing is said when none joins.
  A duplicate's Replace calls ReadingList.replace(_:with:) before removeDeletedBook, so the new copy takes the old one's place before the old one leaves; a Replace at the Reading List of a book not on the list adds the copy to its end, as Keep Both does.
  Library.removeBook(id:) and removeFolderAndContents(id:) take a removed book off the list, so every way a book leaves the library ends there, the books Remove from Library Only retired included (retirement markers, below).
  The list's order is its own: moving a book in it never touches a folder's manual order.
- How others observe it: LibraryCategory.readingList, the Library window's fifth category, lists readingListBooks, which a search narrows and nothing sorts.
  A book row carries ReadingListCommands (Add to Reading List for its books not in the list, Remove from Reading List for those in it, each counting a selection's books), as context menu items and as its last VoiceOver actions, and, in edit mode, EditModeBar shows ReadingListCommand.editBarCommands(for:inList:atReadingList:) beside Move: those a selection's row would offer, or, with nothing selected, the one the view suggests, acting on no book and so dimmed (Remove at the Reading List, Add elsewhere), worded by ReadingListWording.editBarTitle, editBarLabel(_:count:), which counts the books as Move's label does, and editBarHint, and run through LibraryView's performReadingListCommand; a book row also says, outside the Reading List, "In reading list" (ReadingListWording.inReadingListNote) in its accessibility label, right after the title and author (BookRow.rowAccessibilityLabel), so it is in the same place on every row; the row has no accessibility value (until October 17, 2026 "In reading list" was its value, the empty string for a book not in the list).
  At the Reading List, ReadingListOptionsBar shows the options, the Sort menu's one item is ReadingListWording.orderName, checked, the window is titled "Library: Reading List", and an empty list shows ReadingListWording.emptyList as a row.
  Speak Info says a book's place in the list in every view, the brief summary and the full alike (BookInfoFacts.readingListPlace, a ReadingListPlace, which LibraryInfoWording.briefParts(of:) says through readingListNote(_:) after the place note, "In reading list, 3 of 12").
  LibraryOrderCommandsSupport (Views/Library/LibraryView.swift) takes the Library menu's Move Book Up and Down and Add to and Remove from Reading List, which post addToReadingList and removeFromReadingList, for the Library window that takes the command (WindowCommandRouting); ShortcutAction.addToReadingList and .removeFromReadingList are in the Library group, with no default keys. readingListNeighbor(of:direction:skippingFinished:) and readingListContinuation(after:) answer what a reader of a book from the list asks (reading from the reading list, under the reader, below).
  A book counts as finished by LibraryViewModel.finishedBookIDs, what Books Finished records (ReadingStats.finishedBookIDs), which tests replace: a deliberate record, unlike a position near the end (P07), kept when the book is read again.

### Who owns feed items
<!-- id: who-owns-feed-items; keys: feedLink, FeedItemRows, shelf, kept row, feed folder, layout version; src: TextMouth/Models/FeedBookLink.swift, TextMouth/Models/Book.swift, TextMouth/Models/BookInfo.swift, TextMouth/Models/Library.swift, TextMouth/Models/LibraryFeedShelf.swift, TextMouth/Models/FeedItem.swift, TextMouth/Services/Feeds/FeedIndex.swift, TextMouth/Services/Feeds/FeedPaths+Items.swift, TextMouth/Services/Feeds/FeedStore.swift, TextMouth/Services/Feeds/FeedCenter.swift, TextMouth/ViewModels/LibraryViewModel+Feeds.swift -->

Owner: the library model, with each feed's index on disk.
A feed item's row is a Book whose feedLink (Models/FeedBookLink.swift: the feed's ID and the item's) names the feed and item it came from.
The link travels with the row's file location (Book.FileLocation, so a reader following a moved row finds the package) and with the package record (BookMetadata.feedLink, which makeBookInfo() and Book(record:filePath:folderPath:tmbDirectoryName:) carry both ways, a save writing the row's link or else keeping the record's), and it makes tmbDirectory place the package in the feed's own folder, Feeds/<feed ID>/, beside the feed's record (Book.packageDirectory(inDataDirectory:); Services/Feeds/FeedPaths+Items.swift: itemsFolder(of:in:), indexFile(of:in:), packageDirectory(named:of:in:), and feedID(ofItemsFolderNamed:), which takes a folder named by a feed's ID alone, so FeedStore never takes the folder for a record).
Each feed's index is Feeds/<feed ID>/library.json (FeedIndex, Services/Feeds/FeedIndex.swift: its layout version, 1, the feed's ID, and a row for each package, as library.json would hold the row, its link included), which FeedIndexFiles.encoded(_:) writes as compact JSON with sorted keys and its rows by date added, so one index is always the same bytes.
Reading one checks its layout version first (FeedIndex.init(from:), a missing one read as 1), and one of a later version throws FeedIndexNewerLayout.
While TextMouth runs, a feed item's row is in one of two places in the Library: among books while its file is here, so the reader, positions, bookmarks, settings, the reading list, and Stats reach it as they reach any book; or else on Library.feedShelf (FeedShelf, Models/LibraryFeedShelf.swift: the rows held apart, which no list, count, or pass meets, among them, since FR11's branch A2, each row kept after its file went, holding the listener's place; and indexedFeedIDs, the feeds whose indexes the library keeps, so a feed whose last row left gets an empty index and a feed no library named is never written; and indexesLeftAlone, the feeds whose index files no writer touches while TextMouth runs: one only in the cloud, one of a later layout, and a gone feed's while its downloads return to the library, leaveIndexAlone(of:) and forgetIndex(of:); and keepIndex(of:), for a feed whose index is written though its last row left, as Move to Library… leaves it).
Library.libraryBooks and libraryBookCount are the library's own books, every row without a link, and Library.feedIndexRows is each feed's rows, wherever they are, leaving out the feeds in FeedShelf.indexesLeftAlone, for every writer.
Each feed's rows by the identity of the item each came from are FeedItemRows (downloaded, among the books, and kept, on the shelf), which the model's FeedItemRowLookup works out once for each change of the library, keyed by the list cache's content revision, for feedItemRows(of:) and feedBook(withID:), so a feed's counts, an item's state (FeedCenter.state(of:in:) and downloadedRow(of:in:)), whether it is new, and a download restoring a kept row each find a row in one step rather than by a scan.

### Who may write feed items

Who may write it: a download publishes its package into the feed's folder (FeedEpisodeImporter.destinationPackageURL, which makes the folder), and LibraryViewModel.addFeedBook(_:) adds its row with its link and no library folder (downloads, under Feeds, below).
Every save goes through LibraryPersistenceService.writeIndexFile, the one write path of library.json, which first writes each feed's index from Library.feedIndexRows (writeFeedIndexes(of:), through FeedIndexFiles.encodedIndexes(of:placedIn:), each row placed where its package is by FeedIndexFiles.placed(_:in:of:), and FeedIndexFiles.write(_:in:fileManager:)), only an index whose bytes differ from what this process last read or wrote of it, or whose file is gone (feedIndexesOnDisk, a SavedFile.OnDiskMemory keyed by feed ID and confined to the save queue; library.json's write uses the same memory, above), and then library.json, whose encoding (Library.encode(to:)) writes only libraryBooks, so no writer of library.json, a save, a checkpoint, the quit flush, a retry, Rebuild Library Index, or the data-directory move, can hold a feed item's row.
A feed's index that can't be written throws FeedIndexWriteError, naming its file, before library.json is touched, and is reported and retried as a failed library index write.
Reading library.json clears any link a row holds (Library's decoder, through Book.placedInLibraryFolder()), as orphan adoption and a package import do for a package found in the Library folder, whose record keeps the link: only a package in its feed's folder is a feed item's.
At launch, LibraryPersistenceService.load() reads every feed's folder onto the shelf (loadFeedShelf(fromPackages:reader:), FeedIndexFiles.readAll(in:fromPackages:reader:), reading each index without downloading it through an injectable reader), each row placed where its package is, so moving the data directory or opening the library on another Mac rewrites no index first; an index that can't be read is preserved beside itself (SavedFile.preserveUnusable, FEED_INDEX_UNREADABLE) and its rows rebuilt from the packages' records, and a package the index doesn't list is read from its record too (FEED_INDEX).
An index only in the cloud, whose download is asked for (FEED_INDEX_IN_CLOUD), or of a later layout (FeedIndexNewerLayout, FEED_INDEX_NEWER) is left alone (FeedIndexFiles.Contents.isLeftAlone, kept in FeedShelf.indexesLeftAlone): its rows come from the packages' records, no writer writes it while TextMouth runs, and a library.json write meanwhile keeps the checkpoint journal.
The startup repair (migrateOldBooksIfNeeded) shelves every feed item's row first (Library.shelveFeedItems()), since its repairs reconcile the library's own books with the Library folder, and at its end joinFeedItems(journaled:access:skips:) takes the newer positions the checkpoint journal names from their records for every shelf row, and moves the rows whose files are here, or in the cloud, to books; a library.json row sharing a joining row's ID gives way to the feed item's, whose package is the one here, and a shelf row sharing a book's ID that stays is dropped.
While library.json can't be read, the provisional library takes each feed's rows from its packages' records, and Try Again and the data directory's return keep the session's (carryingRecoverySessionState(from:into:), through feedItems(of:over:), in LibraryViewModel+IndexRecovery.swift).
Once the feed engine's records load (moveFeedDownloadsOnceRecordsLoad()), LibraryViewModel+FeedItemMove.swift moves the downloads made before FR11 that a feed's record names as downloaded (FeedItemState.bookID), subscribed to or not, into their feeds' folders (moveDownloadsIntoTheirFeeds(records:), holding the storage work as moving books between folders does), leaving a book where it is when its row names no package the library manages (FileImportService.namesManagedPackage(_:), FEED_DOWNLOAD_MOVE_REFUSED): each package moves in one rename, its row takes its link and its record is written there (moveIntoItsFeed(_:link:root:), through relocatePackage(of:as:root:)), and LibraryPersistenceService.saveAndWait(_:) writes the feeds' indexes and then library.json at once, so a crash between any two steps is mended at the next launch (FEED_DOWNLOADS_MOVED, FEED_DOWNLOAD_MOVE_FAILED).
It then returns the downloads of each feed whose record is gone (below), and marks downloaded again each item an older TextMouth marked not downloaded, when its file is on this Mac (markFeedItemsDownloadedAgain(access:), FEED_ITEMS_DOWNLOADED_AGAIN); a row whose file is not goes back to its feed's shelf as kept (FEED_ITEMS_KEPT).
Move to Library… (FR11's branch D; ViewModels/LibraryViewModel+MoveToLibrary.swift: moveToLibraryReturningOutcome(_:toFolder:), for the rows booksMovableToLibrary(_:) keeps, each an item's download whose record says it is downloaded as that very row (.downloaded(bookID:)), so no two moves mark one item, or else a MoveToLibraryError) makes a feed's download a book of the library's own in an order whose every stop keeps the book.
It marks each item FeedItemState.inLibrary(bookID:), the listener's from then on, and waits for the record (FeedStore.flush(), before it holds the storage work, since a record's write is storage work itself), moving nothing when the record isn't saved (FEED_MOVE_TO_LIBRARY_PUT_OFF): that write is the move's commit point, ahead of the rename where the addendum had it after, so a crash never lets the launch's move of downloads carry the book back into its feed.

A stop before the rename leaves the item In Library with its download in its feed, which markFeedItemsDownloadedAgain(access:) heals at the next launch; a stop after it leaves the package under Library/, which the startup repair adopts under its own book ID (joinFeedItems(journaled:access:skips:)); and the launch's move of downloads passes over an item In Library, reading only FeedItemState.bookID (FeedMoveToLibraryOperationTests).
