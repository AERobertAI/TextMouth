# The library index

Part of [TextMouth's architecture](../../../ARCHITECTURE.md).

- The library: every book's row, the folders, each location's sort, and the reading list (below).
  - Owner: LibraryViewModel.library, published on the main actor. It is the live copy; library.json, with each feed's own index (feed items, below), is its saved form. Each location's sort is kept in folderSortSettings under the location's key (LibraryLocation.sortSettingsKey): a folder's path in Folders, and in every other category a reserved key (LibraryCategory.sortSettingsKey: __allItems__, __unopened__, __recent__, and __readingList__, under which nothing is saved), which no folder may take as its name (BookFolder.reservedNames, made from those keys and the former No Folder category's __noFolder__). The Feeds view and each view the listener made (LibraryViewDefinition.sortSettingsKey) keep their sorts under "/views/" and the view's stored identity (LibraryViewDefinition.sortSettingsKeyPrefix), as "/views/Feeds" or "/views/" and a UUID: a folder path never begins with "/", so no folder can take such a key and BookFolder.reservedNames needs no more names, and renaming, moving, deleting, and repairing folders never touch these keys, which are not valid library paths. The Library tab's commands write them through LibraryViewsSettingsActions: Duplicate copies the sort shown to the copy's key, Delete removes the deleted view's key, and Restore Default removes the restored view's key, or, for Unopened, writes its shipped sort under __unopened__; the editor's Sort By and Order save under the same key as the Sort menu. An older TextMouth keeps these keys, reading every key of folderSortSettings and writing them back.
  - Who may write it: LibraryViewModel and its extensions, on the main actor. Each change is followed by save(), which hands a snapshot to LibraryPersistenceService.save(_:). That waits half a second on the service's serial queue, and only the newest snapshot is written, so an older snapshot never lands after a newer one. A reading checkpoint goes through saveReadingCheckpoint(_:of:writingWithin:) instead, which lets its snapshot wait up to five minutes (readingCheckpointDelay), since the book's record holds the checkpoint meanwhile: any ordinary save writes it sooner, and writePendingIndexSoon() brings it forward when a reader closes (unregisterOpenBook) and when a record cannot take its checkpoint, being only in the cloud or failing to be written. Until an index write holds every checkpoint, ReadingCheckpointJournal names the books whose records are ahead in reading-checkpoints.json, noting each before its record is written, and launch's repair gives each book it names its record's newer position and last-opened date (booksWithCheckpointsAhead() and adoptNewerRecordedPositions). flushPendingSave() writes a waiting snapshot before the app quits. Every write first writes each feed's index whose bytes changed or whose file is gone (feed items, below), then replaces library.json atomically, as compact JSON with sorted keys (encodedIndex(_:)), unless it holds those bytes already: they equal what this process last read or wrote of it, and the file is still there (writeLibraryFileIfChanged(_:), through libraryIndexOnDisk, a SavedFile.OnDiskMemory confined to the save queue like the feed indexes' memory). A save that changes nothing of the library's own books, as the reading checkpoints of a feed episode do while it plays (its row is in its feed's index), therefore writes nothing to library.json. The keys are sorted because Library.folderSortSettings is a dictionary, whose order can differ between two equal ones; the first save after upgrading from a release that wrote them unsorted rewrites the file once. A write skipped so still counts as a save: it settles an earlier failed write (failureCenter.recordSuccess(.libraryIndex)), such as a feed's index that could not be written and is written by the retry while library.json is unchanged, and clears the checkpoint journal, as a write does. A write of library.json that throws, as a write of a feed's index does, forgets what the file was remembered to hold (SavedFile.OnDiskMemory.write(_:for:using:), in [shared helpers](../shared-helpers.md)), since the file's state is then unknown: the retry, and any later save whatever it holds, writes again. Reading library.json notes its bytes (rememberLibraryIndex(_:readFrom:)), so the first save after launch writes nothing when it changes nothing; a library.json that cannot be read or decoded is forgotten, so the next save writes it whatever it would encode to.
  - How others observe it: SwiftUI views observe LibraryViewModel. A reader takes a copy of its book when it opens and reports back through LibraryViewModel: updateLiveReadingPosition (live reading positions, below, which change nothing in the library), persistReadingPosition (the row and the package record at once, library.json within five minutes), and updateContentIndex. Every change of library is offered first to LibraryViewModel.listCache (the lists Library windows show, below), then to LibraryViewModel.bookUpdates, which keeps the copies of open readers current (a reader's copy of its book, below). No timer republishes the library: nothing a Library window shows depends on the clock, and a value that ever does should use a TimelineView rather than a tick that redraws every window. Every window, menu, and list reads a location's sort through Library.sortState(at:), from Library.sortSetting(at:) (Models/LibrarySortState.swift). At the Reading List, which shows an order of its own (LibraryLocation.keepsItsOwnOrder), that is always FolderSortSetting.readingListOrder, shown as manual order, and userChangedSort(_:at:) saves nothing there. Anywhere else it is the first of these that exists: the setting saved under the location's key; in Unopened alone, which took No Folder's place on October 7, 2026, the setting saved under No Folder's key, __noFolder__, unless its field is manual order, which was the arrangement of the root's books alone; and the category's default (title ascending; last opened descending in Recently Opened; date added descending in Unopened, FolderSortSetting.unopenedDefault, since no unopened book has been opened). Nothing is written under __noFolder__ again, so a sort chosen in Unopened, saved under __unopened__, takes that one's place for good. Outside the Reading List, userChangedSort(_:at:) saves only a sort that LibrarySortState.applying(_:) changed: choosing the field shown again returns the sort unchanged (A11), so nothing is saved, and only LibrarySortChange.reverseDirection, the menu's Sort Ascending or Sort Descending, reverses a direction.
  - Files: Models/Library.swift, Models/LibrarySortState.swift, Models/LibraryViewDefinition.swift, ViewModels/LibraryViewsSettingsActions.swift, Models/BookFolder.swift, ViewModels/LibraryViewModel.swift and its extensions, Services/LibraryPersistenceService.swift, Services/LibraryLoadResult.swift.
- Live reading positions: where readers are in their books between checkpoints, for the rows and the summary bar.
  - Owner: LibraryViewModel.livePositions, a LiveReadingPositions on the main actor, holding one LiveReadingPosition for each book, kept for the session.
  - Who may write it: readers, about once a second while they play, through LibraryViewModel.updateLiveReadingPosition; a book no longer in the library changes nothing. When openBookIDs changes, a book no reader has open drops its entry (keepOnly), its reader having saved its position to the library as it closed.
  - How others observe it: a book's row (BookRow) observes its own book's entry, so a live position redraws that row alone, and the summary bar (TimeRemainingBar) observes the store; the library model publishes nothing. A live position is shown in place of the row's own only while it is the newer (ReadingPosition.lastUpdated), so a checkpoint, or a position another window saved, takes over at once.
  - Files: ViewModels/LiveReadingPositions.swift, ViewModels/LibraryViewModel.swift, ViewModels/LibraryViewModel+BookOperations.swift, Views/Library/LibrarySubviews.swift.
- The lists Library windows show: each location's books in its sort, narrowed by a search, and the book counts of folder trees.
  - Owner: LibraryViewModel.listCache, a LibraryListCache on the main actor, which derives each list once and keeps it, at most LibraryListCache.entryLimit lists, until a change it depends on. It publishes nothing, so a window may derive and store a list while SwiftUI draws.
  - Who may write it: the library itself, which offers every change of library to listCache.libraryDidChange(from:to:) before anything reads it. A change of membership (which books there are, their order in the library, their folders, and their feed links), of the reading list's books or their order (LibraryListCache.readingListMayDiffer, which its options never change), or of a field a sort or a search reads (the title, the author, the dates added and last opened, the manual order, and the book's file) drops every list; any other change, such as a word count or a voice setting, keeps every list's order and refreshes only its books' values. A reading checkpoint stamps the book's last-opened date, so it sorts the lists again. Folder trees are counted in one pass whenever the lists are dropped, from the library's own books, and the sizes a File Size sort reads are measured once per book, until its file changes. A list's key (LibraryListCache.Key) holds, for a feed's folder in Folders, the feed whose items it lists, so the list is derived again when that changes although no book did.
  - How others observe it: a Library window reads its list through displayedBooks(at:matching:) and bookCount(inFolderTree:) as often as it draws: the first read after the lists were dropped derives its list again, and the first after any other change refreshes the list's books. Before sorting, a location lists LibraryViewModel.booksForCategory's books: a folder's in Folders, with its feed's items for a feed's folder (feedItems(listedIn:)); every book of the library's own in All Items (Library.libraryBooks); in Unopened every book of its own never opened, from every folder (Library.unopenedBooks(), the books Book.isUnopened names, those whose lastOpened is nil, as a record's BookState.isNew says too); in Recently Opened the ten rows opened last, books and feed items alike, of each feed's items only the one opened last, which takes one of the ten places (LibraryBookSorter.recent(_:limit:)); and at the Reading List the list's books in its order (readingListBooks), which displayedBooks(at:matching:) never sorts, a search narrowing that order. A feed's items are listed nowhere else (feed items, above). Opening a book stamps its lastOpened, which the lists depend on, so the book leaves Unopened as the list is derived again. LibraryLocation.manualOrderFolder is nil in All Items, Unopened, Recently Opened, and the Reading List, whose books come from many folders that share no one order. What dragging and Move Book Up and Move Book Down rearrange is LibraryLocation.reorderTarget(sortedBy:), a LibraryReorderTarget: a folder's manual order in Folders, the root included, while the list shows it, or the reading list at the Reading List, always. LibraryViewModel.moveBook(_:direction:in:) and reorderBooks(in:from:to:) take a move or a drag there, and each move made from the Library menu, the keyboard, or a row's context menu is announced alike (ManualBookOrder.MoveResult.announcement, as in "Moved Bestiary above Almanac"). A row's Move Up and Move Down VoiceOver actions go through LibraryView's moveSayingPlace(_:direction:), which moves through moveBook(_:direction:in:) as well and announces the book's new place instead (MoveResult.placeAnnouncement, "Dune, 3 of 12", MoveResult.count being the order's length as the list shows it), or, when the list changed after the row offered the move, ManualBookOrder.cannotMoveAnnouncement ("Dune can't move up.").
  - Files: ViewModels/LibraryListCache.swift, ViewModels/LibraryViewModel+FolderManagement.swift, ViewModels/LibraryViewModel+SortAndOrder.swift, Models/LibraryBookSorter.swift, Models/LibrarySortState.swift.
- The reading list (FR09): books from any folder, in an order the user arranges, and what a book opened from it does when it ends.
  - Owner: Library.readingList, a ReadingList (Models/ReadingList.swift), saved in library.json with the rest of the index: the books' IDs in reading order, each once, and three options, continuation (ReadingList.Continuation: playBookBelow, the default, playBookAbove, or stop, saved by its raw value, never by the words the options bar shows) skipsFinished (true until cleared), and removesFinished (false until set: a finished book on the list leaves it). It is read leniently: an ID that can't be read is skipped, one listed twice is kept where it first appears, an option missing or unknown reads as its default, and a list that can't be read at all is left empty, so it never makes the index unreadable.
  - Who may write it: LibraryViewModel+ReadingList, every change through editReadingList(_:), which edits the list as the window shows it, any ID naming no book left out, and makes a change one change of library and one save, and a request that changes nothing no save: addToReadingList and removeFromReadingList, whose announcing forms serve a row's, a selection's, the edit-mode bar's, and the Library menu's commands and say what they did, or why nothing changed, in ReadingListWording's words, each through LibraryView's changeReadingList(_:with:), which at the Reading List also takes the books taken off the list out of both selections, so the edit-mode bar counts the books still shown; moveInReadingList and reorderReadingList, for Move Book Up and Down and a drag; and setReadingListContinuation, setReadingListSkipsFinished, and setReadingListRemovesFinished, for the options bar. removeFinishedBookFromReadingList(_:) takes a just-finished book off the list when removesFinished is on, through removeFromReadingList(_:), silently: LibraryViewModel.observeFinishedBooks(of:), which startLibrary starts, hears ReadingStatsService.markBookFinished's .bookDidFinish, which is posted for every end it is told of and not for a rewind's replay, and receives it on DispatchQueue.main, so the removal never comes within the telling. Two things order the removal. A reader of a book from the list asks readingListContinuation(after:) in the turn it tells the end, and that answers only for a book still on the list, so the finished book is still there to be asked about. And a reader that reads its book from the list holds it at its end (ReaderViewModel.holdFinishedBookOnReadingList(), made before the end is told, counted in LibraryViewModel.readingListHoldCounts): the book is still the list's for that reader, whose replayed end, Play at the end, and Next in Reading List all ask the list, and the list overrides the book's own end rule (the user, October 7, 2026). While a hold stands, a finished book is noted (finishedBooksAwaitingRelease) and stays; the reader releases the hold (releaseFinishedBookOnReadingList(), then LibraryViewModel.releaseFinishedBookFromReadingList(_:)) when it goes on to another book through the list (continueThroughReadingList(to:), openFromReadingList(_:)) or closes (close()), and the book leaves then. A book no reader holds, finished elsewhere such as a feed item marked played, leaves one turn after the telling. The reader then reads its book as any book (ReaderViewModel.followReadingList(in:)). Turning the option on takes off none of the books already finished. An older TextMouth ignores the key and reads the option as off, and drops the key at its next save of library.json (a playing book saves within five minutes), which turns the option off for every Mac sharing the library. An import made at the Reading List (ImportRequest.addsToReadingList, set through the addingToReadingList: parameter of importFiles, importDAISYFolders, importZipAsync, importSingleFileAsync, and createBookFromText) adds its books to the list's end at every place its books join the library, a ZIP batch's together, through addImportedBooksToReadingList(_:request:), which announces ReadingListWording.importedAnnouncement(added:folderPath:), naming the folder the books went to, or LibraryFolderOption.rootLabel; a book already in the list stays where it is, and nothing is said when none joins. A duplicate's Replace calls ReadingList.replace(_:with:) before removeDeletedBook, so the new copy takes the old one's place before the old one leaves; a Replace at the Reading List of a book not on the list adds the copy to its end, as Keep Both does. Library.removeBook(id:) and removeFolderAndContents(id:) take a removed book off the list, so every way a book leaves the library ends there, the books Remove from Library Only retired included (retirement markers, below). The list's order is its own: moving a book in it never touches a folder's manual order.
  - How others observe it: LibraryCategory.readingList, the Library window's fifth category, lists readingListBooks, which a search narrows and nothing sorts. A book row carries ReadingListCommands (Add to Reading List for its books not in the list, Remove from Reading List for those in it, each counting a selection's books), as context menu items and as its last VoiceOver actions, and, in edit mode, EditModeBar shows ReadingListCommand.editBarCommands(for:inList:atReadingList:) beside Move: those a selection's row would offer, or, with nothing selected, the one the view suggests, acting on no book and so dimmed (Remove at the Reading List, Add elsewhere), worded by ReadingListWording.editBarTitle, editBarLabel(_:count:), which counts the books as Move's label does, and editBarHint, and run through LibraryView's performReadingListCommand; a book row also says, outside the Reading List, "In reading list" (ReadingListWording.inReadingListNote) in its accessibility label, right after the title and author (BookRow.rowAccessibilityLabel), so it is in the same place on every row; the row has no accessibility value (until October 17, 2026 "In reading list" was its value, the empty string for a book not in the list). At the Reading List, ReadingListOptionsBar shows the options, the Sort menu's one item is ReadingListWording.orderName, checked, the window is titled "Library: Reading List", and an empty list shows ReadingListWording.emptyList as a row. Speak Info says a book's place in the list in every view, the brief summary and the full alike (BookInfoFacts.readingListPlace, a ReadingListPlace, which LibraryInfoWording.briefParts(of:) says through readingListNote(_:) after the place note, "In reading list, 3 of 12"). LibraryOrderCommandsSupport (Views/Library/LibraryView.swift) takes the Library menu's Move Book Up and Down and Add to and Remove from Reading List, which post addToReadingList and removeFromReadingList, for the Library window that takes the command (WindowCommandRouting); ShortcutAction.addToReadingList and .removeFromReadingList are in the Library group, with no default keys. readingListNeighbor(of:direction:skippingFinished:) and readingListContinuation(after:) answer what a reader of a book from the list asks (reading from the reading list, under the reader, below). A book counts as finished by LibraryViewModel.finishedBookIDs, what Books Finished records (ReadingStats.finishedBookIDs), which tests replace: a deliberate record, unlike a position near the end (P07), kept when the book is read again.
  - Files: Models/ReadingList.swift, Models/ReadingListCommand.swift, Models/ReadingListWording.swift, Models/Library.swift, Models/LibrarySortState.swift, Models/ImportDecision.swift, Models/LibraryInfoWording.swift, ViewModels/LibraryViewModel+ReadingList.swift, ViewModels/LibraryViewModel+SortAndOrder.swift, ViewModels/LibraryViewModel+Import.swift, ViewModels/LibraryViewModel+Duplicates.swift, ViewModels/LibraryViewModel.swift, ViewModels/LibraryListCache.swift, Views/Library/ReadingListOptionsBar.swift, Views/Library/LibraryView.swift, Views/Library/LibrarySubviews.swift, Views/Library/LibraryInfoRow.swift, Views/ContentView.swift, App/MenuCommands.swift, Models/KeyboardShortcut.swift.
- Feed items (FR11): the episodes and articles a feed downloaded, their packages, and each feed's own index.
