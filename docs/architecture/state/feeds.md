# Feeds

Part of [TextMouth's architecture](../../../ARCHITECTURE.md).

- Feed records (FR03): each subscription and the episodes and articles it keeps.
  - Owner: FeedStore, on the main actor, inside FeedCenter.shared. Each subscription's record (FeedRecord, in format FeedRecord.currentFormatVersion, 1) holds the Feed (its address, title, folder by ID, the newest item date, after which an item is new, whether it uses plain http, its size as its last read found it, its own List and download choice and delete-after override, the date the listener unsubscribed, nil while subscribed (Feed.unsubscribedDate, written only once set, read through Feed.isSubscribed; FR11's branch D), and, until the move to the choice clears it, a retired kept-entries number) and its items, newest first (FeedItem, each with its download's state, who asked for its download last, when it played, when its download was deleted, and when the item was deleted). An item's state may be inLibrary(bookID:), once Move to Library… made its download a book of the library's own: FeedItemState.libraryBookID reads it, linkedBookID either kind, and bookID stays a download's alone. An item In Library is always listed, never new, not counted as a download, and counted among the newest N. The size, Feed.entryTotal, a FeedEntryTotal, counts the entries the feed lists, each once, the ones the listener deleted among them, and says whether the feed lists more than the parser reads (listsMore, past FeedParser.maximumItems, 2,000); it is optional, so a record written before October 7, 2026 loads without it. It is one file in the data directory's Feeds folder, Feeds/<feed ID>.json (FeedPaths), pretty-printed with sorted keys and ISO 8601 dates. The file's name decides the feed's ID, so a sync service's conflict copy is never read. Beside it, Feeds/<feed ID>/ holds the feed's downloaded items' packages and its own index of them, which the library model owns (feed items, under the library index, above), and, hidden, a kept package set aside while a download replaces it (.replaced- and the package's name) and, in a library in the cloud, the notes of launches that found the record missing (.record-absent- followed by a Mac's ID and a launch's, FeedRecordAbsence).
  - Who may write it: FeedCenter's operations (subscribing, unsubscribing and resubscribing, a feed's folder and its own settings, marking an item played or unplayed, or every item played, deleting a download or an item, and deleting the feed, below), FeedReconciler's merges of a refresh, each of which records the feed's size before the kept-entries rule, whose number is now the feed's listing (the List and download choice, below), chooses the items kept, keeping beside the newest every item downloaded or downloading, every item played (board #1412), and every item whose row the library keeps after its file went (FeedReconciler.kept, keepingRecordsOf:, FR11's branch A2), the download manager, the lifecycle (played downloads, below), the newest-N rule and the move to the List and download choice (below), and Move to Library…, which marks an item In Library (feed items, under the library index, above). Each durable change is written atomically on the store's serial queue, as storage work (StorageWork.savingFeeds), so a data-directory move waits for it; a download's progress is never written, an item downloading or waiting to being written as not downloaded (FeedRecord.durable). While the data directory is unavailable, or after a write fails (FEED_RECORD_SAVE_FAILED), the change waits in memory, written with the feed's next change or once the data directory is back. A failed write is reported to PersistenceFailureCenter under feed subscriptions (feedRecords, keyed by the feed), naming the feed, so the banner offers Retry, which writes the record as it is now on the write queue, after every write asked for before, and waits for it (retryWrite(of:failureID:)), and quitting asks first; the feed's next write that succeeds settles it, and removing the feed's record withdraws it (FeedStore.remove(_:), which Delete Feed… calls). The engine's environment names the center (FeedEnvironment.failureCenter), so tests use one of their own. Delete Feed… (FeedCenter.deleteFeed(_:), Services/Feeds/FeedCenter+DeleteFeed.swift, FR14) is the one command that deletes a feed, subscribed or not, in an order whose every stopping point is safe. It refuses while one of the feed's downloads is in use, open in a reader, being transcribed, or being exported (FeedLibraryHost.feedBookUse(of:); FeedDeleteError.downloadInUse(title:use:), FEED_DELETE_REFUSED). Then it closes the feed's downloads (FeedDownloadManager.closeFeed(_:), below) and waits for the imports and rule removals already on the import queue (runBesideImports); removes the feed's downloads and the packages it kept for removed downloads as Delete Episode removes one, the Trash or for good as the removal setting says, every row of the feed (LibraryViewModel.everyRow(ofFeed:), ViewModels/LibraryViewModel+DeleteFeed.swift) leaving the library and its reading list and the indexes written before any file goes (FeedLibraryHost.removeFeedFiles(of:keepingPackages:remove:)), so a failed write deletes nothing (FeedDeleteError.indexNotWritten, FEED_DELETE_PUT_OFF) and a package that can't go keeps the feed with what stayed (filesStayed, FEED_DELETE_STOPPED); forgets the feed's index for good (forgetFeedIndex(of:)), so no save makes its folder anew, and removes Feeds/<feed ID>/ (FEED_DELETE_FOLDER_LEFT when it can't, for the next launch, which finds the folder without its record and, since it holds no package, deletes it, returning nothing); removes the record and this Mac's fetch details last (FeedStore.remove(_:), FeedFetchStates.remove(_:)), since a launch that found the folder with its record gone would return the downloads as books; and removes the feed's library folder only when nothing else is in it, no book of the library's own, folder, or other feed's items (removeFolderOfDeletedFeed(_:), FEED_DELETE_FOLDER_KEPT when it can't). It returns a FeedDeleteOutcome, the downloads and kept packages deleted and the folder's fate (FeedFolderFate), and writes FEED_DELETED. A book without the feed's link, as an item moved into the library, stays.
  - How others observe it: FeedCenter republishes every change of the records and the fetch details, publishes the feeds refreshing (refreshingFeedIDs), and sends FeedEvent values (a subscription, a refresh's end, the end of a refresh of every feed, a download's start, end, failure, or cancelling (downloadCancelled(feedID:itemID:)), and a change of the List and download choice taking effect, itemPolicyApplied(global:feedIDs:)), which the interface reads (below). A record that can't be read is preserved beside itself (SavedFile.preserveUnusable, FEED_RECORD_UNREADABLE) and its feed left out; one only in the cloud is asked of the sync service and read at the next refresh of every feed (FEED_RECORD_IN_CLOUD).
  - Files: Models/Feed.swift, Models/FeedItem.swift, Services/Feeds/FeedStore.swift, Services/Feeds/FeedReconciler.swift, Services/Feeds/FeedCenter.swift, Services/Feeds/FeedCenter+DeleteFeed.swift, ViewModels/LibraryViewModel+Feeds.swift, ViewModels/LibraryViewModel+DeleteFeed.swift.
- This Mac's fetch details.
  - Owner: FeedFetchStates, on the main actor: for each feed, the ETag and Last-Modified date a refresh sends back, the SHA-256 digest of the body last read, the number of entries kept when it was merged, the last check and the last success, the last failure's sentence, and whether the server said the feed is gone. One file per feed in this Mac's Caches folder (MachineLocalPaths.feedCaches, Fetch State/<feed ID>.json), written on a serial queue of its own and never synced, since a refresh changes them every time. A file that can't be read counts as missing, and macOS emptying Caches only means each feed is read whole once. It also notes the updatedDate of the record after the merge of the last body read (recordUpdatedDateOfLastBody, decoded leniently, so an older file still reads), and FeedRefresher.fetchAndRead counts the last body, by its digest or a 304, as merged only while the loaded record has that date, to the whole second (lastBodyIsMerged(into:)); otherwise it reads the feed whole and merges again, so a merge whose write was lost, when TextMouth quit or the data directory was unavailable, never hides its new episodes behind an unchanged check. A merge that changed no item keeps the record's date.
  - Who may write it: the refresher after each check, and subscribing. Unsubscribe keeps them, for Resubscribe's check (FR11's branch D); Delete Feed… removes them with the feed's record (FeedFetchStates.remove(_:), FR14).
  - How others observe it: the refresher's conditional requests, and FeedCenter.fetchState(of:).
  - Files: Services/Feeds/FeedFetchState.swift.
- A refresh.
  - Owner: FeedRefresher, inside FeedCenter.shared, which fetches through FeedNetwork: two ephemeral URLSessions, one for feeds and web pages and one for downloads, which cache nothing on disk, keep no cookies, and send TextMouth's own User-Agent. They are the app's only network connections, a search of the podcast directory going through them too, and App Transport Security allows arbitrary loads (Info.plist), since many feeds and episode hosts still use plain http; a feed that uses http is flagged (Feed.usesInsecureTransport).
  - Who may write it: FeedCenter: at launch when feedRefreshAtLaunch is on, every feedRefreshIntervalHours hours while TextMouth runs (never while that is 0, and a turn that falls in Low Power Mode is skipped), and when the listener asks (refresh(_:) and refreshAll(origin:)). The refreshes TextMouth makes by itself never use an expensive or constrained network, and skip a feed the server called gone (FeedRefreshOrigin.isDiscretionary). At most four feeds refresh at once, and one feed's refreshes never overlap. A feed the listener unsubscribed from is never refreshed (FR11's branch D; FeedRefresher.isChecked(_:)): refreshAll(origin:) passes over it, with no report, refresh(_:origin:) returns nil before fetching, and a fetch under way as the listener unsubscribed changes nothing once it ends; Check Feed chosen from a menu drawn before says so (FeedWording.notChecked(title:)).
  - How others observe it: a fetch sends the last ETag and Last-Modified date, and a 304, or a body whose digest matches the last, is unchanged, the feed's size kept as it was, unless the number of entries kept has changed since, or the record does not know its feed's size (Feed.entryTotal nil), when FeedRefresher.fetchAndRead sends no validators and reads the feed whole once. FeedParser reads RSS 0.9x and 2.0, RSS 1.0, and Atom, with Apple's podcast elements and Podcasting 2.0's, up to 25 MB and 2,000 items, with XMLParser, and reads a document that isn't well-formed again through XMLDocument's tidy mode (FEED_PARSE_REPAIRED). A document whose first character is "{" is JSON Feed, 1.1 or 1.0, which JSONFeedParser reads, through FeedJSON, into the same ParsedFeed (format json), so it is merged, listed, and downloaded as any other; JSON that names no JSON Feed version is no feed. The readers share the rules for choosing an enclosure (FeedEnclosure.preferred(among:otherwise:)), an untitled item's stand-in title (ParsedItem.standInTitle(from:isHTML:)), and dropping content that only repeats the summary (ParsedItem.isRepeating(_:_:)). FeedDiscovery takes a page's application/feed+json alternate too, never plain application/json. The fetch, the parse, and a first merge (FeedReconciler) run off the main actor; a second merge on the main actor folds the result into the record as it is by then, so what the listener did meanwhile is kept. A feed that moved for good, by a permanent redirect or itunes:new-feed-url, is fetched from its new address from then on (FEED_MOVED). Each refresh ends in a FeedRefreshReport, and a refresh of every feed in a FeedRefreshSummary, which FeedCenter sends as events; each refresh's end (refreshEnded) then asks for a sweep of played downloads and a pass of the newest-N rule over its feed, which downloads what the feed's List and download choice keeps downloaded (below). The transfers and fetches wait on a FeedOnceContinuation (Services/Feeds/FeedNetwork.swift), resumed once only, by whichever comes first, the task's end or its cancel, since a CheckedContinuation resumed twice traps; a transfer or fetch cancelled before it begins throws its cancelled failure before any URLSession task exists (even offline), and one cancelled between the check and the delegate is caught by URLSessionTask.resumeUnlessCancelled(otherwise:), so a cancel in the turn a download starts never leaves FeedDownloadManager.run waiting for good.
  - Files: Services/Feeds/FeedRefresher.swift, Services/Feeds/FeedNetwork.swift, Services/Feeds/FeedParser.swift, Services/Feeds/FeedDates.swift, Services/Feeds/FeedReconciler.swift, Services/Feeds/FeedDiscovery.swift, Services/Feeds/JSONFeedParser.swift, Services/Feeds/FeedJSON.swift, Resources/Info.plist.
- Downloads.
  - Owner: FeedDownloadManager, inside FeedCenter.shared, which downloads items one at a time, in the order asked, an item the listener opens, or a reader waits to go on to, coming first (download(_:of:origin:opening:startingNext:), which FeedCenter.download(_:of:startingNext:) calls for the reader's wait, opening nothing), though never ahead of the download under way. An item asked for again while it waits keeps its place in the queue, unless the new ask opens it or starts it next, so a listener who asks at every Play does not send it to the back.
  - Who may write it: FeedCenter's download, open, and cancelDownload, and the newest-N rule (the List and download choice, below), whose discretionary downloads never use a network with data limits. A download records who asked for it as it finishes, or fails (FeedItem.downloadOrigin): the listener whenever the listener asked for it at any point, or made the item theirs meanwhile, otherwise the rule (FeedDownloadOrigin.after(_:given:), which never overwrites the listener's). A download stopped as its file arrives, by Cancel Download or the downloads section's Cancel, stops before its import (Task.checkCancellation() in downloadEpisode; feed review item 15), as an article stops before its book is written; Cancel Download makes its item the listener's, while the section's Cancel leaves each item whoever's it was (FR14). Each of those cancels, and the one Delete Feed… makes, sends FeedEvent.downloadCancelled(feedID:itemID:) once its item reads not downloaded (announceCancelled(_:)): at once for a request taken out of the queue (FeedDownloadManager.cancel(_:of:), which cancelDownload calls, cancelEveryDownload(), closeFeed(_:)), and for the download under way where its task ends (run(_:)), never for the rule's put-off requests, a download stopped for quitting, or one that fails or finishes. The reader waiting for the next episode hears it (see [The reader](reader.md)). Delete Feed… closes the feed's downloads first (closeFeed(_:), closedFeedIDs): the one under way stops, those waiting to start and those put off go, every resume data file of the feed goes with the partial file it names, download(_:of:origin:opening:startingNext:) asks for none of its items, commit(_:for:restoredKeptPackage:) discards the package of an import that ends meanwhile, and a restored kept package (FeedEpisodeImporter.restoresKeptPackage(_:)), through discardPackage(of:asTheListenersDeletion:because:) as Removal Behavior says, closeFeed(_:) marks the items it drops not downloaded (markNotDownloaded(_:of:), shared with cancelEveryDownload() and withdrawRuleDownloads), and the sweep of played downloads and the newest-N rule leave the feed alone, until reopenFeed(_:), once the feed is deleted or left as it was. FeedPartialDownloads (Services/Feeds/FeedDownloadManager+PartialDownloads.swift, FR14) removes resume data only together with the partial file it names, which the system keeps in the process's temporary folder: it reads every string of the resume data's property list, without decoding the system's undocumented layout, and removes only a plain file directly in that folder named as the system names a partial file, CFNetworkDownload_ and letters and digits then .tmp. Cancel Download, a transfer stopped for good, the launch's sweep of week-old resume data, the section's Cancel, and Delete Feed… all remove resume data through it.
  - How others observe it: an episode's file comes through a URLSessionDownloadTask, whose bytes go to the downloads' progress alone (the feed downloads' progress, below), never to its item's state or its record. A download that stops partway keeps its resume data in this Mac's Caches folder (Resume Data, a week), and the finished file waits in Feed Downloads until FeedEpisodeImporter imports it, as storage work, through the import pipeline (ImportStaging and FileImportService.publishReadableBook), publishing the package in the feed's own folder, Feeds/<feed ID>/ (destinationPackageURL), and adding the book's row, with its feed link and no library folder, to the library on the main actor before that work ends (addFeedBook(_:); feed items, under the library index, above). A download needs the feed's library folder all the same, which lists it: a feed whose folder is gone downloads nothing. An episode, audio or video, becomes an audiobook, a video one playing its sound, and an article an HTML book written from its text, or from its web page's article when its own text runs under 200 words and it links a page. The book's row and record name its feed and item (Book.feedLink and BookMetadata.feedLink, a FeedBookLink), which its feed's index holds and library.json never does, and every later save of the record keeps the link (Book.bookInfo(replacing:contentIndex:revisionFloor:)); writeVerifiedRecord checks it on read-back. Whatever an interrupted download left in Feed Downloads is swept away at the next launch. A rule download that a network with data limits refused waits (FeedItemState.waiting, FeedDownloadWait.network, with one FEED_DOWNLOAD_WAITING line) and is put off (putOff); the next refresh TextMouth makes by itself that wasn't skipped, which shows the network has no data limits now, asks for the downloads put off again (retryPutOffDownloads, from FeedCenter's refreshEnded). One that lacks room waits too (FeedDownloadWait.room), for the rule's next pass, which never removes anything to make room; a download the listener asked for still fails for want of room. As TextMouth quits, once the unsaved-changes guard lets it, the downloads are one piece of the quit's work (FeedQuitHold.work, kind "feed downloads"; the quit is in [Launch](../launch.md)), which ends when FeedDownloadManager.stopForQuit() ends or after three seconds (longestWait), whichever comes first: stopForQuit stops every download (isStoppedForQuit), lists each one asked for, the one under way first and those put off last, in this Mac's resume folder (Downloads at Quit.json, as SavedDownload, each with who asked for it), and then stops the transfer under way, keeping its resume data when its server allows (FeedTransferHandle, through cancelByProducingResumeData). The next launch asks for them again (resumeDownloadsSavedAtQuit, after sweepLeftovers), only where the engine works on its own.
    - A quit the person asks for (0.4.4) is cancelled while the downloads keep their place, says so, and is asked again, instead of being left pending.
      - TextMouth says "TextMouth is finishing up before it quits: keeping the place of your feed downloads for next time. It will quit as soon as that is done." in a panel and through VoiceOver (QuitFinisher, QuitNotice).
      - A second Command-Q or the Dock's Quit during those three seconds is cancelled too and says the same words again, so it no longer quits at once with the list of downloads half written.
      - Only the system ending the session (log out, restart, shut down) is still answered .terminateLater by FeedQuitHold.hold, since cancelling it would stop the log out.
    - Downloads stopped for a quit that is then cancelled stay stopped (0.4.4). The work ends before the quit's last pass through the questions of step 0 and the unsaved-changes guard, so a Cancel there (a failed write during the wait, or a library move, a take, or an editor's edits that began meanwhile) leaves TextMouth open with isStoppedForQuit true for the rest of the session. Each download is listed for the next launch, which asks for it again. Nothing resumes them in the meantime, and FeedQuitHold's comment says so.

- Played downloads, and their deletion.
  - Owner: each item's playedDate and downloadDeletedDate, in its feed's record.
  - Who may write it: ReadingStatsService.markBookFinished posts bookDidFinish, and FeedCenter marks the item whose download finished played (FEED_ITEM_PLAYED), so a finished episode or article counts among Books Finished too; markPlayed(_:of:) and markUnplayed(_:of:) set or clear it for the listener, and markAllPlayed(of:) sets it for every item of a feed not played yet, in one change of its record. A sweep (requestSweep(), at launch, after each refresh, when an item plays to its end or is marked played, and whenever the books open in readers change, as when a reader closes) deletes the file of each download played at least feedDeleteDownloadsDaysAfterPlayed days ago, or the feed's own number (0 at once, -1 never), for good, with dataless files left in the cloud, keeping its package, with an article's content.md in it (FeedItemPackage.staysWithoutTheFile(_:)), while it holds the listener's state, in the order the feed items entry gives (feed items, under the library index, above): never a book in use, which the sweep leaves for its next pass (FeedLibraryHost.feedBooksInUse: one open in a reader, one an export is reading, BookExportModel.booksBeingExported, the one being transcribed, TranscribedBooks.shared.transcribingBookID, and a book whose text is being edited with Edit Text, LibraryViewModel.textEditSessions.bookIDs, which the rules wait for but the listener's own deletions do not, since an editing session ends only when TextMouth quits and a refusal would stand until then; FeedDueRemovalOutcome.inUse and the reports' inUseBookIDs; REV11 F1), never while the library's index is being recovered, never a download made before FR11 that has not moved into its feed's folder, and, in a library in the cloud, only a package this Mac holds whole, as the packages' cloud states, read off the main thread first, say (packagesHeldWhole, FEED_SWEEP_LEFT_IN_CLOUD). The removal goes through removeDue(_:from:by:at:putOffEvent:), which the newest-N rule shares (the List and download choice, below): the records and the feeds' indexes are written and waited for on the main actor (LibraryViewModel.readyFeedFilesForRemoval(of:keepingPackages:)), the files are removed off the main thread, on the download manager's import queue (FeedDownloadManager.runBesideImports(_:)), inside StorageBoundary.perform as StorageWork.removingFeedDownloads, so a data-directory move waits for a removal under way and a removal waits while a move holds the work (it logs FEED_DOWNLOAD_DELETE_WAITING while held), reading TextMouthPaths.root only after any wait so it removes from the data directory as the move left it, and the outcome is settled on the main actor (settleFeedFileRemovals(_:failures:)).   - Who may write it: search(), from the Search button or Return in the Search field, through FeedCenter.searchDirectory(for:) and the directory the engine's environment names (FeedEnvironment.directory: FeedDirectory.apple, Apple's iTunes Search API, or a test's stub server). FeedDirectory asks for podcasts alone, at most 50 (media=podcast, entity=podcast, limit=50), with the term percent-encoded beyond the unreserved characters, through the feed engine's connections, as a request the listener made, on any network, and reads the answer through FeedJSON (results(in:)), keeping each podcast that names a web feed once (FeedAddress.comparisonKey). A failure is a FeedSearchError, worded by FeedFetchError.searchMessage, as when the directory refuses more than about 20 searches a minute. subscribe(to:) puts a result's feed in the address field and subscribes as Subscribe does.
  - How others observe it: AddFeedSheet lists the results, each read as one line beside a Subscribe button of its own, and VoiceOver hears how many were found, or why none were (FeedWording).
  - Files: Services/Feeds/FeedDirectory.swift, Services/Feeds/FeedJSON.swift, Services/Feeds/FeedCenter.swift, Views/Feeds/AddFeedSheet.swift, Views/Feeds/FeedWording.swift.
- New items arriving: the alert and the notifications (FR03).
  - Owner: FeedArrivals.shared, on the main actor: the alert waiting to be shown (pendingAlert, a FeedArrivalAlert), and the Library window showing it (alertWindow).
  - Who may write it: FeedArrivals itself, from FeedCenter.events. A refresh of every feed that TextMouth made by itself (FeedRefreshOrigin.isDiscretionary: at launch or on the interval) and that brought new items makes the alert, while feedRefreshAlert is on, and posts a notification for each feed through its FeedNotifying, while feedNotifications is on and notifications are allowed. A refresh the listener asked for is answered where it was asked, by VoiceOver (FeedWording.refreshedAll and FeedWording.checked). Turning notifications on asks permission the first time (FeedArrivals.settingTurnedOn). FeedArrivals also speaks FeedEvent.itemPolicyApplied(global:feedIDs:), which FeedCenter.itemPolicyChanged(for:) sends as its ten-second wait ends, after a change in Settings, Feed Info, or config.json: FeedWording.itemPolicyApplied(global:feedIDs:in:) gives the global setting's sentence when it changed, then one for each feed whose own changed within that wait that the library still holds, an unsubscribed one included, since its rules still act (feed review item 20; FeedCenter keeps globalItemPolicyChanged apart from the feeds changed, so neither hides the other); its announce is injectable, for the tests.
  - How others observe it: the first Library window in front to ask takes the alert (claimAlert(by:isKeyWindow:)), so it shows once, and waits while no Library window is in front; dismissing it forgets it. SystemFeedNotifier posts through the system's notification center, whose delegate (FeedNotificationPresenter) shows banners while TextMouth is in front too; a process hosting tests uses InertFeedNotifier, which posts nothing and never asks.
  - Files: Views/Feeds/FeedArrivals.swift, Views/Feeds/LibraryFeedsWindowSupport.swift, Views/Feeds/FeedSettingsView.swift, Views/Feeds/FeedItemPolicyControls.swift.
- A podcast episode's own transcript and chapters (FMT25; 0.4.2).
  - Owner: FeedEpisodeExtras (Services/Feeds/FeedEpisodeExtras.swift) fetches, once an episode's audio has downloaded and for every feed, the files its item links as Podcasting 2.0's podcast:transcript and podcast:chapters (FeedItem.transcripts and FeedItem.chapters).
  - Who may write it: the download. It tries at most three transcript links (maximumTranscriptTries), in the order WebVTT, JSON, SubRip, by the link's MIME type and then its address's extension; HTML and plain text are never fetched. Files are fetched under the download's own network rules (FeedNetwork.fetch): no cookie, redirects to http and https only, no link inside a file followed, and a body cap of 5 MB for a transcript and 1 MB for chapters (TimedTextLimits). The whole fetch stops after FeedNetwork.feedResourceTimeout, 2 minutes (timeLimit). FeedEpisodeImporter puts the chapters into the staged package as podcastChapters.json (TextMouthPaths.podcastChaptersFileName, titles cut to 200 characters), where they become the episode's headings when its audio has none; attach(_:to:) makes the transcript the episode's once its book is listed, with Origin podcast.
  - A podcast's own transcript does not keep an aged-out download's package (2a398017). When an episode downloads again, TranscriptInstallation replaces an untouched podcast transcript (givingWayToAnUntouchedPodcastTranscript); a transcript recognition made, or that the listener edited or cleaned up, is kept. This is one commit that can be dropped on its own (fda87492, with 42daa613).
  - How others observe it: the debug log has one line for a file left out, naming the episode, its feed, the server by its host alone, and why, never a word of the file. Nothing here can fail the episode's download.
  - Not done: a switch for each feed, HTML and text transcripts, and the audio's checksum stamped in the kept chapters file, so that a later re-analysis can't reuse chapters a failed removal left. A quit during the fetch downloads the episode again at the next launch.
  - Files: Services/Feeds/FeedEpisodeExtras.swift, Services/Feeds/FeedEpisodeImporter.swift.
