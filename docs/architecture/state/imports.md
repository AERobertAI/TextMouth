# Imports

Part of [TextMouth's architecture](../../../ARCHITECTURE.md).

- An import in progress.
  - Owner: LibraryViewModel's SerialImportQueue, which runs one import at a time off the main thread, each as storage work that a data-directory move waits for or holds back (StorageBoundary.perform), and reports activity on the main queue, and ImportCancellation, which the queued imports share and the progress overlay's Cancel button sets.
  - Who may write it: FileImportService does the work. Open Book offers the types it reads (FileImportService.supportedTypes), video among them, since an audiobook may be an MPEG-4, M4V, or QuickTime file whose sound alone plays (BookFormat.audio's mp4, m4v, and mov; public.mpeg-4, com.apple.m4v-video, and com.apple.quicktime-movie), so a video episode's package imports again too, as does the audio the import converts (BookFormat.audio's ogg, oga, and opus, with org.xiph.ogg-audio, also declared in Info.plist, and ImportAudioConverter.coreAudioExtensions, which the list ends with, each offered by its system type where it has one) and an M3U playlist (public.m3u-playlist); ArchiveEntryLimits.audioExtensions is the same list; a feed still tells a video enclosure from audio for itself (FeedMediaKind, whose audioExtensions leave video's out). It identifies the source, builds the package under a hidden staging name (ImportStaging, .import- followed by a UUID and .tmb), in this Mac's Import Staging folder while the data directory is on its volume and beside the package's destination otherwise (ImportScratchSpace), copies the content, reads the book as the reader will, writes bookInfo.json and reads it back, and only then publishes the package with one rename. A TextMouth package is staged as every import is (REV13): ImportStaging.makeEmpty makes the staged package, then the .copying step copies the source package's items into it (copyContents(of:)), so the import overlay names the copy, and a package whose own folder is read-only imports, since the staged folder is TextMouth's own. A failure removes whatever was staged and throws an ImportFailure naming the file and the step, and the original file is never touched after a failure. A ZIP is inspected and extracted within an ArchiveBudget into an Archive Extraction folder on the same condition, this Mac's or the data directory's (ArchiveExtraction), and every format reader takes entries out of archives through ArchiveEntryReader, which holds each entry to its limits. A reader that looks up more than a member or two, as the EPUB, Word, and DAISY readers do, finds them in an IndexedArchive, the archive's entries read into an index by path once, since ZIPFoundation finds each by reading the archive's central directory from its start; the index answers exactly as the archive would, the first entry at a path winning. IndexedArchive.file(at:) finds the entry at exactly a path, else the first file entry whose path matches it without regard to case (ST09; Archive.file(at:) is the same rule for an archive not indexed), which the EPUB reader's lookups and the DAISY reader's use, since a badly made book may name a member in another case than its ZIP spells it; the exact spelling always wins. DAISY audio conversion copies each audio file through DAISYFileProvider.copyFile(at:to:): out of a ZIP a megabyte at a time (ArchiveEntryReader.stream), never whole, and from a folder as a clone. A ZIP batch reads each book's checksum once, for its duplicate check, and hands it to the book's import (importFileWithReport(from:checksum:toFolder:observer:)).
  - How others observe it: LibraryViewModel adds the published book to the library, unless the library already holds a copy, and the overlay shows how far the import has got (import progress, below); every question an import raises waits its turn in one queue (import questions, below).
  - The manifest's check (FR15): an archive whose manifest.json is found (AudioManifestLocation.find(in:)) is checked in a step of its own, Reading its manifest (ImportStep.readingManifest), after extraction and before the book is read. AudioManifestCheck.checkedManifest(at:audioFolder:) stops at the first problem, in the order a person fixes them, with an AudioManifestProblem whose sentence begins "manifest.json". Only the import checks; every later read is lenient (AudioManifest.read(inAudioFolder:)).
  - Files: Services/FileImportService.swift, Services/FileImportService+Packages.swift, Services/ImportStaging.swift, Services/ImportScratchSpace.swift, Services/ImportFailure.swift, Services/ArchiveBudget.swift, Services/ArchiveExtraction.swift, Parsers/ArchiveEntryReader.swift, Parsers/DAISYParser.swift, ViewModels/LibraryViewModel+Import.swift, ViewModels/LibraryViewModel+Duplicates.swift, Parsers/AudioManifest.swift, Parsers/AudioManifestCheck.swift.
- Import progress (FR10): what the import overlay shows, and what VoiceOver hears of an import.
  - Owner: LibraryViewModel.importProgress, an ImportProgress (ViewModels/ImportProgress.swift) on the main actor, whose state is an ImportProgressState: a notice, the books done of the total, the book under way (its name, its number in a batch, its ImportStep, when it began, and, for an archive holding one audiobook, how far its extraction has got, BookUnderWay.extraction, which its line says while it extracts), what the books done took (timing, a WorkTiming), the sizes the batch's books are timed by (bookSizes), the time left, whether Cancel was pressed, and the imports waiting behind the one shown (waitingImports), which a new import's state keeps. The duplicates a batch skipped are counted once, in its ZipImportResult (skippedDuplicates). Whether the overlay shows at all is still the model's isImporting.
  - Who may write it: the imports, on the main queue. ArchiveExtractor reports an archive's extraction as an ArchiveExtractionProgress, its entries and the bytes they declare, both totals from the archive's central directory, which the budget reads anyway: at the start, and whenever the whole percentage of either changes, between the chunks of a large entry as well as between entries. A ZIP batch reports ZipImportProgress.extracting, then .importingBook as each book begins and as each step of it begins (through the importer's ImportStepObserver), and .importing(done:total:skippedDuplicate:) as each book is imported, fails, or is skipped as a duplicate; a batch also reports .foundBooks(sizes:) once, before its first book, each size from FileImportService.timedSize(of:): a text book's file size (an EPUB, PDF, Word document, rich text, Word 97-2003, OpenDocument, Word 2003 XML, web archive, SSML, or plain text, Markdown, or HTML file), and nil for an audiobook's file, whose import reads its chapters rather than its every byte, for a DAISY book, a DTBook on its own included, and for an RTFD, which is a folder. A single file, or an archive holding one book, reports through ImportProgress.observeBook(_:startingAt:then:), which tells the overlay of each step before the queue's test hook, and so do a TextMouth package opened from the Finder (openTMBPackage(from:), from .checkingPackage), New from Text (createBookFromText, from .preparingPackage, by its title), and a recording's save (LibraryViewModel.saveRecording, from .preparingPackage, by its title, REV13), whose line is cleared (clear()) rather than ended, so it announces nothing, since the New Recording window says how the save ended; an archive holding one audiobook reports its extraction through observeExtraction(). TimeLeftEstimate (Models/TimeLeftEstimate.swift, shared with the feed downloads' progress) gives the time left from the WorkTiming of the books imported or failed, duplicates not timed: each book still to come of known size takes its bytes at the rate the sized books took theirs, and any other the average time of the books timed without a size, or of every book timed before any of those, less the time it has run; TimeLeftEstimate.rounded(_:) rounds it to the minute under 10 minutes, to 5 minutes under an hour, and to 15 beyond. The library follows the import queue's count of imports queued or running (importActivityChanged(to:), which observeImportActivity() starts, and which assigns isImporting only when it changes, so the library model publishes as imports start and end and not with each import queued or done, REV13), and the progress counts those behind the one shown as waiting (noteImportsQueued(_:)). Cancel calls cancel(), and end(_:) ends the import shown.
  - How others observe it: only ProgressObserver, a generic view in Views/ContentView.swift, observes it, as it observes the text cache's progress (PERF12, #1461), drawing the overlay in a TimelineView that ticks every 5 seconds from the book's start, so the time on a book keeps up between reports while the library model is never republished. ProgressOverlay takes detail lines and a spoken summary from its caller; the text cache overlay keeps its own. ImportProgressWording words every line, the overlay's VoiceOver label, the announcements, and Speak Import Progress, the imports waiting included (waiting(_:), "2 more imports waiting", left out once Cancel is pressed, since queued ZIP archives never start). An import that has run 10 seconds (ImportProgress.announcedAfter) announces each quarter of a batch's books once, at medium priority, and its end, unless Cancel was pressed, when its alert says where it stopped; Cancel is announced at once. A batch that found no new book and in which nothing failed (ZipImportResult.foundNoNewBook) is not announced: LibraryViewModel.completeZIPImport raises the library's alert instead, which waits on screen and which VoiceOver reads, since an announcement made while TextMouth has no window in front is never spoken (October 13, 2026). The alert is titled ImportProgressWording.nothingImportedTitle ("Nothing Imported", set in LibraryViewModel.errorTitle, which goes back to nil, "Error", whenever showError turns false) and says nothingImported(from:result:): the duplicates sentence, noNewBooks(in:alreadyInLibrary:), or, for an archive with no book, noBooksFound(in:holding:), which names what it held by kind from ZipImportResult.nonBookFiles, a NonBookFiles that FileImportService.importCandidates counts by extension for every file it passes over, those in archives inside included. A batch with failures or an incomplete book raises the alert under ImportProgressWording.zipAlertTitle(for:addedBooks:), set through presentImportMessage(_:title:), where addedBooks counts the books the library took (completeZIPImport's acceptedBooks, not result.books): nothingImportedTitle when the batch found no book, alreadyInLibraryTitle ("Already in Library") when it found books and the library took none, someFilesNotImportedTitle ("Some Files Not Imported") when books came in but a file failed or the batch was cancelled, and otherwise bookImportedTitle or, for more than one book, booksImportedTitle ("Books Imported"), so that title never reads "Error" over books that came in. Every batch also ends with one ZIP_IMPORT_FINISHED event line in the debug log (ZipImportResult.logLine(archiveName:)). The reading list's join after an import made at the Reading List is announced at medium priority (addImportedBooksToReadingList(_:request:)), after the import's own words rather than over them. ShortcutAction.speakImportProgress, under Information with no default key, and Library > Speak Import Progress post speakImportProgress, which the library model hears from any window (observeImportProgressRequests()) and answers through VoiceOver.
  - Files: ViewModels/ImportProgress.swift, Models/ImportProgressWording.swift, Models/TimeLeftEstimate.swift, Services/ArchiveExtraction.swift, Services/FileImportService.swift, ViewModels/LibraryViewModel+Import.swift, ViewModels/LibraryViewModel.swift, Views/ContentView.swift, Models/CountWording.swift, Models/KeyboardShortcut.swift, App/MenuCommands.swift.
- Import questions.
  - Owner: LibraryViewModel.importDecisions, an ImportDecisionQueue of the questions imports are waiting to ask (whether to replace or keep a duplicate, whether to delete an original file, whether to put a ZIP archive's books in a new folder, and whether to transcribe an audiobook just imported), asked one at a time in the order they arose. Each ImportDecision holds everything its answer acts on, captured when its import finished (a duplicate's new copy and the copy it matched, an original file, a ZIP archive's books and folder, or an audiobook's ID, title, and length), and the ImportRequest its import was made with: the Library window it started in (ImportOrigin), whether to open the book afterwards, and the cancellation its batch shares.
  - Who may write it: LibraryViewModel+Import and LibraryViewModel+Duplicates. ask(_:) queues a question behind those waiting, and a question an answer raises about the same file, such as whether to delete the original of a duplicate just kept, is asked next. An offer to transcribe (ImportDecision.Kind.transcriptionOffer, FR05) is queued after an import's own questions, for each audiobook it added, when TranscriptionOffers.offersTranscription(of:) allows it: an audiobook in a package of its own, Offer to transcribe after importing an audiobook on, and a Mac that can transcribe. Its Transcribe sends LibraryViewModel.acceptedTranscriptionOffers to the Library window that asked (LibraryTranscriptionSupport), which opens the Transcribe Audio sheet, starting at once when it can. answerImportDecision(_:with:) acts only on the question being asked, named by its ID, so a second press can never answer the next one; an answer that fails, such as a folder name the library refuses, keeps the question open with the reason. While the data directory moves (dataDirectoryMove is set), it refuses every answer with DataDirectoryMoveWording.importAnswerRefusal, shown in the sheet and spoken, and the question stays until the move ends, since a window asking one when a move begins keeps that sheet instead of the move's. cancelImports(), the progress overlay's Cancel, withdraws the questions of its batch, those waiting and those raised later: a duplicate's new copy is discarded, an original file is kept, a ZIP archive's books stay where they are, and an offer to transcribe is dropped.
  - How others observe it: each Library window's ImportDecisionPresenter watches the queue, and exactly one window asks the question at its front (ImportDecisionQueue.askingWindow): the window its import started in while that is open, or else the first open Library window, the question waiting while none is open. That window shows ImportDecisionSheet, whose words, the screen's and VoiceOver's alike, come from ImportDecisionWording, with a title that gives the question's place when there is more than one, as in "Duplicate Book Found, 2 of 5". The choice that removes nothing comes first; Return and Escape press the marked choices, and Replace Existing and deleting an original file are never on a key. A duplicate's question says what Replace Existing keeps (ST04): ImportDecisionWording.duplicateMessage adds, after the choice, replacingKeepsSentence(existing:new:), which chooses from both copies' kinds and never promises what DuplicateReplacement.carriedBook drops: replacingKeepsTextSentence or replacingKeepsAudioSentence for two copies of one kind, and replacingAcrossKindsSentence when one is an audiobook (BookFormat.isAudio) and the other is not, which says "played from its recording" and "read aloud from its text" rather than "not an audiobook", so that it is true of a DAISY book too. Then replacedCopySentence(movesToTrash:) follows the Trash setting (RemovalPreferences.movesToTrash): with the Trash on it says that the files go to the Trash but putting them back won't return that copy to the library, since the package's record names the book the new copy now is, which no launch adopts a second time (adoptOrphanedTMBPackages); with it off it is RemovalMode.deletePermanently's files clause. The choice's hint is ImportDecisionChoiceWording.replaceExisting(acrossKinds:), which across kinds promises only the folder and the place on the reading list. The words say what Replace Existing does (replacing a duplicate, below). A question that appears while the user is in another window waits without taking focus or being announced. A book whose import asked to open it, as one opened from Finder does, opens through LibraryViewModel.readerOpener once it is in the library and its questions are answered.
  - Files: Models/ImportDecision.swift, Models/ImportDecisionQueue.swift, ViewModels/TranscriptionOffers.swift, ViewModels/LibraryViewModel+Duplicates.swift, ViewModels/LibraryViewModel+Import.swift, ViewModels/DataDirectoryMoveProgress.swift, Views/Library/ImportDecisionPresenter.swift, Views/Library/ImportDecisionSheet.swift, Views/ContentView.swift.
- Unanswered duplicates (October 31, 2026): a duplicate's question lives only in memory, and the new copy's package is published before it is asked.
  - Owner: DuplicateQuestionMarker (Services/DuplicateReplacement.swift), the empty hidden file .awaitingDuplicateAnswer at the top of the new copy's package, written before the question is queued. Keep Both takes it off before the copy joins the library, and Replace Existing after the copy's record is written and before the index names it, and puts it back when the replacement is not committed; either keeps the question, saying why (DuplicateCopyWording.markerStays), when the marker cannot come off.
  - Who may write it: no walk of the library adopts a marked package: adoptOrphanedTMBPackages passes it over before reading its record and records it in an optional collector, UnansweredDuplicates, and one whose folder or marker is only in the cloud, where another Mac may still be asking, counts as a cloud skip instead. Only the launch repair gives the collector (LibraryViewModel.adoptOrphanedPackages), and discardUnanswered then moves each recorded package whose question this library is not asking to the Trash, whatever the Trash setting says, logging DUPLICATE_UNANSWERED, unless the marker is less than a day old (unansweredQuestionGrace, by the marker's modification date; a date that cannot be read counts as new), when another Mac may be asking and the copy stays. A rebuild, the provisional library, and a repair run again while a question waits discard nothing. A package imported with the marker still on it, as a copy that Cancel or the discard sent to the Trash and Open Book or Finder opens again, has it removed beside the removal marker.
  - How others observe it: one alert after the repair, DuplicateCopyWording.unansweredTrashedTitle, "Duplicate Copies Moved to the Trash", names the titles moved (up to three; more are counted), appended to an alert already showing. Keep Both and Replace Existing say why they cannot keep a copy through DuplicateCopyWording: libraryUnreachable(bookTitle:) while the data directory is unavailable, checked first, and copyGone(bookTitle:) when the package is gone, so the original is never deleted by then; a marker that stays is logged as DUPLICATE_KEEP_FAILED with the system's reason. Tests: ImportDecisionFlowTests.

- Replacing a duplicate (ST04): what Replace Existing does with the two copies of a duplicate's question. The new copy, which its import has already published in a package of its own, takes the place in the library of the copy the library holds, as that same book.
  - Owner: the library's row of the replaced copy, which the new copy takes over under the same ID. DuplicateReplacement (Services/DuplicateReplacement.swift) decides what the new copy keeps (carriedBook(replacing:with:places:location:)): the ID, so that what the app keeps by ID stays, such as the place on the reading list; the folder, the place in the folder's manual order, the date added, and when it was last opened and played; the metadata the user edited by hand (Book.HandEdits, keepHandEditedMetadata(of:)); and, for two books of one kind (areSameKind: both audiobooks, or both read from their text, a DAISY book among them, since BookFormat.isAudio tells them apart), the book's own settings (Book.hasOwnSettings, takeOwnSettings(of:): voice, speed, pitch, what happens at its end, and the units of its skips) and its places (carriedPlaces). A text book's places are moved from the old text to the new one by the words they were saved by where the two texts differ (PlaceRelocator.relocate(_:from:to:movedAt:)), but only from an old text that is the text they were saved in, the content.md TextMouth last wrote or took, whose digest the record keeps (holdsTextOfPlaces, as Edit Text moves places only then); from a save no edit took, or when the old text cannot be read, they are found in the new text by their words alone (PlaceRelocator.relocate(_:within:movedAt:)), and a place nothing finds stays as it was saved; PLACES_RELOCATED is logged when any moved. An audiobook's places count time in its recording (P08) and follow the new chapter list (movedAudioPlaces(_:from:to:at:)): the same list leaves them; a book of tracks, one track to a chapter with every old track among the new copy's, moves each place to its track at the same time into it, a skipped heading with it (TrackPlaces.moved); any other list moves each place through time on the recording (PlaceClock) to the new chapter that holds the time where its old chapter starts plus its offset's time, never held to that chapter's end, and its skipped headings wait, naming no heading, since another chapter list does not keep them. A copy of the other kind keeps only the ID, the place in the library, and the hand-edited metadata, since a text's places and speed mean nothing to a recording. Everything else is the new copy's: its file and text, what reading them measured, its title and author where the user edited neither, and where it came from. The new copy's package record keeps the import's own ID until the library commits the new row, so a stop before then never leaves two records naming one book.
  - Who may write it: LibraryViewModel.replaceExisting(with:of:), which answerImportDecision(_:with:) reaches for Replace Existing, on the main actor, in this order. It finds the library's copy that matches now (duplicateMatch(for:)), which an earlier answer may have changed since the question arose, and adds the new copy as Keep Both does (keep(_:of:)) when none matches. It refuses (replacementRefusal(of:), a DuplicateReplacement.Refusal) while another operation holds the library's storage work (StorageBoundary.shared.heldFor: .storageBusy, as a folder edit does while it moves packages off the main thread, when the replacement would carry nothing from a package moved meanwhile and write its record into the old package's new place); while the copy is open in a reader, being transcribed, or being exported, the uses a deletion of a feed's download refuses (.inUse, FeedBookUse.refusal(of:doing:retry:), whose clause names the action); while its audio is edited in the audio editor or saved from it (.audioBeingEdited, AudioEditActivity.isBeingEdited); while its text is being read again in another encoding (.readingAgain, which carries that re-read's own sentence, LibraryViewModel.readingAgainRefusal(of:), and is asked last, since a re-read ends by itself in a moment; Reading a book again in another encoding, in [Text caches](text-caches.md)); and when the old package or a file carried over is only in the cloud (.filesInCloud), which a replacement never downloads. It flushes the analyses of the old copy that wait in the buffer (analysisSummaries.flush()); one still on its way names the old package, which the new row's is not, so it never lands on the new row (applyAnalysisSummaries). DuplicateReplacement.prepare(replacing:with:) then reads everything carried over before it writes anything, and writes it into the new copy's package, which it moves into the old copy's folder: the copies Edit Text kept (TextMouthPaths.isKeptTextCopy); the old text, kept beside the new text as content.md.edited- (BookTextEditSessions.keepCopy(of:bytes:)) when the two differ and it holds text TextMouth did not write, an edit on record (Book.editedText) or a content.md whose digest is not the one written (DuplicateReplacement.holdsUnwrittenText(_:of:hasher:), which a re-read in another encoding asks too), or, for an audiobook, a save its transcript's layer does not account for or the text of an edited transcript that stays behind, with TextNotKept thrown when no copy can be made; the transcript, with the one kept before its cleanup; and the places. The transcript is kept only when the new copy's audio is proven to be the audio transcribed (fitted(_:to:index:sourceMatches:access:)), and nothing is hashed, since this runs on the main thread: a book of one file whose content hash (Book.md5Hash) is the digest the transcript recorded for its file, whatever its name (the transcript's file is then renamed to the new copy's); the same source imported again (the two copies' content hashes equal, an archive's own or a folder's), with every file the transcript names at the same path and of the same size, since extracting an archive gives every file a new date; or each file the same by path, size, and date (TranscriptTextLoader.audioCheck with no hasher). A file only in the cloud proves nothing, and a transcript of a later layout goes into the new package as it is. A failure while writing undoes what was written (Preparation.undo()), putting the package back as the import published it. commitReplacement(of:by:) then commits the new copy, each step on disk before the next: whatever waits to be written for the old copy goes into its own package (LibraryPersistenceService.writePendingBookInfoNow(bookID:)), then the new row's record under the kept ID (saveBookInfoThrowing()), then the library's index naming it (LibraryPersistenceService.saveAndWait(_:)); a failure of the last throws IndexNotSaved, and the caller undoes the preparation and writes the new copy's record under the import's own ID again. Only then does the library hold the new row, at the old row's place; the old row's queued writes are forgotten (LibraryPersistenceService.forgetDeletedBook) with the reading text this Mac kept for it (ReadingTextCache); the old copy's Edit Text session ends saying so (endEditingSessions(of:): BookTextEditor.endBecauseBookWasReplaced(_:title:), BookTextEditWording.stoppedBookReplaced) and its Edit Manifest session ends quietly; the transcript is noted (TranscribedBooks); and DUPLICATE_REPLACED is logged. removeReplacedPackage(of:) then removes the old package (DuplicateReplacement.removeReplacedPackage(of:movesToTrash:)): to the Trash in one move under its own name, or, with the Trash off, renamed first to a staged package's hidden name in its own folder (ImportStaging.freshName()) and deleted with everything in it (ImportStaging.removeStagedPackage(at:), which gives back the write permission a read-only item took away), since a deletion can stop partway and a half-deleted package under its own name would be a broken book; what cannot be deleted stays hidden, and the next import into that folder removes it (ImportStaging.removeAbandoned(in:)). The replacement stands whatever happens then: a package that cannot be removed stays in its folder, and the library's alert says so (DuplicateReplacement.oldCopyLeftMessage). When the old text was kept, VoiceOver says where, after the answer's own words (DuplicateReplacement.keptTextAnnouncement(title:copy:), whose second sentence is BookTextEditWording.earlierTextKept(_:), which a re-read in another encoding says too). The new row then finishes as a kept book does (finishKeeping(_:from:of:offeringTranscription:)): a book already on the reading list keeps its place there, and an audiobook is offered for transcription only when its transcript was not kept. A refusal, or a failure before the commit ("Could not replace duplicate" and the reason, or TextNotKept's or IndexNotSaved's sentence), is an OperationOutcome.failure: the question stays open and the library's copy is as it was.

  - The rich text reader (RTFDocumentReader, written from Microsoft's RTF 1.9.1 specification), in steps:
    1. html(of:as:includesPages:) picks the file: for an .rtfd that is a folder, the file named TXT.rtf (matched without regard to case; a link, or no such file, is TextutilConverter.Failure.unreadable(.rtfd)), and otherwise the file itself. DocumentByteLimit.contents(of:) reads it (empty is FileImportError.noTextToRead, past the limit DocumentTooLargeError), and TextutilSourceCheck.beginsAsRTF must find {\rtf at its start, else Failure.unreadable. An rtfd's attachments are never opened and do not count toward the limit.
    2. RTFTokenizer turns the bytes into group starts and ends, control words (names of at most 32 letters, parameters of at most 10 digits clamped to 32 bits), control symbols, \'hh bytes, and runs of text. It skips the bytes of a \binN, and a \binN that claims more bytes than remain ends the document.
    3. RTFInterpreter walks the tokens with its own array for the group stack, so no recursion follows the file's depth; a nesting of more than 10,000 groups (deepestNesting) throws Failure.unreadable(.rtf). Each group carries an RTFGroupState: its destination (RTFDestination: body, skipped, attachment, shape, font table, style sheet, style entry, info, title, author, list table, list text), bold, italic, hidden, font size, font, the \uc skip, and the paragraph's style, outline level, list, list level, and table flag. Text goes only to the body: skipped destinations (pictures, objects, headers, footers, comments, field instructions, bookmarks, and every unknown starred destination) read nothing. Hidden text (\v) and deleted text (\deleted, which includes a moved-away \mvf; \revised is read) read nothing: RTFGroupState.isDeleted sits beside the hidden flag, isUnreadRun is true for either, and it governs text, \line, \page, and a bullet and tab. \plain and \deleted0 undo \deleted, as the group's end does. A \page, \pagebb, or \sect in unread text begins no page. A footnote or endnote (\footnote, \ftnalt) is a .note destination, read by a second RTFBlockBuilder that the interpreter swaps in while the note lasts (the budget is taken from what is left and charged back at the end): the notes follow the body in file order (RTFDocument.notes), a note's reference mark (the reference run, or the up to 10 characters before the note's first \pard) is not read and is never a heading, a note is read only when its reference stands in read text, an unterminated note is closed at the document's end, and a note nested in a note, or in a header, title, or list marker, is skipped. A shape's text box (\shptxt, \dptxbxtext) is read by the same swap, except in a header or footer, and its blocks wait in the interpreter (RTFBlockBuilder's text boxes) and are written right after the paragraph or cell that holds its anchor. A field's \fldrslt is read and its \fldinst is not. The \info group gives the title and the author.
    4. The code page: \ansi is 1252, \mac 10000, \pc 437, \pca 850, and \ansicpgN wins; a font's \fcharset or \cpg gives the code pages of the text set in it (RTFEncodings: ANSI, Mac Roman, Shift-JIS 932, Korean 949 and Johab 1361, GBK 936, Big5 950, Greek, Turkish, Vietnamese, Hebrew, Arabic, Baltic, Cyrillic, Thai, Eastern European, and the two PC pages). Bytes wait in a run and are decoded together, so the two bytes of a double-byte character are one, even when the second is ASCII (isMultibyte); a run invalid in its code page is read byte by byte as Windows-1252, and a number with no encoding is 1252. \uN is a signed 16-bit value, a surrogate pair is two \u, and the \ucN characters after it are skipped.
    5. RTFStyleSheet records each paragraph style (at most 100,000) with its name, outline level, \sbasedon, and \pagebb. headingLevel(ofStyle:) follows the chain in a loop to the first style that says anything, and a loop or an undefined style gives no heading. An outline level of 0 to 8 is level 1 to 6 (deeper is 6) and wins over a name; "heading 1" to "heading 9" are the names, "Title" level 1, and "Subtitle" level 2. RTFListTable maps \lsN through \listid to the \levelnfc of each level (23 is a bullet, 255 none), at most 10,000 lists. A paragraph is a list item when it has a list or a \listtext or \pntext marker; the marker's text is never read; a bullet and a tab at the start of a paragraph make one too. A paragraph in a table cell carries its RTFListPosition, and the cell is written through the same list writer as the body, so an item in a cell is a list in the Markdown (an export shows its number), and no list's number is in the reading text.
    6. RTFBlockBuilder gathers the paragraphs, runs of one style joined; places the page breaks; groups cells into rows and tables (a table in which no cell holds a word is dropped; the words of a nested table stay in the cell around it); and keeps the budget: the limit in bytes, charged the text's bytes, 16 for each piece of text, 64 for each paragraph, and 81 for each cell (64 and its word's 17), past which DocumentTooLargeError (a table of about 790,000 cells, 5.5 MB of rich text, is the most a document may hold). A \page, a \pagebb (directly, or by its style), and a \sect whose section starts a page (\sbkpage, \sbkeven, \sbkodd, and \sectd's default; not \sbknone or \sbkcol) each add a pending break, written before the next letter or digit; a \pagebb or style break before any letter or digit adds none.
    7. When no paragraph is a heading by a style or an outline level, RTFSizeHeadings.apply guesses them by TextutilHTMLStructure's rule over the RTFBlocks (the body size by characters, a paragraph of 1 to 120 characters that is not one letter, larger sizes by rank, bold at the body size unless the body is mostly bold), never in a table or a list.
    8. RTFHTMLWriter writes the HTML (a heading carries no emphasis; consecutive list items share their lists by level; a list can begin no deeper than one level below the open list).

It differs from Word 97's in these steps:
    1. The FIB (readLegacy) holds the flags at 10, the language at 6, the character set at 0x14, the first and the end of the text at 0x18 and 0x1C, the lengths of the stories from 0x34, and the structures' offsets and sizes from 0x58. There is no table stream: the structures lie in the WordDocument stream, and the text between the two offsets is one range, or, for a document saved with Fast Save, in pieces of a piece table of plain offsets.
    2. WordLegacyCharacters reads the text one byte a character in a code page, or two (fExtChar: the Far East editions and files saved with them; a 16-bit unit with a zero above a Latin byte, or the lead byte of a double-byte character above its trail byte). WordLegacyCodePages chooses the code page for each run of one-byte text, in this order: text in the Symbol font is the Adobe Symbol encoding; the run's own mark (sprmCChse, 256 for Macintosh, else the FIB's mark for a Macintosh document); the character set of the run's font (direct, character style, paragraph style, sheet default); an explicit Windows mark in a Macintosh document; and the document's default, the non-Western code page whose fonts hold over half of the characters above 0x7F, else the language's. A double-byte document's code page is the document's. One sweep over the run boundaries with a cursor keeps the cost linear.
    3. WordLegacySprm turns the properties into Word 97's sprms (translation) so the readers of properties, styles, and sections are one for both. A property modifier is one opcode byte and an operand whose size the opcode gives, so a table of sizes (fixedSizes, a size byte first for the sprms whose operand varies, a 16-bit size for sprmTDefTable) is how a list is walked; it holds only established sizes, and an opcode it does not hold ends the walk of that list, which costs a toggle at worst. The sizes of 22 sprms and the section sprms 142, 147, and 164 to 169 were confirmed by walking every list in the real files to its exact end; italic (86), hidden (92), and deleted (65) rest on the fixed offset from Word 97's order alone.
    4. A paragraph with an ANLD and no level is not numbered. The numbering a style carries is not followed.

A deeper entry is a heading annotation (level depth + 1, at most 6) at its anchor. MOBIMarkup checks no nesting of its own since 0.4.1, where it threw damaged for markup nested more than 256 open elements deep (MOBIMarkup.maximumNesting and its estimate of the depth are gone): a section's markup reaches SwiftSoup only through MarkupGuard, in HTMLToMarkdownConverter.convert, which refuses markup nested more than 128 levels deep, with too many tags, too many attributes on one tag, or too much work, by throwing MarkupRefusal before SwiftSoup builds anything (see Shared helpers and, for the sentences, [Adding books](../../user/adding-books.md)). A section that opens as XML goes to SwiftSoup's XML parser, and a broken declaration in it is rewritten as an empty comment.

  - The steps: TextFileDecoder.decode(_:fileName:format:policy:) finds the encoding of a file's bytes in this order (decodeBytes), and finishes the text the same way whatever the encoding: a leading U+FEFF is removed, and every line ending becomes a line feed.
    0. The listener's choice, before everything the bytes say of themselves (encodingchoice): when the policy is .chosen(identifier), chosenText(_:identifier:fileName:) reads the whole file in that encoding alone, so a byte-order mark, valid UTF-8, and an HTML declaration settle nothing, and its basis is chosen. The read is strict (strictlyDecodedText(_:in:), Choosing the encoding, below): a byte the encoding does not define throws TextEncodingError.invalidForChosenEncoding, naming the file and the encoding as a listener hears it, and an identifier that is neither UTF-8 (utf8Identifier, "utf-8") nor the catalog's throws unknownChosenEncoding. Neither goes to the fallback, so a choice is never read as something else. The leading U+FEFF is removed, and the line endings made line feeds, as for every reading.
    1. A byte-order mark, for UTF-8, UTF-16, or UTF-32 (byteOrderMarks). Bytes after a UTF-16 or UTF-32 mark that are not valid in it throw TextEncodingError.invalidForMarkedEncoding. Bytes after a UTF-8 mark that are not valid UTF-8 go to the fallback (step 7) whatever the policy, and are never guessed.
    2. UTF-16 and UTF-32 without a mark, recognized by the structure of their bytes (unmarkedUnicode(in:)), by four rules in this order, the first that names an encoding deciding. (a) UTF-16 in a Latin script (unmarkedUTF16Encoding(of:)): an even length, more than half the code units with a zero byte in one position, and none with a zero byte in the other; its text is taken as it is. (b) UTF-32 (unmarkedUTF32Encoding(of:)): a length of at least 8 bytes that is a whole number of code units, every unit with its top byte zero and the byte below it at most 0x10 in one byte order and not the other, and one unit not zero. (c) UTF-16 in an alphabet (UTF16ByteStatistics.isAlphabetic): at least 16 bytes, at least 8 code units with a nonzero high byte, 85% of those sharing one high byte of 0x03 to 0x06 (Greek, Cyrillic, Armenian and Hebrew, Arabic). (d) UTF-16 in any other script (isAnchoredByZeros): at least 8 code units with a nonzero high byte; at least 8 anchors, the units with a zero high byte and a low byte of ASCII text (tab, line feed, carriage return, 0x20 to 0x7E: a space, a digit, a line ending), making up at least 90% of the units with a zero high byte, so that a few stray NULs in UTF-8 or 8-bit text, which make zero-high units of any low byte, show nothing; at most one zero low byte for four zero high bytes (一 and 가 have one); and 15% of the units with a nonzero high byte with a low byte of 0x80 or more. A byte order counts only when exactly one shows a rule, and the text of (b), (c), and (d) must read as text (isPlausibleText: no control character but tab, line feed, form feed, and carriage return, no C1 control, noncharacter, private-use character, character in planes 4 to 13, replacement character, or unpaired surrogate); a reading that is not goes on to the next rule, (b) to (c) or (d) (a UTF-16 column of single characters, one to a line, passes (b) as UTF-32 in planes no text uses and reads right by (c) or (d)), and the bytes that no rule reads go on to the steps after. A book that recorded its encoding (EncodingPolicy.recorded), and a reader whose files are no book and have no version to raise (a web archive's page without an encoding name, a .doc that is really a web page: TextFileDecoder.Evidence.legacy), ask (a) alone, as every read did before, and the legacy readers do not read an HTML file's ISO-2022-JP declaration either. Scripts at U+09xx to U+0Dxx are left out of (c), since their high bytes are 0x09, 0x0A, and 0x0D, the tab, line feed, and carriage return of a column of single characters, and Chinese, Japanese, and Korean UTF-16 with no ASCII character in it reads in the same bytes as Shift JIS, GBK, or EUC text; both are left to the steps after, since a missed recognition costs less than a wrong one. The rules were tried on 89 text samples of TestData in about 124,000 windows, and on the same sentences in more than 20 encodings in about 84,000, with no false positive, and again with one to four NULs put into the same windows at random places (about 81,000 windows of TestData, 12,000 of the sentences in 14 encodings) (TextFileDecoderTests). It comes before UTF-8 because UTF-16 of ASCII text is valid UTF-8 too, and so is Cyrillic UTF-16, read as control characters. The basis is unmarkedUnicode.
    3. A file in a 7-bit encoding that the policy names, ISO-2022-JP (sevenBitText(_:policy:)), which comes before UTF-8 because such a file is valid UTF-8 too. Only the guessing policy, and the recorded policy for a book that recorded a 7-bit encoding, look for one, so a book from before FMT16 reads the file as UTF-8, as it always did, except an HTML file whose declaration names ISO-2022-JP (declaredSevenBitText(_:)): when it holds an escape and guessSevenBit(_:) finds it well formed with a shift into JIS X 0208, it is read in ISO-2022-JP with the basis declaration(label:) under every policy but a recorded one (3a in decodeBytes), the declaration being unreachable otherwise since the file is valid UTF-8. A declaration with no escape in the file, or with a truncated one, changes nothing.
    4. Valid UTF-8.
    5. For an HTML file alone (readsDeclarations), the encoding declared in its first 1,024 bytes (declaredEncodingLabel(in:)): the XML declaration's, else the first meta element's charset, passing over comments. ISO Latin 1 and ASCII read as Windows-1252 (windows1252Equivalents), as browsers read them. A label TextMouth does not know, or bytes that are not valid in the encoding, throw TextEncodingError (unsupportedDeclaredEncoding, invalidForDeclaredEncoding) and are never guessed; a label that names a Unicode encoding, which the bytes have already failed, leaves them to the next step.
    6. The policy for bytes that name no encoding (settledText(_:policy:)): .recorded reads them in the recorded encoding, .guess asks TextEncodingGuesser.guess(_:), and .fallback leaves them to the next step.
    7. The Windows-1252 fallback (fallbackText(_:)), which gives every byte a character (windows1252Text(_:)).
  - The policy: TextFileDecoder.EncodingPolicy is what a read does with bytes that name no encoding, and it keeps a book's text from changing under its reader. .fallback is the policy of a book with no recorded encoding and of every reader of a file that is no book (M3UPlaylist.read, WebArchiveReader, and the web page TextutilDocumentReader reads for a .doc that is really one). .guess is the policy of the import of a file the user chose. .recorded(identifier) is the policy of a book with a recorded encoding, and EncodingPolicy.forBook(recording:) chooses between it and .fallback. .chosen(identifier) is the policy of a book whose encoding the listener chose (TextEncodingRecord.policy gives it, from the record's source, in place of forBook(recording:)): not an answer to bytes that name no encoding, as the three before it are, but a reading that overrules whatever the bytes name, and that is strict.   - The guess: TextEncodingGuesser.guess(_:) returns a Guess, the catalog's entry and the whole file read in it, or nil, which leaves the Windows-1252 reading. A missed guess costs less than a wrong one: the default is today's reading, while a guess that is wrong turns text that was right into text that is not, which the book keeps.
    1. examinedBytes(of:) takes the sample: the lines that hold a byte of 0x80 or more, from the start, until sampleLimit (64 KiB) is gathered. A line ends at a line feed or a carriage return, which no multi-byte encoding the guess reads uses inside a character; a single line longer than four limits is cut after a byte that ends a character in all of them (lastByte(ofLineFrom:to:in:): a byte below 0x40 that is not a digit, since the digits are the second and fourth bytes of a four-byte GB 18030 character). A file with no such line, or whose sample is more than maximumControlByteShare (2 in 100) control characters other than white space and escape, is no text and is not guessed.
    2. The sample is read as Windows-1252 and judged as Judging.windows1252, and in every catalog entry marked isAlwaysTried and the one entry Foundation's own guess names (foundationHint(for:), from NSString.stringEncoding(for:encodingOptions:convertedString:usedLossyConversion:) through TextEncodingCatalog.entry(for:); none when it names nothing, Windows-1252, or an encoding the catalog lacks), judged as Judging.rival. A reading with a replacement character is dropped.
    3. The readings are ranked by their surprise, fewest first, a tie keeping the catalog's order. In that order each must pass, or give way:
       - Its disorder, the anomalies and the excess uppercase, may be at most the greater of 1 and 3 in 100 of its non-ASCII characters (maximumDisorderShare). A reading that fails is passed over for the next.
       - The default must be worse by at least minimumGain (3) surprises, its surprises must be at least minimumDefaultSurpriseShare (3 in 100) of its non-ASCII characters, and it must show that it is wrong (isGarbled(comparedTo:)). If it does not, there is no guess.
       - settle(on:among:hint:) must be able to call the reading. If it is a Hebrew reading (Windows-1255 or ISO 8859-8), or ties with one, there is a guess only when Foundation's guess names Hebrew, since Hebrew letters are bytes that every Cyrillic encoding reads as clean lowercase letters and Hebrew has no case to betray a wrong reading. No other reading with as few surprises may read differently, unless only two distinct readings tie and Foundation's pick is one of them; readings that read alike differ only in name, and the hint's name, else the catalog's first, is used. If it cannot be called, there is no guess.
       - The whole file, not only the sample, must decode in the encoding (decodedText(_:in:)) and encode back to exactly the same bytes (allowLossyConversion false). A reading that fails is passed over.
  - ISO-2022-JP: guess(_:) cannot find it, since every byte is ASCII and the file is valid UTF-8, so guessSevenBit(_:) finds it by its structure, which TextEncodingByteGrammar.isWellFormedISO2022JP(_:requiringAShift:) checks as RFC 1468 defines it: only the escape sequences for ASCII, JIS Roman, JIS X 0201's half-width katakana, which Windows writes in mail, and JIS X 0208 (ESC ( B, ESC ( J, ESC ( I, ESC $ @, ESC $ B), pairs of bytes from 0x21 to 0x7E while in JIS X 0208, bytes up to 0x5F while in the katakana, a return to ASCII or JIS Roman before the end, and, for the guess (requiringAShift), at least one shift into JIS X 0208, since plain ASCII reads alike in every encoding; a file chosen to be read in ISO-2022-JP needs no shift. Foundation's reader lets a truncated escape or a byte above ASCII through, so it does not decide.
  - The judgment: TextPlausibility(reading:judging:) counts three kinds of surprise over a reading's characters outside ASCII (the ASCII ones read alike in every encoding).
    - Anomalies: a C1 control character, an unassigned character, a symbol between two letters, a capital directly after a lowercase letter when either is not ASCII (a case flip), a word that mixes Latin letters with another script, a combining mark that does not follow a letter of its own script, and symbols that text rarely holds.
    - Misfit letters: the non-ASCII letters outside the alphabet of the one language of its table that fits best (alphabets); for a script with no alphabets in the table, the letters of any other script than the commonest.
    - Excess uppercase: the uppercase letters beyond 35 in 100 of the cased non-ASCII letters, counted from 8 cased letters on.
    - surprise is their sum, with excess uppercase counted in a rival alone, and disorder is the anomalies and the excess uppercase.
    - The two sides are judged unlike (Judging). The characters Windows-1252 has (¦ ¬ ¤ ¨ ¯ ¸ ˜, quotation marks and ellipses glued to a letter, accents that stand alone, and ƒ µ ª º taken as symbols, not letters) are ordinary in its own reading, since a writer typed them, and anomalies in a rival, where they are what decoding made of other bytes: Mac Roman reads the bytes of Windows-1252's capitals Ü, É, and Ç as ‹, …, and «, so Windows-1252's "zeigeÜbersicht" read as Mac Roman is "zeige‹bersicht". Excess uppercase is no surprise in the Windows-1252 reading (headings in capitals, names, and identifiers such as "zeigeÜbersicht"), and an Irish accented capital after the h, n, or t that prefixes a word is no case flip there ("na hÉireann").
    - isGarbled(comparedTo:) is the proof that the Windows-1252 reading is wrong, which more surprises than a rival is not: Western text is made of ordinary Windows-1252 characters, each standing singly in a plausible place. It holds when the reading has three anomalies of at least two different characters (garblingAnomalies, garblingAnomalyCharacters); or five case flips (garblingCaseFlips); or misfit letters that are a fifth or more of its non-ASCII letters (misfitShareNeeded), at least ten of them when the non-ASCII letters are 8 in 100 of all the letters or more and at least six when they are half or more (misfitLettersNeeded), while the rival's misfit letters are at most 2 in 100 of its non-ASCII letters (rivalMisfitShareAllowed).
    - The same text is always judged alike: the commonest script decides how letters are judged (dominantScript(in:)), and of scripts with as many letters the first in Script.allCases wins, Latin first, where a dictionary's own order differs from one launch to the next (TextPlausibilityTests calls it with dictionaries of 1 to 64 capacities).

Windows-1252 and the encodings read as it (windows1252Equivalents) take every byte (windows1252Text(_:)); UTF-8 is String(data:encoding:), which refuses every malformed sequence; a multi-byte encoding's bytes must first keep to its grammar (next); and any other is Foundation's, which refuses a byte the encoding does not define, with a result holding U+FFFD refused too, since none of these encodings defines a byte as it. It is not the guesser's rule, which also asks the text to write back to the same bytes, because that refuses valid text with two codes for one character, as Windows writes 髙 in CP932 (0xFB 0xFC, which Foundation writes back as 0xEE 0xE0), and a listener who chooses Shift JIS must be able to read it.
  - The byte grammar: TextEncodingByteGrammar (Parsers/TextEncodingByteGrammar.swift) says which byte sequences make the characters of each multi-byte encoding of the catalog: .sequences, the bytes that stand alone and the lead bytes that begin a character of two, three, or four bytes with the bytes that may follow, or .iso2022JP, which switches character sets with escape sequences (isWellFormedISO2022JP(_:requiringAShift:), which the guesser asks too). The grammars are shiftJIS (cp932 and shift_jis), eucJP, iso2022JP, euc (gb2312 and euc-kr), gbk (gbk and cp936), gb18030 (with its four-byte characters), big5 (big5 and cp950), and unifiedHangul (cp949). of(_:) finds an encoding's by the String.Encoding Foundation reads it with, nil for an encoding of one byte to a character, and admits(_:) says whether every byte belongs to a character and none is cut off at the end. TextEncodingChoiceDecoderTests pins that every multi-byte encoding of the catalog has one.
  - Why it exists: Foundation's readers of several of these encodings let malformed bytes through, as measured on macOS 26.3 (October 24, 2026). EUC-JP and GB 2312 read a byte that cannot follow a lead byte as though its top bit were set, so the letter after it is taken into another character; Shift JIS reads 0x7F after a lead byte as 0x80; EUC-JP reads its single shift 0x8E before any byte; ISO-2022-JP reads bytes above ASCII as Latin 1, and a cut-off escape sequence as the escape and its letters; GB 18030 reads a lone 0x80 as the euro sign. Checking the bytes against the grammar first refuses all of these.
  - What no grammar can mend, since which characters an encoding defines is Foundation's to say: EUC-JP's JIS X 0212 characters (the single shift 0x8F and two bytes) are refused, left out of the eucJP grammar because Foundation takes the last of the three bytes for the start of another character, so "Le café." with é so written reads "Le café窺"; the euro sign in Big5 and CP950 (0xA3 0xE1) and in EUC-KR and CP949 (0xA2 0xE6), and Big5-HKSCS's characters (0x87 0x40 and up), even through Core Foundation's own big5-hkscs, are refused by Foundation's reader; CP950's 0xA2 0xCC reads as 十 followed by U+F87F, a private-use character that a braille display shows; and a GB 18030 file holding a literal U+FFFD is refused by the replacement-character check.
