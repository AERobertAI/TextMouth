# The parts of the app

Part of [TextMouth's architecture](../../ARCHITECTURE.md).

- One SwiftUI application. TextMouthApp (Platform/macOS/App/TextMouthApp.swift) declares three kinds of window:
  - Library windows (LibraryWindowView, ContentView, and LibraryView). The first opens at launch, and Command-N opens more.
  - Reader windows, one per book, identified by the book's ID (BookReaderWindowView, in the scene whose ID is BookReaderWindowView.windowID). A window's book can change in place when listening goes on to the next book, its scene value becoming the next book's ID in the same window (0.2.5, in [Windows](state/windows.md)). Window restoration is off, so none reopen at launch.
  - The Settings window (SettingsView), with ten tabs, one for each SettingsTab case, at the fixed SettingsView.windowSize. SettingsTabContent matches each tab with its view, and SettingsTabPage draws every tab but Text in the grouped form style, which scrolls and fills the window's width, keeping checkboxes and bordered fields (SettingsTab.scrollsAsAWhole); the Text tab's rule list scrolls by itself. SettingsTabFitTests finds every AppKit control of each tab where the window shows it or a scroll view reaches it, and measures each tab's height and width without a window (TODO A10: in the columns style, the Shortcuts tab was 4,113 points tall in the 540-point window, and 223 points wider than any width it was given).
- Two more kinds of window are AppKit's, so that closing one can ask first. The Record window, titled New Recording (RecordingWindowView, in an NSWindow that RecordingWindowController.shared makes, one at a time, with the identifier "new-recording" and restoration off): TextMouthApp attaches the LibraryViewModel recordings are saved into as a Library window appears, and File > New Recording… and Library > New Recording… show it, as does the first Library window's appearance when recordings were left behind (takes left behind, below). And the audio editor's windows, one for each book being edited, titled "Edit Audio:" and the book's title (AudioEditorView, in NSWindows that AudioEditorWindowController.shared makes, with the identifier "audio-editor" and restoration off), which Edit Audio… opens through AudioEditorLauncher (the editor window, below).
- App-wide objects, created once by TextMouthApp and given to every window as environment objects:
  - LibraryViewModel: the library in memory, and every operation on it.
  - SettingsViewModel: the global settings, and the config.json mirror.
  - KeyboardShortcutManager: every action's keyboard shortcuts.
  - SoundEffectService: the sounds that playback events play.
  - LibraryWindowRouter.shared: which window takes each app-wide action.
- AppDelegate (Platform/macOS/App/AppDelegate.swift) starts the router before Finder can hand over a file, owns MenuVisibilityManager, turns off window restoration, and holds a quit until nothing would be lost: it stops a data-directory move that is copying, has the Record window ask about a take it holds (RecordingWindowController.holdQuit) and then each audio editor window about its unsaved edits (AudioEditorWindowController.holdQuit), asks when changes are unsaved (UnsavedChangesTerminationGuard), and then finishes the work a quit must not cut off, the feed downloads keeping their place (three seconds at most, FeedQuitHold), a book's text read again (ten), and a speech export (five), saying what it finishes (QuitFinisher; see [Launch](launch.md)). At quit it cancels a transcription under way, asking nothing, and ends the session lease.
- Each reader window has its own ReaderViewModel, which has its own SpeechService, AudioPlaybackService, and NowPlayingSession. Readers share SleepTimerService.shared, ReadingStatsService.shared, TextSubstitutionService.shared, ReaderAutoplayRequests.shared, ReadingListOpenRequests.shared, and SpeechRenderCoordinator.shared, and, through ReaderCloudServices, the installed book storage, BookCloudStates.shared, and ReaderWorkingCopies.shared.
- The source folders:
  - App: the entry point, the delegate, the menu commands, the build identity, the process runtime (TextMouthRuntime), and the check made before quitting.
  - Models: value types and small rule tables, such as Book, BookInfo, Library, BookContentIndex, SettingsPolicy, StoredPreference, and the wording helpers.
  - Parsers: one reader per format, each turning a source file into DocumentContent (chapters, headings, and an index), plus shared readers for archives, packages, and text encodings.
  - Services: everything that owns a file, a queue, or a system resource. Services/Feeds holds the feed engine, whose FeedCenter.shared LibraryViewModel starts and offers as feeds, Services/AudioEditing the audio editing engine, which works without a window (audio edits, below), Services/Export the model, walker, and writers of text export, which the Export dialog's Convert to picker chooses among (exports, below), and Services/MP3 the MP3 encoder over the LAME library that project.yml builds from Vendor/lame (an MP3 file TextMouth writes, below).
  - ViewModels: LibraryViewModel and ReaderViewModel, each split into extensions by topic, plus SettingsViewModel, BookSearchModel, and LibraryBookUpdates.
  - Views: the SwiftUI views of the library, the reader, settings, the Record window, the audio editor window (Views/AudioEditor), the Export dialog (Views/Export), transcription's sheets, dialogs, and settings group (Views/Transcription), and the feed reader's interface (Views/Feeds), plus ViewBodyCounter.swift, which counts body evaluations for the hosted tests. VoiceOverFocus.swift, which places VoiceOver's focus in new windows and sheets, is in Platform/macOS/Views.
  - Phone: the iPhone app's plain types, which import no UIKit: PhoneSession, PhoneAppModel, the models and policies behind the reader, the Library, and the sheets, and the iPhone's words. Both apps compile it and the Mac's tests cover it, but the Mac's own app never makes one (see [The two apps and the platform folders](platforms.md)).
  - Platform: what differs between the Mac app and the iOS app (see [The two apps and the platform folders](platforms.md)). Platform/macOS holds what only the Mac compiles, in the same folder layout as the code around it: the entry point and delegate (Platform/macOS/App), the Edit Text and Edit Manifest editors, the helper-program runner WatchedProcess, and the Word 97-2003 export writer (Platform/macOS/Services), and the Record and audio editor windows' controllers, the VoiceOver focus code, and the read-only text area (Platform/macOS/Views). Platform/iOS holds the iPhone app's own code (its delegates, views, and services) and the stand-ins that only the iOS app compiles; the iPhone's plain types are in the shared folder Phone. The files directly in Platform (PlatformTypes, PlatformApplication, PlatformControlStyles) are shared by both apps.
- TextMouthBraille, a folder beside the TextMouth source folder rather than in it, is the C source of a second program built into the app: the helper that runs liblouis (Vendor/liblouis, which only it links) for braille, with the tables of the folder it is given: the app's own, or VoiceOver's for one of this Mac's tables. Its line protocol with the app, protocol 2, is defined once, in TextMouthBraille/include/TextMouthBrailleProtocol.h. The app target copies it into Contents/MacOS, and only BrailleTranslator starts it, under WatchedProcess (see Braille files, in [Imports](state/imports.md)).
- Concurrency: the view models, the window router, the settings mirror, the sleep timer, the statistics, the books' cloud states, the books kept on this Mac, the list cache, the live reading positions, and the voice list run on the main actor. Disk work runs on queues that each own their work: serial queues for the library index and for package records (LibraryPersistenceService), for imports (SerialImportQueue), and for logs (LogWriter), and at most two workers for cache updates (TextCacheUpdateQueue). Each import, text extraction, and book analysis on those queues runs through StorageBoundary.perform, which a data-directory move holds back and waits for, so none runs across the move's publication; the move then copies the data directory off the main actor, while every Library window's sheet keeps the library from changing. Rebuild Directory and the folder edits made from the library's sheets hold storage work the same way; a folder edit moves its packages and rewrites their records off the main actor, then publishes the new rows on it, keeping any change made to the library meanwhile (performLibraryTransition). Work that can wait on a drive or the network never runs on the main thread. The list's cloud refreshes and commands call the cloud services from detached tasks, and work that holds its thread for as long as it takes runs on a global dispatch queue (ReaderViewModel.offMain, OffMainWork) rather than on one of Swift's cooperative threads: the reader's requests to the book storage and its reads of a book, the check of a folder chosen for the library, the count of books only in the cloud before a move, a move's copy, and a folder edit's moves. The audio editor's level measurement reads its composition on a Thread of its own for the same reason: a reader may block for as long as CoreMedia takes, and on October 6 a few cancelled measurements blocked there starved the cooperative pool. A read that must never download runs inside DatalessFiles.withoutDownloading, which leaves dataless files in the cloud for its own thread only. Other work leaves the main thread too. The look-ahead prepares the speech of a chapter too long to render ahead on a global queue, which ChapterSpeechInputs allows by being values and prepare() by being pure, and the main actor keeps the result only while the chapter's inputs are unchanged. Rendered speech is fed to the engine's player node from RenderedSpeechFeeder's own serial queue, which every call on the node goes through, so a busy main thread never leaves the node without audio, and a completion handler of the node never waits on the feeder. The installed voices are listed on a detached task (VoiceCatalog), launch finds the books its cache batch must rebuild on a utility queue, where its metadata refresh reads the files of the rows an older reader read too, and Storage settings ask whether the data directory exists off the main thread. Transcription runs on an actor of its own (TranscriptionService), one book at a time, with its blocking reads on a global queue (OffMainWork); the main actor's TranscriptionJobCenter saves each transcript on a global queue too, a window's TranscriptionPresenter deletes one there, and its Clean Up sheet reads the cleanup's rules, cleans a transcript up, and undoes a cleanup there. The Record window's capture backend (CaptureSessionRecordingBackend) is an actor running on a serial queue of its own, since a capture session blocks while it starts and stops. The feed engine runs on the main actor; a feed's fetch, its parse, and a first merge run off it, its records, this Mac's fetch details, and its imports are written on queues of their own, and the files its after-playing sweep and newest-N rule remove go on the imports' queue (FeedDownloadManager.runBesideImports(_:)), once the records and the feeds' indexes are written on the main actor. Audio editing reads, renders (LAME encoding an MP3 within a render), and deletes originals off the main thread, as storage work (StorageWork.audioEditing), each change of a book's edit history under one lock (AudioEditHistoryStore), and an installed ffmpeg runs as a child process, never on the main thread; the editor window's model runs on the main actor, measuring the edited audio's levels off it, and plays through an AVPlayer. Every target builds in the Swift 6 language mode, set once in project.yml (TextMouthTests/Package.swift matches it), so concurrency diagnostics are errors, and `make check` fails on any Swift warning and on a Release app larger than 50 MB (11 MB on October 3, 2026, once `make build` stopped compiling with code coverage and the symbols were stripped into a dSYM that `make install` keeps for the last five installs, and 15.4 MB on October 4, with that day's features and LAME's encoder). The mode adds runtime isolation checks to `@objc` methods of main-actor classes and to main-actor closures handed to Objective-C APIs; each of the app's checks runs on the main thread, and VoiceWarmUp's buffer callback relies on AVSpeechSynthesizer calling back on the thread that called write(). SpeechService handles every callback of its direct synthesizer on the main queue, so its announcement of a text the speech engine refused, made only when no reader listens, asserts the main actor there (endDirectSpeechRefused(at:refusing:spanning:)). A render's RenderCancellationObserver, called on whatever thread the synthesizer uses, only sets a flag in an OSAllocatedUnfairLock and signals the semaphore the render queue waits on; it is Sendable, as the SDK makes every synthesizer delegate (AVSpeechSynthesizerDelegate is NS_SWIFT_SENDABLE), and the compiler checks it, with no `@unchecked`. Speak Info's LibraryInfoSpeechDelegate ends an announcement at once when called on the main thread, and otherwise on the next turn of the main queue, and the reader's WhereAmIDelegateHelper hands each finish and cancel of an announcement to the main queue. UncheckedConcurrencyPolicyTests requires a comment naming a lock, queue, actor, or thread on the three lines above each `@unchecked Sendable` or `nonisolated(unsafe)` declaration and pins their counts (27 and 15). The twenty-seventh `@unchecked Sendable` is ManifestOwedFields, the record of the title and author a manifest is owed, whose one stored property is a constant and UserDefaults is documented thread-safe. The fourteenth `nonisolated(unsafe)` is the record of each feed's index on disk, LibraryPersistenceService.feedIndexesOnDisk, confined to the save queue since FR11's branch A1, and the fifteenth the record of library.json on disk beside it, libraryIndexOnDisk, confined the same way.
- PlaybackMemoryGuard (Services/PlaybackMemoryGuard.swift) reads TextMouth's memory from launch on, whether or not anything plays (REV17a): applicationDidFinishLaunching begins the readings (beginWatching(), which starts no second loop), and readers report to it through followPlaybackForMemoryGuard. MemoryGuardPolicy decides from the state and the last reading alone: readWait(whileAnythingPlays:readInterval:idleReadInterval:) gives 5 seconds (readInterval) while anything plays, while playback it stopped for a runaway has not recovered, and while the last reading was at or above 1 GB (watchCloselyFootprint), and 30 seconds (idleReadInterval) otherwise. It stops playback at 3 GB, only while something plays, and saves and quits at 6 GB in every state, nothing playing included (B07). MemoryQuitMarker, the marker the next launch tells of, carries wasNothingPlaying, true when nothing played and no playback had been stopped for the runaway, which makes announcement() leave the book out ("… while nothing was playing."); a marker written before the field existed reads as false. PlaybackMemoryGuard.quitAtOnce() ends the converting children (WatchedProcess.terminateAll()) before it calls _exit.
