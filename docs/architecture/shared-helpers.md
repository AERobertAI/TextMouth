# Shared helpers

Part of [TextMouth's architecture](../../ARCHITECTURE.md).

These small types each own one rule that several parts of the app follow; use them rather than writing the rule again.

- LibraryWindowRouter (Services/LibraryWindowRouter.swift): decides which window takes each app-wide action.
- WindowCommandRouting (Views/Library/LibraryView.swift): decides which of several open windows takes a menu command or keyboard shortcut posted as a notification: a shortcut goes to the window it was pressed in, a menu command to the key window, and a window not attached yet takes either. Every Library window asks it through LibraryView's takesCommand(_:), and a reader, which counts its own sheets as itself, asks it too, as does an audio editor window's model for the editor's own shortcuts.
- LibraryBookUpdates (ViewModels/LibraryBookUpdates.swift): how open readers learn that the library changed their book or is moving its files.
- ReaderRequestStore (Services/ReaderRequestStore.swift): the one store of requests that wait for a book's reader, Continue to Next Book's (ReaderAutoplayRequests) and the reading list's (ReadingListOpenRequests): one a book, claimed once, thrown away after 30 seconds unless the book's reader holds them while the book downloads, and dropped when the open they wait for is refused (ReaderOpenRefusal).
- LiveReadingPositions (ViewModels/LiveReadingPositions.swift): where readers are between checkpoints. A live position goes there, never into the library, which takes a reader's position only at its checkpoints.
- ReaderSnapshot and SheetOverOneReader (Views/Reader/ReaderSnapshot.swift): what a view shows of its reader, republished only when it changes, and sheets that compare equal while they show the same reader. A view over a playing reader observes a snapshot, never the whole reader.
- TextCacheFingerprint (Models/TextCacheFingerprint.swift): what a text cache was written from, checked by size and date before any file is read.
- MarkdownCacheService.chapterMarker(title:) (Services/MarkdownCacheService.swift): the line that starts a chapter in content.md, which EPUB extraction and a transcript's text both write.
- MarkdownLiteral (Parsers/MarkdownLiteral.swift): the one place text is written as literal Markdown. escaped(_:) puts a backslash before every ASCII punctuation character, the form every content.md writer uses so that TextMouth's reader reads exactly a book's characters (PlainTextParser, HTMLToMarkdownConverter, the DOCX and DAISY converters, and the braille reader through MarkdownEmphasis). minimallyEscaped(_:smartPunctuation:) puts one only where a Markdown reader needs it, and guardingLineStart(_:) adds the one a line's start needs; with smartPunctuation, which TextMouth's own reader needs, quotes and doubled hyphens or periods are escaped too. The export's Markdown (MarkdownExportWriter) writes without it, and a transcript's content.md (TranscriptTextBuilder.markdown) with it. MarkdownEmphasis.markdown(_:styles:literal:) takes the writer for each stretch between delimiters, MarkdownLiteral.escaped unless the caller gives its own.
- ParserUtilities.removingSoftHyphens(_:) (Parsers/ParserUtilities.swift): the one place a soft hyphen (U+00AD) is left out of a book's words. The Kindle readers call it, for a KF8 book's markup and its contents' labels, and for a MOBI 6 book's markup, labels, and plain text (see [Imports](state/imports.md)). The EPUB reader does not call it. A publisher puts soft hyphens inside words to say where a line may break.
  - The spellings it catches, in the text it is given, which is markup that SwiftSoup decodes afterwards:
    - the character itself, U+00AD;
    - `&shy;` in lower case, and `&shy` with no semicolon when no ASCII letter or digit follows it, which SwiftSoup decodes too;
    - `&#173;` and `&#xAD;`, with `x` in either case, with or without the semicolon, and with any number of leading zeros. The number's value is judged, capped while its digits are read, and not its length.
  - The spellings it leaves alone, since the parser keeps them as text: `&SHY;` and `&Shy;` (HTML has no such entity), `&shy1` and `&shyx` (a letter or digit follows), and any other number.
  - A text with no soft hyphen costs one scan and no copy.
  - Measured on November 9, 2026, a soft hyphen left in a word:
    - hid the word from Search in Book: `hyphenation` did not find `hy\u{AD}phenation`, literal or as a regular expression (`SoftHyphenEffectTests`);
    - became a visible hyphen in braille, dots 3-6, with the rest of the word unchanged where no contraction spans the cut, in UEB grades 1 and 2 (`SoftHyphenEffectTests`); a cut inside a contraction was not measured;
    - was spoken as the hyphen it is taken for: the speech engine rendered exactly the frames a hyphen-minus gives, 2.2% and 5.8% more than the same words whole, in two sentences with compact Samantha (`Scripts/agents/probes/speech-soft-hyphen-probe.swift`, with its results at the end of the file). Nothing was played.
  - Known gap: `&shy` directly followed by `=`, `-`, `_`, `#`, or `&` is removed by the helper, while SwiftSoup would keep it as text (`a&shy=b` becomes `a=b`). The check found 43 such strings in 60,000 random ones, and no real book writes this.
  - Not decided: the EPUB reader keeps soft hyphens, and they do the same there. The EPUB samples hold none.
- TranscriptText (Models/TranscriptTextIndex.swift): a transcribed audiobook's text with its timing, sentence by sentence: the sentence heard at a time, the place in the text for a time and the time for a place, and so the reader's audio cursor converted both ways. An edit in the user's editor (TranscriptEditing.apply) and a cleanup (TranscriptCleanup) both rewrite sentences through it.

It is in the app rather than the tests so that later work, such as learning rules from the user's own edits, can use it.

- SavedFile (Services/SavedFile.swift): reads a small file that TextMouth reads whole and replaces whole, one another Mac writes too or one of this Mac's own, with dataless files left in the cloud, telling a missing file, one only in the cloud, and one that can't be read apart, and preserves one that can't be used before anything replaces it. SavedFile.renameReplacing(_:_:) is the one rename(2) helper, which puts a file in place of another in one step: the log writer's rotation, the reading-text cache, and a filtered audio render's result use it. SavedFile.OnDiskMemory is the one memory of what this process last read or wrote of some files in one data directory (holds(_:for:at:), remember(_:for:), write(_:for:using:), forget(_:), startOver(unlessIn:)), so a save writes a file only when its freshly encoded bytes differ: library.json and each feed's index use it (see [the library index](state/library-index.md)). A write goes through write(_:for:using:), which runs it and remembers the bytes only when it succeeds; when it throws, it forgets what was remembered of the file, since a rename on a network volume can land and still report failure, so the file's state is unknown, and a later save, an undo to the older bytes included, writes instead of being skipped as unchanged. remember(_:for:) is for bytes just read, or known to be what the file holds. The caller must encode the same content to the same bytes, with sorted keys and a fixed row order, and confine the value to the queue it reads and writes on, since it does no locking of its own.

- MarkupGuard (Parsers/MarkupGuard.swift), MarkupScanner (Parsers/MarkupScanner.swift), and XMLOpenElements and HTMLTreeModel (Parsers/MarkupNesting.swift): the one way markup reaches SwiftSoup, since 0.4.1. A book's markup is untrusted, and three things in it took the whole app down, or the Mac's memory with it:
  - SwiftSoup's XML parser traps on a declaration it takes apart and finds no element in, such as `<?a>` or a torn `<?xml version="1.0"`. The guard rewrites any such declaration as `<!---->` before the parser sees it, which SwiftSoup 2.14 does too, and changes no other byte, so no book that could be read reads differently.
  - SwiftSoup walks up an element's parents by recursion, and an import runs on a 512 KiB stack, so markup nested thousands of levels deep overflows it.
  - An element takes a kilobyte or two of memory however few bytes its tag has, so a limit on bytes is no limit on memory.
- MarkupGuard's entry points are `parse(_:baseURI:deepestNesting:)`, which picks SwiftSoup's XML parser when the markup opens with `<?xml` (by `opensAsXML`, SwiftSoup's own idea of whitespace) and its HTML parser otherwise, `parseXML(_:baseURI:deepestNesting:)`, and `parseBodyFragment(_:)`. `MarkupGuardTests.testEveryParseGoesThroughTheGuard` fails on any `SwiftSoup.parse`, `Parser.parse`, `Parser.xmlParser`, `Parser.htmlParser`, `.parseInput(`, or `XmlTreeBuilder(` in the app's sources outside MarkupGuard.swift, so a new reader cannot leave the guard behind. The readers that ask it are the EPUB, HTML, DAISY, Kindle (through HTMLToMarkdownConverter), and TextutilDocumentReader paths, the portable XML tree's lenient reader, and the feed code's discovery, article, and title reads.
- The two layers hold the depth, so that one slip of the first cannot crash the app:
  - Before the parse, `inspect(_:as:limits:)` makes one pass over the bytes, linear in their size. MarkupScanner finds the tags SwiftSoup 2.13.9's tokeniser finds, in the same places (a map of `TokeniserState`, MIT, with its oddities: a declaration ends at its first `>`, quoted or not). XMLOpenElements follows `XmlTreeBuilder` exactly: a start tag that does not close itself pushes its name, and an end tag pops to the nearest open element of the same name and letter case. HTMLTreeModel follows `HtmlTreeBuilder` and `HtmlTreeBuilderState`, mode by mode, with the open elements, the formatting list, foster parenting, the adoption agency, and the form and head pointers, and counts the depth of the deepest element, `html` at 1, never less than the real tree. It copies SwiftSoup's own slips and not the HTML standard: the body has no `frameset` rule, `generateImpliedEndTags()` with nothing to exclude does nothing, the body reads the current node once as a start tag begins, `p` is in button scope whenever one stands above the last `button` while every open element has a tag id, an end tag of `applet`, `marquee`, or `object` does nothing while an element named "name" is in scope, `InTableBody` asks for `tfoot` in the ordinary scope, `InSelect` serves every select, and the adoption agency looks only at the first 64 stack entries. Where the markup cannot say which way the parser goes (a character reference that may decode to whitespace), the model takes the deeper way; where it cannot follow tags (a head's `noscript` holding raw-text tags), `tagsAreCertain` is false and the pass counts every tag ahead as open.
  - After the parse, `MarkupGuard.requireDepth(of:atMost:)` walks the parsed tree with a stack of its own and throws `MarkupRefusal.nestedTooDeeply` when an element is deeper than the limit, before the converter or any other reader that calls itself for each level sees the tree. `parse`, `parseXML`, and `parseBodyFragment` all end with it.
- The big stack (0.4.2): `MarkupGuard.onLargeStack(_:)` runs SwiftSoup's parse, the depth walk after it, and the release of a refused tree on a `pthread` of its own, so that a wrong count in the first layer cannot overflow SwiftSoup's recursion up a tree's parents. All three entry points use it.
  - The size: `stackBytes(forTreeDepth:)` gives 512 bytes (`stackBytesPerLevel`) for each of 1,000,000 levels (`deepestTreeParsed`, the most the memory limit lets through, since every node counts as at least one unit of 1,000,000) and a megabyte more, in whole megabytes, which is 490 MiB. The worst shape measured, an inline element or a list closed again, touches about 200 bytes a level in a debug build and 160 to 190 in Release; the release of a tree touches none, because SwiftSoup 2.13.9's `Node.deinit` takes a deep tree apart in a loop. 512 is two and a half times the worst, measured on 12 shapes and not on all.
  - If the system refuses a stack, the size drops to a quarter, in whole megabytes, while it is at least 8 MiB (`smallestStack`): with today's limits 490, 122, and 30 MiB, the last holding about 59,000 levels. Then the body runs on the caller's thread, with the first layer's count as the only guard. The sizes below 30 MiB are never tried, since 7 MiB is under the floor.
  - Waiting: the caller blocks in `pthread_join` until the thread ends, as it was blocked while the parse ran on its own stack. The thread takes no lock and waits for nothing the caller holds. It has the caller's quality of service. `pthread` is used, not `Thread`, because a failed `pthread_create` with no fallback would leave the caller waiting for ever.
  - The job and its result cross the C interface as an address, so Swift 6 does not check them. `outcome` is written by the thread alone before it ends, and read by the caller alone after the join. `withExtendedLifetime(job)` keeps the job alive until then. There is no `@unchecked Sendable`.
  - The task-local limits are read on the caller's thread and passed in as constants, since a task-local does not follow a `pthread`.
  - `MarkupGuard.Limits.deepestTree` (nil in the app) sets the second layer's limit apart from `deepestNesting`, which `deepestParsedTree` falls back to. Without it, lifting the first layer's count lifted the second layer too, and the second layer could never be seen refusing a tree the count let through.
  - Cost: about 55 microseconds more a chapter in a Release build (`alice.epub`: 266 to 321 microseconds a chapter), and about 22 microseconds more for each of 20,000 short feed fragments. A 300-chapter book costs about 7 ms more. Peak memory is the same.
  - Not checked: shapes beyond the 12 measured; HTML trees past 50,000 levels, because the lifted first-layer count is quadratic (the stack use of HTML was measured to 20,000 levels, and of XML to about a million, where it showed none); and iOS, below.
, set on November 7, 2026 from 3,236 documents of 327 real files and from how deep a tree each reading path survives on the 512 KiB stack of an import. A test binds others with `MarkupGuard.$limits.withValue(_:operation:)`, a task-local that changes only the reading that operation does:
  - Nesting, 128 (`deepestNesting`). The deepest real book nests 12 levels and the deepest web page tried 36. The converter's recursion reads at least 552 levels in a Release build (nested quotes, where the Markdown parser runs out), 862 of lists, and about 1,190 of most other shapes, and a tree can go twice as deep as the count, and two more, so the deepest tree at 128 is 258 levels. A debug build reads only 108 levels of lists and 117 of divisions, so a hostile file nested 108 to 128 deep can overflow a developer's debug build and never the app.
  - Memory, 1,000,000 units (`mostMemoryUnits`), where a unit is `tags + 2 * tagsWithAttributes + attributes / 3` (about 800 bytes of SwiftSoup's tree for a node with text). The most in a real document is 431,296, Webster's Unabridged Dictionary as one 32 MB HTML file.
  - Attributes on one tag, 1,000 (`mostAttributesOnATag`). No real tag has more than 7; SwiftSoup's time grows with the square of them.
  - Work, 30,000,000,000 (`mostWork`), what SwiftSoup spends where its time grows with the square of the markup, about half a minute. The most in a real document is 1,300.
- Feed discovery (`FeedDiscovery.deepestNesting`) has a limit of its own, 512, passed as `deepestNesting`, because it walks the page with a stack of its own and converts nothing. What still calls itself for each level is SwiftSoup's own recursion, which reads at least 3,002 levels in Release and 2,002 in debug, so at 512 the deepest tree is 1,026.
- MarkupRefusal has four cases, each a sentence a listener can act on that never calls the file damaged: `nestedTooDeeply(limit:)`, `tooMuchMarkup`, `tooManyAttributes(limit:)`, and `tooMuchWork` (the sentences are in [Adding books](../user/adding-books.md)). The pass costs 13% of an HTML parse and under 2% of an XML one, and 0.133 seconds on Webster's 32 MB against the parse's 0.944.
