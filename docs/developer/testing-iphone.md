# Testing the iPhone app
<!-- id: testing-iphone-app; keys: ; src: -->

Part of [TextMouth's documentation](../../README.md).

The iPhone app is tested in two places: on the Mac's test host, for everything that does not need iOS, and in the iOS simulator, for what only iOS compiles. See [The two apps and the platform folders](../architecture/platforms.md) for how the code is divided, and [Building TextMouth](building.md) for how the simulator is built.

Tests that act as a person does find what tests of the parts miss: the first iPhone test to set End of heading at a book's opening found a bug that the Mac's unit tests never met.

## The phone area
<!-- id: phone-area; keys: ; src: TextMouthProductionTests/PhoneSessionTests.swift, TextMouthProductionTests/PhoneLaunchRequestTests.swift, TextMouthProductionTests/PhoneBookSearchTests.swift, TextMouthProductionTests/PhoneFocusRequestsTests.swift, TextMouthProductionTests/TranscriptSearchTests.swift -->

- The `phone` area of `Scripts/test/areas.conf` holds the iPhone app's tests as far as the Mac's test host can reach it. It has 56 classes of TextMouthProductionTests: the session, the models, the routes, the words, the policies, `IOSInfoPlistTests`, and the iOS branches of shared code (`IOSBranchTests`).
- Most of the iPhone's logic is in plain types under `TextMouth/Phone/` that import no UIKit, so this area decides nearly every rule: `PhoneSessionTests`, `PhonePassagePolicyTests`, `PhoneEscapePolicyTests`, `PhoneScreenHoldsTests`, `PhoneLaunchRequestTests`, and the rest.
- Three of the 56 classes are for the error alert, Speech Stopped, and the preview's pause: `PhoneErrorAlertPlanTests`, `PhonePreviewPauseTests`, and `PhoneSpeechRefusalPresentationTests`. `Scripts/test/areas.conf` lists them in `phone` only.
- Search in Book (0.4.4) is tested in the hosted suite by:
  - `PhoneBookSearchTests` (12 tests): the words, that the shared words are the Mac's own, the one-second typing pause, a text result's row (a percent) and a transcript's (a time), a result with no heading, that a row says what the Mac's row says, an empty source, and the model searching, saying the count once, saying "No matches" and an invalid pattern, and saying nothing when cancelled.
  - `PhoneFocusRequestsTests` (6 tests): an undisturbed request posts once; a landing on any kind of reader control cancels the waiting request, with every control kind tried so that one whose landing fails to cancel is named; a landing elsewhere (Back, the title) cancels nothing; a landing cancels every request waiting; a request made after a landing stands; a landing with nothing waiting is harmless.
  - Additions to `PhoneReaderModelTests` (an untranscribed audiobook says why without telling anyone to transcribe, the Mac's words still name the command, a text book's jump), `PhoneReaderControlsTests` (the control's words, and `testTheGridRowsKeepOrderAndPairs`), `PhoneFoundationTypesTests`, `PhoneLaunchRequestTests` (6 tests: the third variable, the reads and the debug-only type), `PhoneSessionTests` (four tests of `closeBook(id:)`), and `TranscriptSearchTests` (`goToSearchResult` takes the transcript's move for a transcript and the other move for any other book). The Mac's pinned sentences in `TranscriptSearchTests` still call with the defaults.
  - These classes run in the full suite. `PhoneBookSearchTests` and `PhoneFocusRequestsTests` are not listed in an area of `Scripts/test/areas.conf` at the merge, so `run-area.py` does not run them.
- `PhoneLaunchRequestTests` is inside `#if DEBUG`, with the type it tests, so a Release test run does not have it. `PhoneSessionTests` pins the reopen keys that go with the crash guard (`testTheReopenKeysGoWithTheCrashGuardWhenTheSessionIsMade`, `testTheVerdictLeavesTheKeysOfABookOpenedSince`, and `testTheReopenKeysStandWhenNoCrashGuardIsFound`), and `PhoneLifeCycleReopeningTests` checks from the life cycle that the crashed book's key is gone after the verdict (see The crash guard in [The two apps and the platform folders](../architecture/platforms.md)).
- It runs like any area: `make test-area AREAS="phone"`, `Scripts/test/run-area.py phone`, or a train request with `--areas phone` (see Reusable test tools, above).
- It tests the Mac's build. A rule written under `#if os(iOS)` that has no plain type behind it is not reached here.

## The two iOS test targets
<!-- id: two-ios-test-targets; keys: ; src: TextMouthiOSUITests/LargeTextUITests.swift, TextMouthiOSUITests/PlaybackUITests.swift, TextMouthiOSUITests/SearchUITests.swift, TextMouth/Phone/PhoneLaunchRequest.swift, TextMouthProductionTests/PhoneLaunchRequestTests.swift -->

- Both are in the committed `TextMouthiOS` scheme, which runs them together in the iOS simulator. The Mac's schemes do not run them. Since November 11, 2026 GitHub runs both in one `xcodebuild` run (see Tests on GitHub Actions, above), so this Mac needs no simulator to run them.
- `TextMouthiOSTests` is a unit-test bundle hosted in the iPhone app. It has 19 tests, which make no sound (they play, speak, and record nothing; `test_run_ios_ui_tests.py` fails if a file of the folder names an audio framework, a player, or a recorder), so they need no sound variable. The check reads names, so it does not see a call whose name starts with another word, such as `startSpeaking(` or `startPlayback(`; what it does catch is the model types a unit test would reach one through (`ReaderViewModel`, `PhoneAppModel`), so add a pattern for those words if a unit test ever takes a bare model.
  - `PhoneControlButtonTests` (12 tests) tests the reader's UIKit control: its words, its traits, that it is one element, its actions, and its smallest height of 44 points.
  - `IOSRuntimeTests` (4 tests) tests the iOS runtime: that a hosting process runs in a sandbox, that a UI test's launch request does too, that without the request the home is the app's container, and that the library lives in Application Support. The two tests that read `PhoneLaunchRequest` are inside `#if DEBUG`, as the type is, so a Release test run has 2 of the 4.
  - `PhoneValueRowTests` (3 tests) measures `PhoneValueRow` at the 12 Dynamic Type sizes: stacked at the 5 accessibility sizes, side by side at the 7 others (see PhoneTextStyle in [The two apps and the platform folders](../architecture/platforms.md)). A third test checks that SwiftUI still has 5 and 7.
- `TextMouthiOSUITests` is an XCUITest bundle that drives the app from outside, in the simulator. It has 35 tests, of which 13 press Play or type (the 6 of `PlaybackUITests`, 6 of the 7 of `SearchUITests`, all but its empty sheet's, and the Search test of `LargeTextUITests`) and run only where sound is allowed, on GitHub's runner (see In the simulator, sound tests run on GitHub only, below).
  - Each test launches the app with a library of its own and, usually, a public-domain book sent to it: Alice's Adventures in Wonderland, Project Gutenberg #11, from `TestData/alice.epub` (see PhoneLaunchRequest in [The two apps and the platform folders](../architecture/platforms.md)).
  - `ReaderUITests` (4 tests): the reader's order, its first values, 44-point controls, and its audit.
  - `LibraryUITests` (4 tests): the Library's words and order, empty and with a book, and the audit of each.
  - `ScreenOrderUITests` (10 tests): the order of the Add to Library sheet, Settings, Bookmarks, Headings, Go To, Sleep Timer, the Voice sheet, Book Information, and the navigation unit's choice, with the audit of each.
  - `LargeTextUITests` (4 tests): see LargeTextUITests, below.
  - `SearchUITests` (7 tests, 0.4.4; typed since November 10, 2026; see SearchUITests, below).
  - `PlaybackUITests` (6 tests, November 10 and 11, 2026): see PlaybackUITests, below.
  - `ToolbarPlacementProbeUITests` is gone (0.4.3). It was one test that recorded what iOS shows for a button in `.cancellationAction`. Its answer is in `PhoneSheetButton.swift` and in [The two apps and the platform folders](../architecture/platforms.md), and its launch variable, `TEXTMOUTH_PROBE_SYSTEM_PLACEMENT`, went with it.
  - They read what VoiceOver would be given: each element's label, value, and traits, in the order of the accessibility tree, as a depth-first walk of one snapshot.
  - No wait lasts longer than 60 seconds.
- To run them, use the `TextMouthiOS` scheme with the build rules in [Building TextMouth](building.md): the iPhone 17 simulator, the one build folder, `Scripts/agents/run_locked.py`, and a new result-bundle name for each pass. A test run has the shape `xcodebuild test -project TextMouth.xcodeproj -scheme TextMouthiOS -destination 'platform=iOS Simulator,name=iPhone 17' -derivedDataPath build/DerivedData-ios.noindex`, and `-only-testing:TextMouthiOSTests` or `-only-testing:TextMouthiOSUITests` runs one bundle.
- The passes of November 9, 2026 (the fix round `ios/fix-d-1109`), all on the iPhone 17:
  - Pass 3, before the review: 19 of 19 unit tests and 21 of 21 UI tests passed.
  - The review's fixes made Dynamic Type and clipped text fail again at the largest size (see LargeTextUITests, below). Pass 4 then ran 21 UI tests with 1 failure, Settings scrolled, on a nameless "Text clipped". Pass 5 ran 21 with 2: a nameless "partially unsupported" on the Library scrolled, and a Bookmarks tap that opened nothing, which is not a largest-size test.
  - The branch's last commit accepts the first and retries the second. The reports say it was only compiled. The log of a sixth pass, in the round's folder under `build/orchestrator/iosfixd/`, shows 19 of 19 unit tests and 21 of 21 UI tests with 0 failures, finished after that commit. The reports do not mention it, and the commit it ran is not recorded there.
  - Nothing here was run with VoiceOver.

## The audit and its accepted findings
<!-- id: audit-accepted-findings; keys: ; src: TextMouthiOSUITests/TextMouthUITestCase.swift, TextMouthiOSUITests/SearchUITests.swift, TextMouth/Services/BookTextEditing.swift, TextMouth/Services/TranscriptTextBuilder.swift, TextMouthiOSUITests/LargeTextUITests.swift -->

- Each UI test that audits runs Apple's accessibility audit on the screen showing, `performAccessibilityAudit`, and fails once with every finding that is not accepted. Each finding is listed with its type, its element, and Apple's words, so one run shows them all. A screenshot of the audited screen is kept with the results.
- **Each kind runs alone.** `audit` makes one `performAccessibilityAudit` call for each of the seven kinds, from one table, `auditKinds` in `TextMouthUITestCase` (the kind and its name), which `name(of:)` reads as well. The seven are the iOS 26.0 SDK's: contrast, element detection, hit region, element description, Dynamic Type, clipped text, and trait.
  - Why: audited together, a finding named no element ("no element"), so it could be neither matched to an accepted one nor found on the screen. Audited alone, it names its element. Go To's "Potentially inaccessible text" appeared in both runs that audited every kind together, and in none of five launches that audited that kind alone. Its cause is unknown. That it is a product of the combined run rests on two combined runs against five single ones.
  - The loop runs the kinds in the table, not `.all`. A kind that a later SDK adds is skipped until it gets a row there, and the table's comment says so.
  - A finding's element is read from one snapshot, taken only if the element still exists, and the same snapshot serves the match and the trace (type, label, value, identifier, frame, whether it is enabled, and its children).
- On iOS the audit only inspects. The audit of an element's actions exists on macOS alone (`XCUIAccessibilityAuditTypes.h`).
- A finding is accepted only when the app cannot change it, or when it is proven false. An `Accepted` value matches the audit's type and the element's label (exactly, or by its start when `labelIsPrefix`), and, for some, Apple's own short description of the finding. It is kept with the results, with its reason. There are eight, in four groups. The Search in Book audit declares one more of its own, in the test (see SearchUITests, below).
  - **Parts iOS draws:**
    - `searchField`: the clipped-text finding on "Search books", because the system's search field clips its placeholder at the largest text sizes, and VoiceOver and braille read it whole.
    - `barItem(label)`: the Dynamic Type finding on a button in a bar, because iOS draws the button and does not grow bar items with Dynamic Type. It shows them in the Large Content Viewer instead. Two bars count: the bar at the bottom of the Library ("Settings", "Add to Library"), and the top bar of a sheet (Cancel, Close, Done, Save, and Back to Book). Each sheet's test names its own buttons.
    - `navigationTitle(title)`: the clipped-text finding on a screen's title, because iOS truncates a long title at large sizes, and VoiceOver and braille read it whole. It is accepted for the reader (the book's title) and the sheets: Add to Library, Settings, Bookmarks, Headings, Go To, Sleep Timer, "Voice & Speed for This Book", Book Information, and "Navigation unit".
  - **A false positive, proven:** `firstHeader(title)` is the contrast finding on the first section header under a bar, "Voice" on Settings and "New Timer" on Sleep Timer. On November 9, 2026 the screenshots kept with the results showed black text, (0, 0, 0), on (235 to 242, 235 to 242, 240 to 247), in a frame 370 by 40 points at (16, 116) or (16, 132): about 17 to 1. Nothing switched off cleared it. It is matched by the header's words and the contrast kind only, so any other contrast finding still fails.
  - **Large text, by element:** `librarySummary` is the Dynamic Type finding ("partially unsupported") on the Library's summary row, matched by the first words of its label, "1 book." The row is a plain `Text` that grows and wraps (5 lines at the largest size in the screenshots). Its cause is unknown.
  - **Large text, with no element**, used only on the audits of `LargeTextUITests`, and matched by an empty label, the kind, and Apple's exact words:
    - `unnamedUnsupported`: "Dynamic Type font sizes are unsupported". Probably the system stepper's minus and plus, which iOS does not grow, but this is unproven. It is accepted on Settings at the largest size, as it first appears, as well as scrolled, and on the Library scrolled.
    - `unnamedPartlyUnsupported`: "Dynamic Type font sizes are partially unsupported", seen once on the Library scrolled. It is accepted on the two scrolled audits.
    - `scrolledPastTheEdge`: the clipped-text kind and Apple's words "Text clipped", for text cut by the screen's edge or the bar it scrolls under, which is what scrolling does. The screenshot of pass 4 showed a line cut under the navigation bar and a row cut at the bottom edge. It is used only by the two scrolled audits.
    - These three are broader than the others and not verified one by one. A real fixed font would still name its element and fail.
- Any other finding fails its test. To accept a new kind, add an `Accepted` value with its reason to `TextMouthUITestCase`, and add its reason here.

### Audits that report without failing
<!-- id: audits-that-report-without-failing; keys: ; src: TextMouthiOSUITests/LargeTextUITests.swift, TextMouthiOSUITests/TextMouthUITestCase.swift, TextMouthiOSUITests/SearchUITests.swift -->

- `audit(_:screen:types:informing:accepting:)` takes `informing`, a kind of finding that is kept with the results and does not fail the test. The note is an attachment named "<screen>: findings reported, not failed".
- It is for a kind that another test checks, or whose cause is not known. Five audits use it, all for Dynamic Type at the normal text size:
  - the Library with a book (`testTheLibraryWithABookPassesTheAudit`), for its summary row;
  - Settings (`testSettingsPassesTheAudit`), for the lower rows: a slider's value and caption, and the switch;
  - Sleep Timer, for its stepper's label, a system control's;
  - Book Information, for the read-only rows at the bottom;
  - the Search in Book sheet with results (`testTheSearchSheetPassesTheAudit`), for the status line, the "Search results" heading, the regular-expression switch, and the field; `LargeTextUITests` measures that these grow (see SearchUITests, below).
- `LargeTextUITests` does not use it any more: it fails on what it finds, except the accepted findings above.
- A test that reports is not proof that the screen passes. `LargeTextUITests` audits the same screens at the largest size.
- Every other kind of finding on those screens still fails.

### LargeTextUITests
<!-- id: largetextuitests; keys: ; src: TextMouthiOSUITests/TextMouthUITestCase.swift, TextMouthiOSUITests/LargeTextUITests.swift, TextMouth/Platform/iOS/Views/PhoneTextStyle.swift, TextMouthiOSUITests/SearchUITests.swift, TextMouthiOSUITests/ScreenOrderUITests.swift -->

- It audits for Dynamic Type and clipped text only (`sizeFindings`), at the largest size iOS offers, Accessibility Extra Extra Extra Large. A bigger size does not exist.
- The size is set at launch with `-UIPreferredContentSizeCategoryName UICTContentSizeCategoryAccessibilityXXXL` (`TextMouthUITestCase.largestText`), as the Larger Text setting would. Nothing changes the simulator's own settings.
- **Dynamic Type and clipped text fail again** (0.4.3). The branch's first version made all five audits report only, which silenced every Dynamic Type finding at any size, so a fixed font could pass. The review caught it. Now only the accepted findings above pass, and any other Dynamic Type finding, such as a fixed font on either screen, fails.
- Its four tests:
  - `testTheLibraryWithABookHoldsAtTheLargestText` audits the Library with a book, as it first appears and then scrolled once, since the summary row is below the first screen at this size. It accepts the system parts and `librarySummary`, and, scrolled, the three nameless findings.
  - `testSettingsHoldsAtTheLargestText` audits Settings as it first appears and then scrolled two screens down. It accepts the title and `unnamedUnsupported`, and, scrolled, the other two nameless findings. `PhoneValueRow` stacks the value under the name at these sizes, and the screenshots show nothing cut or overlapped.
  - `testAddToLibraryHoldsAtTheLargestText` audits the Add to Library sheet. It accepts its title and Cancel, and nothing else.
  - `testTheSearchSheetHoldsAtTheLargestText` (November 11, 2026) types a search into the Search in Book sheet (so it runs only where sound is allowed) at the default size and then at the largest, in two launches of the same test, and measures the height in points of the four parts the sheet's audit named: the field, the status line, the switch, and the "Search results" heading. Each must have grown by at least its own bound (`minimumGrowth`: the field 2.4, the status line 1.55, the switch 2.5, the heading 1.75, as height at the largest size over height at the default). Each bound lies about halfway between what the sheet measures with every part capped at Accessibility 2 and what it measures as it is (run 43374972739 on a proof branch that capped it, never merged, and run 43066870675), so a cap at Accessibility 2 or any smaller size fails, naming every part that fell short, and the sheet as it is passes; text in a fixed font would not grow at all. Every run prints each part's heights and ratio on `SEARCH-GROWTH` lines of `ios-ui.log`. The sheet's elements come from `openSearchSheet`, `waitForStatus` and `waitForResults`, which moved from `SearchUITests` to `TextMouthUITestCase` for it. It then audits clipped text only at the largest size (Dynamic Type is the measurement's), accepting the title, Back to Book and `scrolledPastTheEdge`. It passed in run 43041108180 (the sheet's text grows), in 58 seconds.
- **The sheet taps retry.** At the largest size the first tap after a launch was seen to do nothing (a Back, an Add to Library, and, in pass 5, the Bookmarks control). `tap(_:until:in:what:)` taps up to three times, 5 seconds apart, until the screen it wants shows. At the top of each round it returns if that screen is already there, so a screen that was slow to come is not tapped past. `LargeTextUITests` and `openReaderSheet` of `ScreenOrderUITests` use it.
- Nothing is pressed but a book's Back, Settings, Add to Library, and Search in Book, and nothing is typed but the one search of the Search test.

### PlaybackUITests
<!-- id: playbackuitests; keys: ; src: TextMouthiOSUITests/PlaybackUITests.swift, TextMouthiOSTests/PhoneControlButtonTests.swift, TextMouthProductionTests/PhoneReaderControlsTests.swift -->

- They press Play, Pause, the skip buttons, and the Sleep Timer's buttons in the reader, on Alice's Adventures in Wonderland (an EPUB, so nothing is played through Apple's players but the app's own speech), and read what VoiceOver would be given. Each starts with `requireSound`, so each skips on this Mac, saying why. XCUITest reads a control's label, value, and type (button), and whether it is enabled; it does not read the hint or the other traits (adjustable, starts a media session), which `PhoneControlButtonTests` and the Mac's `PhoneReaderControlsTests` hold.
- The six tests:
  - `testPlayBecomesPauseAndPauseBecomesPlay`: before, "Play", a button, enabled, with no value; after Play, "Pause" with no value, still there three seconds later (a failed speech would put an alert up or turn it back into Play); after Pause, "Play" with no value, since nothing was moved. Then Play, three skips forward while playing, and Pause leave Book content past where it began; a second Play and Pause leave it at that place or later in the same passage (found inside the first, with white space made alike), never at the book's opening, so a Play that started the book over fails.
  - `testSkippingForwardWhilePlayingMovesTheBookAndKeepsItPlaying`: the sentences are learned first, silently: paused, each of six Skip forward presses puts the sentence at its new place in Play's value, and six presses back return Book content to the opening. Then, playing, six presses forward leave Pause on screen, and after Pause Book content begins at the sixth sentence or later (the first 80 characters tell sentences apart), never at the opening or the first five. The new place is not searched for in the opening passage: that is a short title page, and the place is in a later chapter.
  - `testSkippingBackwardAtTheStartSaysSoAndLeavesTheBookPlaying`: paused at the opening, Skip backward puts words in Play's value ("previous", "start" or "beginning" in them; the spec's are "No previous sentence.") and leaves Book content alone; with the book playing, the same press leaves Pause on screen.
  - `testASleepTimerCountsDownWhileTheBookPlaysAndStopsWhenItPauses`: the 10-minute preset starts the book (Pause), the Sleep Timer reads "M:SS remaining" between 9:00 and 10:00, a later reading is smaller while it plays, and two readings four seconds apart are equal once it is paused.
  - `testAnEndOfBookTimerNamesItsStopAndCancelEndsIt`: "Stop at the end of the book and start playing" starts the book and the control reads "stops at the end of the book"; the sheet then lists Sleep Timer (its title), Reset Timer, Cancel Timer and New Timer, and after Cancel Timer the control reads "Off". The sheet's "Current Timer" heading and its status line are not in the tree once a timer is set, though Reset Timer after them is; a list scrolled to the last timer used would explain the heading but not that, so whether VoiceOver misses them is not settled and needs a device.
  - `testAnEndOfHeadingTimerSetAtTheCoverPlaysOnAndNamesItsStop` (November 11, 2026): at the book's opening, "Stop at the end of this heading and start playing" starts the book (Pause), the Sleep Timer reads "stops at the end of this heading" and not "Off", and Pause is still there three seconds later (`assertHolds`). It passed in run 43041108180 with the fix, in 23 seconds, and fails without it (see the proof, below).
- **End of heading at the cover.** In run 42948545901 the timer set with "Stop at the end of this heading and start playing" was gone at once: the book was not playing and the control read "Off" for the whole minute the test waited. The cause, read from the code on November 10 and fixed in 0.4.6 (the merge 5862bce0): the timer saved the first heading after the cursor, and the cursor is at the silent cover chapter, while Play skips to the first chapter with words, whose own heading was the saved one, so the first refresh found the heading already reached and ended the timer ("Sleep timer expired at the end of the heading"). The timer now takes the heading Play starts in. The Mac's reader shares the code.
- **Proof that the test finds the fault.** A branch with the merge's changes under `TextMouth/ViewModels/` taken out (never merged, sent to `TestBuild` once by hand) was run with this class on GitHub (run 43048443160, November 11, 2026). `testAnEndOfHeadingTimerSetAtTheCoverPlaysOnAndNamesItsStop` failed with the symptom of run 42948545901, "The book did not start playing ... The control reads \"Play\", and the Sleep Timer reads \"Off\"", and the class's other five tests passed.

## In the simulator, sound tests run on GitHub only
<!-- id: simulator-sound-tests-run-github; keys: ; src: TextMouthiOSUITests/TextMouthUITestCase.swift, Scripts/agents/tests/test_run_ios_ui_tests.py -->

The old rule, "never press Play and never type in the simulator", was the orchestrator's, not the user's, and the user withdrew it on November 10, 2026 ("I definitely think those should be tested on the IOS"). The rule now:

- The interface tests press Play and type, as a person does. That makes sound, since the simulator plays through the Mac's speakers and the keyboard clicks, so such a test runs only where nobody listens: on a GitHub runner.
- A test that makes sound runs only when the environment variable `TEXTMOUTH_UI_SOUND` is 1. `Scripts/agents/run-ios-ui-tests.py` is the one place that sets it (as `TEST_RUNNER_TEXTMOUTH_UI_SOUND`, which `xcodebuild` hands to the test runner without the prefix), and it runs only on the runner: anywhere `GITHUB_ACTIONS` is not `true`, it stops at once with exit status 2, before it reads a request, writes a file, or starts a simulator. Never run it on this Mac; to run the interface tests, ask a GitHub run for them. The workflow, the other scripts, and the Mac never set it: `test_run_ios_ui_tests.py` fails if another tracked file names it, if the workflow sets it, or if a test file presses Play or types by hand.
- `TextMouthUITestCase` decides in one place. `requireSound(_:)` skips the test, saying why, unless the variable is 1. The helpers that make sound (`pressPlay`, `pressPause`, `startSleepTimer`, `type`) call it first themselves, so a test that forgot still makes no sound on this Mac. A test that makes sound calls `requireSound` before it launches anything, so a skip is quick.
- On this Mac those tests skip. Do not set the variable in a shell here. Nothing records audio anywhere.
- The unit tests (`TextMouthiOSTests`) make no sound and have no sound variable. They run in the same xcodebuild run as the interface tests, on GitHub; no agent runs a simulator on this Mac.
- A test that needs a book is sent one at launch (`TEXTMOUTH_OPEN_AT_LAUNCH`) and finds Play unpressed.
- Never play Ogg through Apple's frameworks, here or on the runner; the tests use the EPUB `TestData/alice.epub`.
- No test may trap, hang, or use a microphone, and every wait has a limit.
- VoiceOver does not run in the simulator. XCUITest's element queries stand in for it for labels, values, traits, and order, and the audit for missing labels, hit areas, and Dynamic Type. Everything that sounds or needs VoiceOver is checked only on a phone, with the spec's hand-check list.

## Type-checks and tests
<!-- id: type-checks-tests; keys: ; src: TextMouthProductionTests/PhoneSettingsVoicePreviewTests.swift, TextMouthProductionTests/PhoneVoiceModelTests.swift, project.yml, Scripts/agents/run_locked.py -->

- `make typecheck-ios` and `make typecheck-mac` build the app's sources alone, in a package of their own. They compile no test file.
- `make typecheck-tests` compiles the Mac's hosted tests too. It builds the app and `TextMouthProductionTests` (the folder of that name and the files of `TextMouthTests/Sources/Tests` that `project.yml` lists for it) with SwiftPM and `swift build --target TextMouthProductionTests`. It links no test bundle and runs nothing. Run it, once for a batch and after committing, before asking the build train for a build. `make typecheck-tests REF=<commit>` checks that commit from any worktree. It takes the heavy-work lock itself, so never wrap it in `run_locked.py`. A run takes about four minutes when most test files compile again, six from a cold start, and seconds when nothing changed, after the wait for the lock. Its errors read as the train's do (file, line, message), and its summary is in `build/typecheck/results/` of the main checkout.
- `TextMouthiOSUITests` can be type-checked on this Mac without the iOS runtime, because Xcode's iPhone Simulator SDK and its XCTest are enough (`xcrun --sdk iphonesimulator --show-sdk-path`). It touches nothing and builds no app; run it under the heavy-work lock: `python3 -I Scripts/agents/run_locked.py NAME xcrun swiftc -typecheck -sdk $P/SDKs/iPhoneSimulator26.0.sdk -target arm64-apple-ios26.0-simulator -F $P/Library/Frameworks -I $P/usr/lib -swift-version 5 TextMouthiOSUITests/*.swift`, with `P=/Applications/Xcode.app/Contents/Developer/Platforms/iPhoneSimulator.platform/Developer`. It would have found the unterminated string of run 42947183810 in seconds. `make typecheck-ios` does not cover these files, nor `TextMouthiOSTests`: it builds the app's sources alone.
- So, apart from `make typecheck-tests` and that command, a compile error in a test file is found only by a build that builds the tests.
  - For `TextMouthProductionTests`, `make typecheck-tests` finds it before a train does, and the build train finds it otherwise.
  - For `TextMouthiOSTests` and `TextMouthiOSUITests`, that is a simulator build (`build-for-testing`).
- This happened. On November 8, 2026 the iPhone branch's trains of 03:30 and 04:00 each stopped on a compile error in a test, though every type-check had passed: a stand-in that was not on the main actor in `PhoneSettingsVoicePreviewTests`, and a fixture out of scope in `PhoneVoiceModelTests`.
- After changing a test file, run `make typecheck-tests` before requesting a train for it. Do not take a clean `make typecheck-mac` or `make typecheck-ios` as a sign that its tests compile.
