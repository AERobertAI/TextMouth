## Description

**What happens.** In the full Mac suite after the B16, Q12, and B17 merge (November 18, 2026), `MacBrailleTableCheckTests.testFrenchGermanAndSpanishPassAndRoundTrip` failed once at `MacBrailleTableCheckTests.swift:469`: "XCTAssertGreaterThan failed: ("0") is not greater than ("0") - mac:es.tbl". It passed on its second try, under the suite's retry on failure. The same test passed on its first try in the two FMT54 suites that night. The suite log is `build/orchestrator/nov17/suite-smallfixes.log`, line 34360.

**The likely cause.** `MacBrailleTableCheck` takes a table's peak resident memory from the readings that `BrailleTranslator`'s measured run samples while the helper works (`BrailleTranslator.swift`, around lines 201 to 232). Spanish's table is small and loads fast. A run that ends before its first reading measures 0, and the check then records a need of 0 bytes.

**The fix.**
- Take one reading at the end of the run as well, or the helper's own peak from `rusage` when it exits, so that a fast run can't measure 0.
- Decide what a 0 means for the check's verdict: a table the check measured as needing nothing should not set the memory limit (`MacBrailleTableCheck.swift:172`) from it.
- Test a run that ends before the first sample, with a stand-in helper.

**Cause and fix (flakeq15).** The watchdog read the child's memory only inside its loop, after the first wait, and it starts the reaper process first, which takes several milliseconds; a helper that finishes within them (a small table's check, such as Spanish's) got no reading, so its peak was recorded as 0. `WatchedProcess` now reads once the moment the child exists. A peak of 0 means no reading and never sets a limit (`TableNeeds.limits(raising:)` takes the larger of today's limit and twice the need). Tests: `testAHelperThatEndsAtOnceIsStillMeasuredOnce` (failed without the fix on GitHub) and `testAMeasuredNeedOfZeroBytesNeverSetsTheMemoryLimit`; GitHub run 44823357501 ran the class 50 times with no retry, 0 failures.
