## Description

**What happens.** On the iPhone, when braille's engine abandons a call that ran past its time, the sentence names that call's own limit. Near the end of a book's time, that limit is only the time the book had left, so a long translation stuck in its last call is said to have "run longer than 3 seconds". It is the same fault FMT54's review found in FFmpeg's sentence (finding 5), which FMT54 fixed for FFmpeg. In `BrailleTranslator.swift`, around line 947, the abandonment is rethrown unchanged, where the stopped path names `timeAllowed ?? seconds`.

**Why it waits.** No test can reach it safely. A test must let a liblouis call be abandoned while it runs, and liblouis is not thread-safe: train 1117-2249's iPhone run crashed with SIGSEGV in liblouis when such a test's abandoned call ran beside the next test's. The fix (e0bfb1201) was reverted for that reason (1c787ca75).

**The fix.**
- Give braille's tool a stand-in for the liblouis call, a seam like FFmpeg's `openSession`, so that a test can stall a call without any real liblouis call being abandoned.
- Then name the book's whole limit when the time left was what cut the call, as FFmpeg's sentence does, and test it through the seam.
- **A testing rule** for `docs/developer/testing.md`: no test may let a real liblouis call be abandoned.

**Found by** verify-phoneffmpeg (item 4) and phoneffmpeg, November 17 and 18, 2026.
