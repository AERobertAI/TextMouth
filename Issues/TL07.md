## Description

**What happens.** A remote train fails as soon as the Mac loses api.github.com for more than about 45 seconds, though its run goes on, on GitHub, and may succeed.
- `github_run.wait_for_run` asks `gh run view` every 30 seconds.
- `gh_json` tries a failed call 4 times, 15 seconds apart, and then raises `RemoteFailure`.
- The train is marked failed, and nothing is downloaded from the run it watched. Its requests go back in the queue, and after `REMOTE_RETRY_MINUTES` they are pushed and run again from the start.

**Seen twice on November 17, 2026.** Both times the Mac's lid was closed on battery ("Clamshell Sleep" in `pmset -g log`, from 14:25 to 15:00 and from 16:11 to 17:41). `caffeinate` can't hold off that sleep.
- **Train 1117-1406:** it failed with "gh run view failed: error connecting to api.github.com".
- **Train 1117-1555:** run 44174383391 succeeded on every job by 16:35, but its results were never collected. The rerun, 1117-1753, started at 17:53, so the agent waited about 80 minutes more for the same results.

**The fix.**
1. **Keep watching through a lost connection.** In `wait_for_run`, a poll that fails is a missed poll, not the end. The watch goes on until the run's own limit (`RUN_LIMIT_MINUTES`, on `CLOCK`, which doesn't count the Mac's sleep), and the train's log says how long the connection was lost.
2. **Retry the download the same way.** Download the results artifact after a lost connection too.
3. **Collect, don't rerun.** If a train still ends this way, record the run's ID with its pushed commit. The next train then collects that run's results, instead of running the same commit again, when nothing it would push has changed.

**Tests.**
- A fake `gh` that fails for several polls and then says the run completed must end the train with the run's results.
- One that fails past the run's limit is still a `RemoteFailure`.
- A recorded run whose commit still matches is collected, not pushed again.
