## Description

**What happens.** In the 0.5.3 release's remote suite (November 18, 2026, at ad9e1f4b4), `BookManifestEditTests.testAHandEditedTitleSurvivesTheFirstLaunchAndALaterManifestEditWins` failed once on GitHub's Mac runner and passed on its second try, under the suite's retry on failure. The failure, at `BookManifestEditTests.swift:1278`:

> XCTAssertEqual failed: ("Optional("Harbour Pilots, Revised")") is not equal to ("Optional("Harbour Pilots, Second Edition")") - The later manifest edit was not taken

The suite log is `build/orchestrator/nov17/remote-suite-0.5.3.log`, line 37090.

**What the test does.** A book's title is edited by hand, and a first launch keeps it. The test then saves a new manifest with "Harbour Pilots, Second Edition", and a second launch should take it. Once, it didn't.

**The likely cause, to be checked.** The second save follows the first launch's own write of that manifest within a fraction of a second. If the launch decides that a manifest changed by its modification date, or by a fingerprint taken at too coarse a resolution, the second edit can look unchanged. Find what the launch compares, and whether a real edit made that soon after TextMouth wrote the file could be missed in the app too. If it could, it is a bug, not only a flaky test.

**The fix.** Make the change test exact (content, or size and nanosecond date), or make the test's second save unmistakably later, whichever is the real cause. Then run the test many times on GitHub to show it holds.

### 2026-11-20, orchestrator, 13 lines

**Cause, found (flakeq16).** No date was involved. The launch's look compares the manifest with the book, and a session's check reads the bytes whenever the size or the time to the microsecond differs. The later edit was written over. `LibraryViewModel.commitManifestEdit` gave the title and author a take found to `setTitleAndAuthor`. That call queued `settleOwedFields` on `BookManifestEditSessions.shared`'s queue, with those fields counted as owed, and the settle ran after a main-thread turn and the queue's earlier work. It wrote the row's title, as the take had found it, into the manifest wherever the manifest now disagreed. A save made in between was written over, or its title was recorded as owed so that the next look wrote over it, and nothing ever took that save.

**In the test.** The first launch's look takes the edited book's manifest too, since its author (Ilse Varga) is not the row's (Unknown). So a settle is queued on the app's shared sessions, whose queue is not the test editor's. On GitHub it sometimes ran after the test's second save. Three failing logs are still kept: the 0.5.3 suite (line 37090), train 1119-0800 (the failing try took 10.1 s), and the cisuite run of November 10 (7.6 s; a fourth sighting, not listed above). Each shows the first launch's two MANIFEST_EDIT_ADOPTED lines and nothing from the second launch, neither a take nor a refusal; each passing try shows a third. The 0.5.4 check's job log on GitHub keeps only its RETRIED line.

**In the app.** A real edit could be lost the same way. The window runs from a take's read of the manifest to its write-back. At launch the write-back comes only after the looks at every other book, and on the manifest queue it waits behind any earlier work (an Ogg conversion's commit) or a storage hold. A save made in that window lost its title to the earlier one. In an Edit Manifest session the rest of that save was not taken either until the session ended, since TextMouth's own write moved the session's baseline.

**Fix** (flake/q16, 46f463b98). A take gives only the row the manifest's title and author (`setRowTitleAndAuthor`, the row's half that `setTitleAndAuthor` keeps for a metadata editor's save), and nothing is written back. A field already owed stays owed until the next look or retitle writes it, as the owed-field tests say. That also takes the same race out of `testOnlyTheOwedFieldIsKeptWhileTheOtherFollowsTheManifest`, whose check that the title is still owed passed only while the main thread beat the shared queue.

**Proof.** `testASaveMadeWhileTheSaveBeforeItIsTakenIsNotWrittenOver` holds the manifest queues (the app's and the editor's) from a take until a later save is made. Two runs of BookManifestEditTests were sent by hand, each test run N times (`-test-iterations N` in place of the retry):
- Without the fix (the branch with main's LibraryViewModel+ManifestEdits.swift, N = 20, run 44841797810): the new test failed 20 of 20, at both its checks. The hand-edit test failed 4 of 20, each time with "the manifest's title is Harbour Pilots, Revised": the manifest itself had been written back over the test's save. The class gave 956 passes and 24 failures in 980 tries.
- With the fix (the branch as it is, N = 50, run 44843120549): 2,450 of 2,450 tries passed, the hand-edit test and the new one 50 of 50 each.

**Also found, not changed.** A session's check trusts a file whose size and time to the microsecond match its baseline, without reading it; Edit Text's check does the same. On APFS that never hides a save. On a volume with coarse file times (HFS+ 1 s, FAT 2 s), a save of the same size in the same tick as the baseline would be missed until the next save. It is not Q16's cause, and it is left for a follow-up.
