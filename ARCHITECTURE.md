# TextMouth architecture

This document explains how TextMouth is put together and, above all, which part of the app owns each kind of state: who keeps it, who may change it, and how everything else finds out about a change. It describes main as of October 3, 2026. When a change moves the ownership of some state, update its entry here in the same branch.

README.md covers building, testing, the files in the data directory, and keeping the library in the cloud. Paths below are relative to the TextMouth source folder unless they start with the name of another top-level folder, and names in the text are the names of Swift types, functions, and properties.

## The parts of the app

- One SwiftUI application. TextMouthApp (App/TextMouthApp.swift) declares three kinds of window:
  - Library windows (LibraryWindowView, ContentView, and LibraryView). The first opens at launch, and Command-N opens more.
  - Reader windows, one per book, identified by the book's ID (BookReaderWindowView, in the scene whose ID is BookReaderWindowView.windowID). Window restoration is off, so none reopen at launch.
  - The Settings window (SettingsView), with eight tabs.
- App-wide objects, created once by TextMouthApp and given to every window as environment objects:
  - LibraryViewModel: the library in memory, and every operation on it.
  - SettingsViewModel: the global settings, and the config.json mirror.
  - KeyboardShortcutManager: every action's keyboard shortcuts.
  - SoundEffectService: the sounds that playback events play.
  - LibraryWindowRouter.shared: which window takes each app-wide action.
- AppDelegate (App/AppDelegate.swift) starts the router before Finder can hand over a file, owns MenuVisibilityManager, turns off window restoration, asks before quitting with unsaved changes, stops a data-directory move that is copying before it lets TextMouth quit, and ends the session lease at quit.
- Each reader window has its own ReaderViewModel, which has its own SpeechService, AudioPlaybackService, and NowPlayingSession. Readers share SleepTimerService.shared, ReadingStatsService.shared, TextSubstitutionService.shared, ReaderAutoplayRequests.shared, and SpeechRenderCoordinator.shared, and, through ReaderCloudServices, the installed book storage, BookCloudStates.shared, and ReaderWorkingCopies.shared.
- The source folders:
  - App: the entry point, the delegate, the menu commands, the build identity, the process runtime (TextMouthRuntime), and the check made before quitting.
  - Models: value types and small rule tables, such as Book, BookInfo, Library, BookContentIndex, SettingsPolicy, StoredPreference, and the wording helpers.
  - Parsers: one reader per format, each turning a source file into DocumentContent (chapters, headings, and an index), plus shared readers for archives, packages, and text encodings.
  - Services: everything that owns a file, a queue, or a system resource.
  - ViewModels: LibraryViewModel and ReaderViewModel, each split into extensions by topic, plus SettingsViewModel, BookSearchModel, and LibraryBookUpdates.
  - Views: the SwiftUI views of the library, the reader, and settings, plus VoiceOverFocus.swift, which places VoiceOver's focus in new windows and sheets, and ViewBodyCounter.swift, which counts body evaluations for the hosted tests.
- Concurrency: the view models, the window router, the settings mirror, the sleep timer, the statistics, the books' cloud states, the list cache, the live reading positions, and the voice list run on the main actor. Disk work runs on queues that each own their work: serial queues for the library index and for package records (LibraryPersistenceService), for imports (SerialImportQueue), and for logs (LogWriter), and at most two workers for cache updates (TextCacheUpdateQueue). Each import, text extraction, and book analysis on those queues runs through StorageBoundary.perform, which a data-directory move holds back and waits for, so none runs across the move's publication; the move then copies the data directory off the main actor, while every Library window's sheet keeps the library from changing. Rebuild Directory and the folder edits made from the library's sheets hold storage work the same way; a folder edit moves its packages and rewrites their records off the main actor, then publishes the new rows on it, keeping any change made to the library meanwhile (performLibraryTransition). Work that can wait on a drive or the network never runs on the main thread. The list's cloud refreshes and commands call the cloud services from detached tasks, and work that holds its thread for as long as it takes runs on a global dispatch queue (ReaderViewModel.offMain, OffMainWork) rather than on one of Swift's cooperative threads: the reader's requests to the book storage and its reads of a book, the check of a folder chosen for the library, the count of books only in the cloud before a move, a move's copy, and a folder edit's moves. A read that must never download runs inside DatalessFiles.withoutDownloading, which leaves dataless files in the cloud for its own thread only. Other work leaves the main thread too. The look-ahead prepares the speech of a chapter too long to render ahead on a global queue, which ChapterSpeechInputs allows by being values and prepare() by being pure, and the main actor keeps the result only while the chapter's inputs are unchanged. Rendered speech is fed to the engine's player node from RenderedSpeechFeeder's own serial queue, which every call on the node goes through, so a busy main thread never leaves the node without audio, and a completion handler of the node never waits on the feeder. The installed voices are listed on a detached task (VoiceCatalog), launch finds the books its cache batch must rebuild on a utility queue, and Storage settings ask whether the data directory exists off the main thread. Every target builds in the Swift 5 language mode with complete concurrency checking, set once in project.yml, and `make check` fails on any Swift warning; UncheckedConcurrencyPolicyTests requires a comment naming a lock, queue, actor, or thread on the three lines above each `@unchecked Sendable` or `nonisolated(unsafe)` declaration and pins their counts (25 and 13).

## Launch

- TextMouthApp's initializer installs the real cloud services (CloudServices.installSystemServices) before anything else runs: SwiftUI creates LibraryViewModel before applicationWillFinishLaunching, and the library's launch check uses them.
- AppDelegate.applicationWillFinishLaunching starts the router before any window exists, so a book Finder hands over waits for the first Library window instead of opening a second.
- The data directory's first location is decided when anything first asks for it (StorageBoundary.shared): TextMouthPaths.root(for:) names the folder the preferences hold, or the default location. When a custom location is missing but its bookmark leads to a folder holding this library under another path, as after a rename or a remount under another name, that folder is the data directory, and the preferences name it from then on.
- LibraryViewModel's initializer copies a sandboxed release's data on first launch (through DataDirectoryMigrator, keeping the original), starts listening for the data directory's loss, and checks the data directory (checkDataDirectory), reading metadata only. Nothing is created or loaded until the check finds the library: then startLibrary creates the data directory's folders, records the library's identity, removes leftover archive extraction folders, loads the library index (loadLibraryIndex), starts the background work below, and begins the session lease. Otherwise every Library window shows Library Not Available, and the Try Again that first finds the library runs startLibrary.
- Loading repairs the index against the disk (migrateOldBooksIfNeeded): books removed with Remove from Library Only stay out, books whose records took reading checkpoints after the index last did get those positions back (adoptNewerRecordedPositions, for the books the checkpoint journal names), equivalent folder rows merge, stale file paths are fixed, legacy books move into packages, packages that two books shared are separated, misplaced packages move into their folders, packages missing from the index are adopted, and the result is saved. Every check and read of the repair leaves dataless files in the cloud, and nothing is moved, rewritten, adopted, separated, relocated, or taken out on the strength of a check that met a dataless folder or a read that was refused; one MAINTENANCE_SKIPPED_IN_CLOUD line counts the books left as they were. The look for a removal marker, which is almost always absent, stops at the first folder above it that is there and not dataless, the package itself, rather than asking every folder up to the data directory. An unreadable index skips all of this and enters recovery instead (below).
- LibraryViewModel then brings every book's text cache up to date, and after that its statistics, in the background (updateContentCachesAndStatistics), leaving books whose files are in the cloud as they are. The batch finds the books whose caches need work off the main thread (booksNeedingCacheUpdate, on a utility queue), and starts on the main actor once it has them.
- SettingsViewModel's initializer applies config.json, reconciles it with the preferences, and starts ConfigService watching the file. While the data directory is unavailable, ConfigService reads, writes, and watches nothing, and it reconciles the file once the library is back.

## Who owns each kind of state

Each entry names a kind of state, then its owner, who may write it, how others observe it, and the files involved.

### The library index

- The library: every book's row, the folders, and each location's sort.
  - Owner: LibraryViewModel.library, published on the main actor. It is the live copy; library.json is its saved form.
  - Who may write it: LibraryViewModel and its extensions, on the main actor. Each change is followed by save(), which hands a snapshot to LibraryPersistenceService.save(_:). That waits half a second on the service's serial queue, and only the newest snapshot is written, so an older snapshot never lands after a newer one. A reading checkpoint goes through saveReadingCheckpoint(_:of:) instead, which lets its snapshot wait up to five minutes (readingCheckpointDelay), since the book's record holds the checkpoint meanwhile: any ordinary save writes it sooner, and writePendingIndexSoon() brings it forward when a reader closes (unregisterOpenBook) and when a record cannot take its checkpoint, being only in the cloud or failing to be written. Until an index write holds every checkpoint, ReadingCheckpointJournal names the books whose records are ahead in reading-checkpoints.json, noting each before its record is written, and launch's repair gives each book it names its record's newer position and last-opened date (booksWithCheckpointsAhead() and adoptNewerRecordedPositions). flushPendingSave() writes a waiting snapshot before the app quits. Every write replaces library.json atomically, as compact JSON (encodedIndex(_:)).
  - How others observe it: SwiftUI views observe LibraryViewModel. A reader takes a copy of its book when it opens and reports back through LibraryViewModel: updateLiveReadingPosition (live reading positions, below, which change nothing in the library), persistReadingPosition (the row and the package record at once, library.json within five minutes), and updateContentIndex. Every change of library is offered first to LibraryViewModel.listCache (the lists Library windows show, below), then to LibraryViewModel.bookUpdates, which keeps the copies of open readers current (a reader's copy of its book, below). No timer republishes the library: nothing a Library window shows depends on the clock, and a value that ever does should use a TimelineView rather than a tick that redraws every window.
  - Files: Models/Library.swift, ViewModels/LibraryViewModel.swift and its extensions, Services/LibraryPersistenceService.swift, Services/LibraryLoadResult.swift.
- Live reading positions: where readers are in their books between checkpoints, for the rows and the summary bar.
  - Owner: LibraryViewModel.livePositions, a LiveReadingPositions on the main actor, holding one LiveReadingPosition for each book, kept for the session.
  - Who may write it: readers, about once a second while they play, through LibraryViewModel.updateLiveReadingPosition; a book no longer in the library changes nothing. When openBookIDs changes, a book no reader has open drops its entry (keepOnly), its reader having saved its position to the library as it closed.
  - How others observe it: a book's row (BookRow) observes its own book's entry, so a live position redraws that row alone, and the summary bar (TimeRemainingBar) observes the store; the library model publishes nothing. A live position is shown in place of the row's own only while it is the newer (ReadingPosition.lastUpdated), so a checkpoint, or a position another window saved, takes over at once.
  - Files: ViewModels/LiveReadingPositions.swift, ViewModels/LibraryViewModel.swift, ViewModels/LibraryViewModel+BookOperations.swift, Views/Library/LibrarySubviews.swift.
- The lists Library windows show: each location's books in its sort, narrowed by a search, and the book counts of folder trees.
  - Owner: LibraryViewModel.listCache, a LibraryListCache on the main actor, which derives each list once and keeps it, at most LibraryListCache.entryLimit lists, until a change it depends on. It publishes nothing, so a window may derive and store a list while SwiftUI draws.
  - Who may write it: the library itself, which offers every change of library to listCache.libraryDidChange(from:to:) before anything reads it. A change of membership (which books there are, their order in the library, and their folders) or of a field a sort or a search reads (the title, the author, the dates added and last opened, the manual order, and the book's file) drops every list; any other change, such as a word count or a voice setting, keeps every list's order and refreshes only its books' values. A reading checkpoint stamps the book's last-opened date, so it sorts the lists again. Folder trees are counted in one pass whenever the lists are dropped, and the sizes a File Size sort reads are measured once per book, until its file changes.
  - How others observe it: a Library window reads its list through displayedBooks(at:matching:) and bookCount(inFolderTree:) as often as it draws: the first read after the lists were dropped derives its list again, and the first after any other change refreshes the list's books.
  - Files: ViewModels/LibraryListCache.swift, ViewModels/LibraryViewModel+FolderManagement.swift, Models/LibraryBookSorter.swift, Models/LibrarySortState.swift.
- Index-write suspension: what protects an index that cannot be read.
  - Owner: LibraryPersistenceService. The flag lives on its save queue, beside the waiting snapshot.
  - Who may write it: load() suspends index writes when library.json exists but cannot be read, after LibraryIndexQuarantine has preserved its bytes as library.json.unreadable- followed by the date and time. Only resumeIndexWrites() (Try Again, once the index reads) and replaceUnreadableIndex(with:) (Rebuild Library Index, which first preserves whatever is there) end it. LibraryViewModel+IndexRecovery drives both.
  - How others observe it: LibraryViewModel.indexRecovery is set while recovering, and the Library window shows the recovery banner and its Recovery Options…. Snapshots taken meanwhile are dropped, never kept for later. areIndexWritesSuspended makes data-directory moves refuse. Package records are still written, so reading positions are not lost.
  - Files: Services/LibraryPersistenceService.swift, Services/LibraryIndexQuarantine.swift, ViewModels/LibraryViewModel+IndexRecovery.swift, Views/Library/LibraryIndexRecoveryViews.swift.
- Retirement markers: books removed with Remove from Library Only.
  - Owner: the marker file in the package, removedFromLibrary.json (RemovedFromLibraryMarker), together with LibraryPersistenceService's set of retired packages on its metadata queue.
  - Who may write it: LibraryPersistenceService.retirePackage(of:) writes the marker first. Only once it is on disk does it cancel the writes queued for the book, remember the package, and delete bookInfo.json, a courtesy to older versions of TextMouth. reinstatePackage(of:) deletes the marker when the package is deliberately taken back, by importing it again or adopting it.
  - How others observe it: every package record write checks the set and drops writes into a retired package; orphan adoption skips a package whose marker names its record's book; launch removes retired books from an index saved before their removal.
  - Files: Models/RemovedFromLibraryMarker.swift, Services/LibraryPersistenceService.swift, Services/FileImportService.swift, Services/FileImportService+Packages.swift.

### Package records

- bookInfo.json and contentIndex.json: each package's record of its book (BookInfo), in two files. bookInfo.json holds the metadata, the reading state, and the bookmarks, about a kilobyte, pretty-printed with sorted keys; contentIndex.json, beside it, holds the content index alone, compact with sorted keys, since it can run to hundreds of kilobytes and changes only when the book is imported or analyzed.
  - Owner: LibraryPersistenceService's metadata queue, for every save the running library makes. The record is built from a Book by Book.bookInfo(replacing:contentIndex:revisionFloor:).
  - Who may write it: saveBookInfo(for:) and saveBookInfo(for:contentIndex:), which hold each book's newest snapshot for half a second and write only it; saveContentAnalysis (below); and flushPendingSave(). A save of a book's state writes over the package's record (BookInfo.saveRecord(to:)): a record carrying an index writes contentIndex.json first, so bookInfo.json never names an index that is not on disk yet, and one without leaves contentIndex.json as it is, so a reading checkpoint writes about a kilobyte. The record such a save replaces is read as a StoredBookRecord, bookInfo.json and whether the package keeps an index, never reading contentIndex.json. A package written whole, by an import, a data-directory move, or a repair that separates a shared package, replaces both files (BookInfo.save(to:)), removing contentIndex.json when the record has no index; an import writes its new package's record so and reads it back (FileImportService.writeVerifiedRecord). Folder moves and migrations write records directly with Book.saveBookInfoThrowing, under the same revision rules but outside the queue's order. A record that is only in the cloud, or whose package or removal marker is, is neither read nor written by the queue, since reading it would download it: the book's saves go to library.json alone until the record is on this Mac again, with one BOOK_RECORD_IN_CLOUD line, and an analysis result for it is dropped.
  - How others observe it: BookInfo.load(from:) reads bookInfo.json with the index from contentIndex.json. An index an older version kept inside bookInfo.json wins, and the next save moves it into its own file, while an older version reading a record written since finds no index and builds one once. A missing or damaged contentIndex.json leaves the record without an index, which the book's next load builds afresh, and a read refused because either file is only in the cloud is passed up rather than downloading it. Content analysis reads the saved index and fingerprints from the record (Book.storedBookInfo()), and saveContentAnalysis reads it back as a Book (Book(record:filePath:folderPath:tmbDirectoryName:)) to merge an analysis into. Orphan adoption, which also builds the provisional library while the index cannot be read, and importing a .tmb package (FileImportService.bookFromPackageInfo) rebuild library rows from records with that initializer too.
  - Files: Models/BookInfo.swift, Models/Book.swift, Services/LibraryPersistenceService.swift, Services/TextMouthPaths.swift.
- Revisions.
  - Owner: BookState.revision, in each record.
  - Who may write it: every write stores one more than the record it replaces, and never less than one more than the highest revision this process has written for the book, so a book's revisions only rise, across restarts too.
  - How others observe it: no decision rests on a revision. Whether an analysis still applies is decided by the book's content (below).
  - Files: Models/BookInfo.swift, Models/Book.swift, Services/LibraryPersistenceService.swift.
- Analysis-owned fields.
  - Owner: the content analysis. Book.ContentAnalysisFields (the word and character counts, the audio duration, the content index version, the cache format version, and the text cache fingerprint) travel together with the content index.
  - Who may write it: LibraryPersistenceService.saveContentAnalysis merges a finished analysis into the book's latest durable state, on the metadata queue: the snapshot still waiting there, or else the record on disk. Only the analysis fields and the index change. A result is dropped, with one CONTENT_ANALYSIS_DROPPED log line, when that state describes other content: another MD5 hash, format, or file path, or another book's record. A save that carries no index keeps the stored index and its fields, so neither kind of write undoes the other. The reader commits a fresh index of its own through LibraryViewModel.updateContentIndex.
  - How others observe it: a library row takes the committed fields and keeps its own reading state, settings, and metadata. The text cache batch and the statistics pass hand each finished book's fields to LibraryViewModel.analysisSummaries (ContentAnalysisSummaryBuffer), which gives the rows all that arrived in one change of library and one save, at most half a second after the first of them (flushInterval), when a pass ends, and when TextMouth quits; a summary a crash loses is recovered from the book's record by the next launch's batch. The batch's progress is an object of its own, LibraryViewModel.textExtraction (TextExtractionProgress), which only the Library windows' overlay and Storage settings observe (TextExtractionObserver), so a finished book redraws only them.
  - Files: Models/Book.swift, Services/LibraryPersistenceService.swift, ViewModels/LibraryViewModel+BookOperations.swift, ViewModels/LibraryViewModel+Migration.swift, ViewModels/ContentAnalysisSummaryBuffer.swift, ViewModels/TextExtractionProgress.swift.

### Text caches and content indexes

- content.md: each text book's text cache, its text as Markdown.
  - Owner: MarkdownCacheService. The format's version is MarkdownCacheService.currentCacheVersion ("3.0.7"), and a book whose recorded cacheFormatVersion is older is extracted again.
  - Who may write it: MarkdownCacheService alone, which writes a new cache only after extraction succeeds and replaces the old one atomically. generateCacheContent runs inside BookContentAnalysisService.load: when an import reads its new book, when a reader opens a book whose cache is missing or outdated, and when a stale cache is rebuilt. generateCacheAnalyzeAndStamp runs for startup maintenance (extractMissingContentCaches, through TextCacheUpdateQueue, which runs ordinary EPUBs on two utility workers and everything else one at a time), for Redo Text Extraction in Storage settings, and for the legacy migration. Maintenance leaves a book whose files are in the cloud as it is (maintenance in a cloud library, below). The extraction behind it parses each EPUB document once: EPUBParser converts a document to Markdown from the DOM its contents scan parsed, and again only when a contents page later in the book names a new destination in it, and asks whether an element is hidden only in markup that holds the word (PublicationSemantics.mayCarryHiddenAttribute(_:)). HTMLToMarkdownConverter wraps emphasis and links in time that grows with what they wrap, not with what was converted before them.
  - How others observe it: BookContentAnalysisService.load reads it and parses it into DocumentContent, splitting it into chapters over Substrings of the cache, one copy per chapter (MarkdownCacheService.splitChapters(_:)).
  - Files: Services/MarkdownCacheService.swift, Services/TextCacheUpdateQueue.swift, Services/BookContentAnalysisService.swift, ViewModels/LibraryViewModel+Migration.swift, Parsers/EPUBParser.swift, Parsers/EPUBParser+Navigation.swift, Parsers/PublicationSemantics.swift, Parsers/HTMLToMarkdownConverter.swift.
- The content index (BookContentIndex): chapter starts and lengths, word counts, headings with their offsets, totals, and, for audiobooks, the media layout and timing, with every clip of a chapter that plays several.
  - Owner: the package record, as its contentIndex.json (BookInfo.contentIndex), beside bookInfo.json. Its version is BookContentIndex.currentVersion ("1.0.0"). library.json keeps only the totals and contentIndexVersion, so launch never decodes every heading in the library.
  - Who may write it: BookContentAnalysisService builds it (BookContentIndex.build) from parsed content, its word counts counted as the runs of Characters that are not whitespace (Chapter.wordCount(of:), which reads a Character whole only around non-ASCII bytes and makes no substring per word), and it is saved only through LibraryPersistenceService (saveContentAnalysis or saveBookInfo(for:contentIndex:)).
  - How others observe it: BookContentAnalysisService.load uses a saved index only when it passes validationFailure(for:audioBaseURL:) and, for a text book, alignmentFailure(with:countingWords:) against the parsed chapters. One that fails is logged as CONTENT_INDEX_REJECTED and replaced by a fresh index. The reader takes headings, chapter offsets, and totals from the index inside its DocumentContent.
  - Which version to change: a change to source extraction changes MarkdownCacheService.currentCacheVersion. A change only to how the reading text or the index is derived changes BookContentIndex.currentVersion instead, so existing Markdown is indexed again without converting every source. Reading Markdown tables a row at a time (each row a paragraph, its cells one space apart, the table set apart from the text around it, as HTMLReadingText reads an HTML table) changed neither version: content.md is unchanged, and the change only adds breaks and spaces, so the saved index of every book it affects, a DOCX or Markdown book holding a Markdown table, no longer lines up with its reading text, fails the alignment check once (CONTENT_INDEX_REJECTED), and is rebuilt from the cache.
  - What guards the output: TextPipelineGoldenTests hold the digests of what the text pipeline produced on main before the performance work of October 3, for TestData's books (its two untracked DAISY audio ZIPs only where a checkout has them), synthetic books, and generated EPUBs: every content.md an import writes, the reading each book opens to (titles, text, headings, and word counts), and the converters' own output. A change meant to keep the output must leave them passing. A deliberate change of output, which changes one of the versions above, records the new digests, which each failure names, once the new output has been checked. TextPipelineBefore (TextMouthProductionTests/TextPipelineFixtures.swift) keeps the code each change replaced, for these tests and the benchmarks to compare with.
  - Files: Models/BookContentIndex.swift, Models/DocumentContent.swift, Services/BookContentAnalysisService.swift, TextMouthProductionTests/TextPipelineGoldenTests.swift, TextMouthProductionTests/TextPipelineFixtures.swift.
- Text cache fingerprints (TextCacheFingerprint): for the source and for content.md, the size, the modification time, and the MD5 digest, as they were when the cache was written. Times are kept in nanoseconds but compared to the microsecond (FileStamp.hasSameModificationTime(as:)), since a sync service can give a file back with its time moved by a fraction of a microsecond.
  - Owner: the package record (state.textCacheFingerprint, also copied into the index), mirrored on the library row.
  - Who may write it: MarkdownCacheService records them when it writes a cache. BookContentAnalysisService fingerprints a current cache written before fingerprints existed, once, the first time the cache passes every check; that result is saved by the usual save.
  - How others observe it: BookContentAnalysisService.loadExistingCache compares the files' sizes and dates with the record before it trusts the cache or its index, and reads a file for its digest only when the size is unchanged but the date is not. A changed file is logged as CACHE_STALE and the cache is rebuilt from the source. Startup maintenance compares the sizes the library row recorded with the files, two stat calls a book, to find stale caches without reading anything, and completedTextCacheIndex checks a package's record when recovering an interrupted batch. A dataless file, whose content is only in the cloud, is never judged by the size and date it reports, since an evicted iCloud Drive file can report 0 bytes, and never read for its digest (FileStampComparison.dataless).
  - Files: Models/TextCacheFingerprint.swift, Services/BookContentAnalysisService.swift, Services/MarkdownCacheService.swift, ViewModels/LibraryViewModel+Migration.swift.

### The data directory

- Its location, and moving it.
  - Owner: StorageBoundary.shared, which holds the current StorageGeneration, the data directory's root numbered by the moves this process has published, and the earlier ones. TextMouthPaths.root is the current generation's root: at launch the folder TextMouthPaths.root(for:) names (~/.TextMouth, or the folder the textMouthDataDirectory preference names, which a test host ignores), and after a move the new location. It changes only when a move publishes its copy, never because the preference changed.
  - Who may write it: a published move, and a check whose bookmark finds the library under another path (its availability, below). TextMouthPaths.moveDataDirectory(to:library:) changes the preference, the current generation, and the library only once the copy is published, and publishes the generation between the persistence queues' writes (LibraryPersistenceService.betweenWrites), so no write resolves its file under the old root and writes it afterwards. Change Location's Move Library Here and Reset to Default in Storage settings, and a changed dataDirectoryPath in config.json, reach the move in LibraryViewModel+Migration, which refuses while the index cannot be read or the data directory is unavailable, while any book is open (openBooksRefusal, naming the books), and while any book inside the data directory has files only in the cloud, which copying would download (countBooksOnlyInCloud, through MaintenanceFileAccess.itemInCloud).
    - Choosing: a folder chosen in Storage settings (StorageSettingsView.makeLibraryFolderPanel, a chooser that shows hidden folders and can make one) is judged off the main thread, from metadata alone, by StorageDestinationAssessment: a move for a missing or empty folder, Use This Library for one holding a library (an identity marker, or library.json beside a Library folder), the library in use, a new library in the default location while the library is unavailable, or a refusal with its reason. StorageChoice and StorageWording word the confirmation or the status line.
    - Holding: withStorageWorkHeld(moving:waiting:_:) holds new storage work back (StorageBoundary.holdWork), waits for the import, text extraction, and book analysis under way (StorageWorkHold.waitForWorkUnderWay), flushes the queued saves and logs, runs the move, and then lets the held work go on under the new generation. Work that captured paths before the publication moves them under the new root first (rebasedToCurrent and rebaseToCurrent), so nothing is written under the old one. Rebuild Directory holds storage work the same way, with no move, while it relocates and adopts packages, so an import that has published its package but not yet added its book finishes first and is never adopted as an orphan too; Storage settings show what the rebuild waits for. So do the folder edits made from the library's sheets (performLibraryTransition: moving books to a folder, and moving, renaming, or deleting a folder while keeping its contents), which then move their packages and rewrite their records off the main actor (OffMainWork.runThrowing), VoiceOver hearing what they wait for. Only one hold is in place at a time: while one is, a folder edit is refused with LibraryTransitionError.storageBusy, and a move or a rebuild with DataDirectoryMigrationError.moveInProgress.
    - Copying: copyAndPublish runs TextMouthPaths.moveDataDirectory on a background queue (OffMainWork) with the task-local DataDirectoryMigrator.copyObserver bound, which hears each DataDirectoryCopyProgress and answers Cancel. DataDirectoryMigrator takes each location as the real folder its links lead to (DataDirectoryLocation): a data directory that is a link is copied from its folder, and a new location that is a link to an empty folder receives the data in that folder, the link staying as it is. Before copying, it refuses overlapping real folders, naming both, a link that leads nowhere, a file at the new location, and a folder that is not empty. It copies into a hidden staging folder (.TextMouth-migration- followed by a UUID) beside the new location's real folder, one item at a time in the order DataDirectoryCopyPlan gives: each package whole, which clones it on one APFS volume, the books first and the small files at the top last, and each folder it makes given its original's metadata with copyfile. Cancel stops the copy between items, or after the last, with DataDirectoryMigrationError.cancelled, and the staged copy is deleted. The migrator points the copy's package records and library.json at the new location and checks them, then looks again: the name must still lead to the same folder, and that folder must still be empty or missing. It removes nothing but an empty folder, with rmdir, which the kernel refuses once anything is inside, and publishes the copy with one rename (moveItem, which never replaces an item). Anything that arrives meanwhile stops the move: the staged copy is deleted, whatever arrived stays, and the data directory in use and its setting stay as they were. The library is taken once the wait is over, and nothing should change it during the copy; a change made anyway is kept, its paths rebased.
    - Use This Library (useLibraryReturningOutcome(at:relaunching:)) moves nothing. It writes pending saves, refuses while changes can't be saved unless the library is unavailable, records the folder for the next launch with TextMouthPaths.setCustomRoot (nil for the default location), and has TextMouthRelauncher open a new instance of TextMouth and quit this one. A process hosting tests never opens again.

### Cloud state

CLOUD-STORAGE-RESEARCH-2026-10-03.md and CLOUD-STORAGE-PLAN-2026-10-03.md, at the repository's root, explain the design, and CLOUD-STORAGE-MANUAL-TESTS-2026-10-03.md says what real drives have verified and what remains to check by hand.

- Where the library lives, and each book's cloud state.
  - Owner: nothing stores either. Both are read fresh from file-system metadata, with downloading switched off, by the two services CloudServices holds. The contract (Models/CloudStorageContract.swift) defines what they answer with (StorageLocation, CloudItemStatus, BookPackage, BookDownloadProgress, BookCloudState, and BookCloudError) and the words each state and failure is shown and spoken in. Until TextMouthApp installs the services, LocalItemStatusProvider and LocalBookStorage treat every library as local; tests install fakes (TextMouthProductionTests/CloudTestDoubles.swift) and put the previous services back.
    - UbiquitousItemStatusProvider reads single items, files and folders: Foundation's ubiquitous-item keys and the file system's dataless flag, which overrules a key that disagrees, and, from the same read, whether the item carries sync flags of its own (SyncFlagReporting.flaggedStatus(of:), a FlaggedItemStatus). It tells where a folder lives from its path (iCloud Drive's Mobile Documents, or a File Provider drive in CloudStorage, named for its service), from iCloud Drive managing it elsewhere, as it does Desktop and Documents, or from its volume, and it asks the sync service to download a file or remove its local copy (FileManager's startDownloadingUbiquitousItem and evictUbiquitousItem).
    - BookCloudStorageService reads whole books: each look at a package lists it and reads the state of each file and of the package folder itself (a Survey), and decides once which items the sync service syncs (Survey.packageItem). The package is the one item when it carries sync flags and none of its listed files does, as on iCloud Drive, whose files inside a package carry none and are refused, as items that don't exist, when a download or a removal is asked for one of them; otherwise each file is, as on Google Drive and Dropbox, whose files carry flags of their own (as their package folders do too). For a package synced as one item, the book's state comes from the package's flags, Downloading while the sync service fetches it whole; the refusal of a book with changes not uploaded reads the package's upload flag; a download asks for the package and ends on its download error; and a removal evicts it. Nothing inside such a package can be looked up while it is evicted without downloading the whole package, so a check of a file inside a package must run with downloading off; Book Info's check of whether a book's file is only in the cloud (LibraryBookInfoReader) still runs with downloading allowed on main (board finding #624).
    - It downloads by asking the sync service for every missing item and checking every half second until all are here, failing at once while this Mac is offline (NetworkReachability), when an item reports a download error, or when the package disappears, and after a minute in which nothing arrives or downloads. Meanwhile it listens, through PublishedFileProgress (Progress.addSubscriber), for the progress the sync service publishes for the package as a whole, as iCloud Drive publishes it for a package it syncs whole, and for each file still to come, as Google Drive and Dropbox publish it. The listener hands on only a download of the item it listens to (isDownload(_:of:)): an upload, or the progress the system also hands a folder's listener for each item inside the folder, is not, which it tells from the operation and the URL the published progress carries in its user info, since the proxy's own properties can still read nil then. The parts it hears fold into BookDownloadProgress (completedBytes by size, partialFiles by files), in whole percent per file, never going back, forgotten once the file is here, and a growing part keeps a stall away.
    - It removes downloads, refusing while changes wait to upload, and reporting a removal the sync service refuses as BookCloudError.removalFailed.
  - Who may write it: BookCloudStates.shared, on the main actor, records what the library list and the readers learn: where the library lives, and each book's latest state, a download's progress included. LibraryCloudRefresher.shared refreshes it while a Library window is visible: when one appears, when the app becomes active, when a book is added, moved, or removed, and on the cadence LibraryCloudRefreshCadence gives, every minute, or every 2 seconds while any book downloads. Those 2-second refreshes read only the books recorded as downloading, and every thirtieth reads every book, so the rest of the list is still read once a minute (LibraryCloudRefreshScope); every refresh an event asks for reads every book. Refreshes never overlap, and each reads off the main thread: where the library lives, once (libraryLocation(), then state(of:in:) for each package), stopping there for a library outside a cloud location. BookCloudStates.refresh records the results in one assignment, publishing nothing when nothing changed. A download TextMouth runs is bracketed by beginDownload and endDownload, and refreshes leave that book's state to it meanwhile. In a process hosting tests the shared refresher never refreshes.
  - How others observe it: every Library window observes BookCloudStates.shared. Only in a cloud location do its rows show and speak each book's note (BookCloudNote) and does TimeRemainingBar count the books in the cloud; elsewhere the list is as it was.
  - Files: Models/CloudStorageContract.swift, Services/UbiquitousItemStatusProvider.swift, Services/BookCloudStorageService.swift, Services/PublishedFileProgress.swift, Services/NetworkReachability.swift, ViewModels/LibraryViewModel+Cloud.swift, Views/Library/BookCloudNote.swift, Views/Library/LibrarySubviews.swift.
- The list's cloud commands.
  - Owner: LibraryCloudCommands.shared, which runs Download Now, Remove Download, and Show in Finder. LibraryCloudCommand.commands(for:isSelection:states:) decides which a book or a selection offers, from the recorded states.
  - Who may write it: a book row's context menu, and its VoiceOver actions, which offer the same commands under the same names. Download Now downloads one book at a time, recording each one's progress and how it ended. Remove Download refuses a book open in a reader without asking the storage, the storage refuses one with changes not uploaded, and a second request for a book under way does nothing.
  - How others observe it: BookCloudStates.shared shows each download in every window. VoiceOverAnnouncer announces each command's start and one summary from the window that asked, which also shows a removal's refusal in an alert (LibraryCloudRefusal). LibraryCloudWording words every title and announcement. Book Info reads a book's metadata off the main thread through LibraryBookInfoReader and never downloads: a book only in the cloud shows the metadata the library keeps, and writing such an EPUB's file is refused.
  - Files: ViewModels/LibraryViewModel+Cloud.swift, Models/LibraryCloudWording.swift, Views/Library/LibraryView.swift, Views/Library/LibrarySubviews.swift, Views/Library/LibraryBookInfoLoader.swift.
- Maintenance in a cloud library.
  - Owner: MaintenanceFileAccess, through which the startup repair, the text cache batch, Redo Text Extraction, and the statistics pass ask whether a book's files are in the cloud, and read them: live in the app, and a fake in hosted tests, which cannot make real dataless files.
  - Who may write it: each pass checks, before it reads a book, that none of the files it will read is in the cloud (fileInCloud(of:reading:), with the MaintainedFiles it reads), reads with dataless files left in the cloud, and checks again before it saves, so nothing read from a file that went to the cloud meanwhile is committed. presence(of:) answers present, absent, or in the cloud, and only an absent file counts as missing. Each pass counts the books it left in its CloudSkips.
  - How others observe it: a pass that skipped any book writes one MAINTENANCE_SKIPPED_IN_CLOUD line, and Redo Text Extraction also says how many in Storage settings' status line (textReextractionOutcome(skippedInCloud:)). A skipped book is caught up the next time its files are on this Mac, and a reader that downloads a book rebuilds its outdated cache as it loads.
  - Files: Services/MaintenanceFileAccess.swift, ViewModels/LibraryViewModel+Migration.swift, Services/FileImportService.swift, Services/TextCacheUpdateQueue.swift, Services/BookContentAnalysisService.swift, Models/TextCacheFingerprint.swift.

  - Owner: ConfigService.shared, on the main actor. Its config property holds the file's values. While TextMouth runs, the preferences store is the source of truth and config.json follows it; at launch, the file is applied first, because it can change while TextMouth is closed.
  - Who may write it: SettingsViewModel, after each settings change (syncToConfig) and when reconciling at launch, and the Storage settings for the three choices only the file holds. A change updates ConfigService.config at once, and scheduleSave() writes the file once changes pause for 250 ms (defaultSaveDelay), so a slider dragged through its steps writes it once; flushScheduledSave() writes a waiting save when TextMouth quits (UnsavedChangesTermination) and before the data directory moves, and in the hosted tests as each test ends (ConfigSaveFlush). ### The reader

- A reader's state: its content, cursor (chapter and character offset), headings, bookmarks, playback flags, and errors.
  - Owner: one ReaderViewModel per reader window, on the main actor, created by BookReaderWindowView with a copy of the library's Book.
  - Who may write it: the reader itself, in its extensions: Playback, Navigation, Bookmarks, Jump, VoiceAndSpeed, WhereAmI, LibraryUpdates, and CloudDownload.
  - How others observe it: ReaderView and its subviews observe the reader, refreshed at most every 0.12 seconds during playback. The Headings, Voice, and Bookmarks sheets observe a ReaderSnapshot of what they show instead, which reads the reader on the main queue's turn after each change and republishes only a value that differs, and, as SheetOverOneReader views, compare equal while they show the same reader, so a playing reader's publishes redraw none of them; when playback crosses into another heading, two of the Headings sheet's rows redraw. The library sees the cursor through LibraryViewModel: the live position about once a second (updateLiveReadingPosition, into live reading positions), and a durable checkpoint (persistReadingPosition) every 30 seconds of active playback (PlaybackCheckpointPolicy) and whenever the reader pauses, stops, closes, finishes a chapter, or navigates.

- A reader's copy of its book.

Its library fields (Book.LibraryFields: where the book's files are, its editable metadata, and the content analysis fields) follow the library; the rest (the position, bookmarks, voice, speed, and other per-book settings) is the reader's own, and the reader writes each change of it through to the library.

A package's move on disk is bracketed: commitLibraryTransition and performLibraryTransition, and a folder rename that only respells the folder, call packagesWillMove before anything moves and packagesDidMove once the library holds the new rows or the move has been put back.

ChapterSpeechInputs.prepare() is pure, so the look-ahead prepares a chapter longer than SpeechRenderCoordinator.maximumTextLength off the main actor, never twice at once, and chooses again once it is ready; speech whose inputs changed meanwhile is not kept. Play's own chapter is prepared at once when nothing is kept for it. A closed reader empties the cache as close() stops it, and keeps nothing a background preparation finishes afterwards.
  - How others observe it: Play, each chapter's start, the look-ahead, and refreshLookAhead() read it, so a chapter is prepared once for as long as its inputs stay the same, and a speed or pitch step prepares nothing.
  - Files: ViewModels/ChapterSpeechCache.swift, ViewModels/ReaderViewModel+Playback.swift, ViewModels/ReaderViewModel.swift.
- The look-ahead and its render signature.
  - Owner: ReaderViewModel.lookAhead: the next speakable chapter's index, the SpeechRenderSignature its render was asked for (a hash and length of the exact spoken text, and the voice), and the AudioEngineService that holds the audio.
  - Who may write it: preRenderNextChapter(), after each chapter starts; refreshLookAhead(), whenever the voice, the substitution rules or their switch, the repeated-symbol settings, the punctuation pause level, or the skipped sections change (speed and pitch do not count, because they are applied as the audio plays, so applyLocalSpeechOverrides, which every playing reader runs at each step of a global setting, refreshes it only when the voice in effect is not the one the look-ahead renders in); and discardLookAhead(). The look-ahead carries its chapter's speech to that chapter's start (ChapterSpeechCache.lookAheadSpeech), so the chapter's end prepares nothing. Renders wait their turn on SpeechRenderCoordinator.shared, which never lets two calls of AVSpeechSynthesizer.write() overlap.
  - How others observe it: at a chapter's end, takeLookAheadEngine(for:) hands over the engine only when it holds finished audio whose renderedSignature equals the signature of the chapter's speech prepared now. Otherwise the chapter starts from its current text.
  - Files: ViewModels/ReaderViewModel+Playback.swift, ViewModels/ReaderViewModel+VoiceAndSpeed.swift, ViewModels/ChapterSpeechCache.swift, Services/AudioEngineService.swift, Services/SpeechService.swift.
- Autoplay requests: Continue to Next Book.
  - Owner: ReaderAutoplayRequests.shared: at most one request per book, usable for 30 seconds, claimed at most once.
  - Who may write it: a reader whose book ends with Continue to Next Book finds the next book with LibraryViewModel.nextBookInFolder(after:), which follows the folder's manual order as the list shows it (ManualBookOrder.orderedBooks), announces it, leaves a request for it, and posts continueToNextBook. LibraryWindowRouter then opens that book's reader, or brings it forward.
  - How others observe it: the next book's reader claims the request when it finishes loading, or at once when it was already open and loaded, and starts playing. A reader that cannot load its book discards the request.
  - Files: Services/ReaderAutoplayRequests.swift, ViewModels/ReaderViewModel+Playback.swift, ViewModels/LibraryViewModel+SortAndOrder.swift, Services/LibraryWindowRouter.swift.

### Media playback

- Speech, for text books.
  - Owner: each reader's SpeechService. speak() starts the text at once with AVSpeechSynthesizer.speak(), the direct mode, and, for a text of at most SpeechRenderCoordinator.maximumTextLength UTF-16 units, renders the same text in the background into an AudioEngineService (AVAudioEngine with a time-pitch unit, for instant seeking and speed changes). The rendered audio takes over only at a natural break: a seek, a pause and resume, a sleep timer's fade, or the next chapter through the look-ahead. Speech never hands over from direct mode to rendered audio while it runs uninterrupted, because the synthesizer's word callbacks run ahead of the sound by an amount that cannot be known.
    - Direct speech starts with a chunk of at most SpeechService.directModeFirstChunkSize (1,000) UTF-16 units, since the synthesizer reads a whole utterance before its first word, and hands the synthesizer each later chunk of at most directModeChunkSize (5,000) as the one before it starts (queueNextDirectChunk()), so speech goes on after the synthesizer's own pause without waiting for the main thread. A queued chunk becomes the one speaking when the one before it ends or when it starts, whichever the main queue hears first.
    - The engine is made the first time speech needs one, for its first render or the first chapter it plays from audio rendered ahead (SpeechService.audioEngine; hasAudioEngine asks without making one), so an audiobook's reader never makes one. releaseSpeech() stops and lets go of the text and the rendered audio without making an engine, for a reader that closes, and restoreEngineVolume() restores only an engine that exists.
    - Rendered audio is a RenderedSpeechAudio: the synthesizer's pieces converted to 16-bit samples as they arrive, in blocks of 128 KB, then the silence padding every render ends with. It is immutable, so the look-ahead's engine hands it to the speech service's. A play converts back only what it schedules: RenderedSpeechFeeder schedules a few slices on the player node at once, and fills and schedules the next each time the node reports one consumed, on a serial queue of its own, so a busy main thread never leaves the node without audio; a seek schedules from the slice that holds the cursor, copying nothing else.
    - The voice is loaded ahead of the first Play: SpeechRenderCoordinator.warmUp(_:) renders one word with it and drops the audio (VoiceWarmUp), once per voice in a session, on the render queue like any render, giving up its turn after 30 seconds. A text book's reader asks when it opens and when its voice changes (ReaderViewModel.warmUpVoice()).
  - Who may write it: the reader, through speak, pause, resume, seek, and stop, and releaseSpeech() as it closes.
  - How others observe it: the reader sets onWordSpoken, which moves its cursor through the offset map, and, for each play, onUtteranceFinished (the playback generation, above), and mirrors whether speech is playing or paused and its speed. Every utterance a synthesizer callback reports (a word, a start, a pause, a continue, a finish, or a cancel) is held until the callback is handled on the main queue (ReportedUtterance), so a new utterance made at a reused address can never take that callback for its own; there the service reads the synthesizer's state from its own synthesizer, never the callback's. Switches between the modes are logged in textmouth_transition.log.
  - Files: Services/SpeechService.swift, Services/AudioEngineService.swift, ViewModels/ReaderViewModel+VoiceAndSpeed.swift.
- The installed voices.
  - Owner: VoiceCatalog.shared, on the main actor: the voices and their languages. The system keeps no list, and each AVSpeechSynthesisVoice.speechVoices() call enumerates every installed voice afresh, so the catalog lists them off the main thread.
  - Who may write it: loadIfNeeded(), which the first Library window, the Settings window, and the reader's voice sheet call as they appear, lists the voices once; listNow() lists them at once, on the main thread, only at the very first launch, when SettingsViewModel must choose a default voice; and reload() lists them again on AVSpeechSynthesizer.availableVoicesDidChangeNotification, as when a voice finishes downloading.
  - How others observe it: SettingsViewModel offers the list for the chosen language each time the catalog lists (observeVoiceCatalog, through didList), and the reader's voice sheet observes the catalog; neither lists voices itself.
  - Files: Services/VoiceCatalog.swift, ViewModels/SettingsViewModel.swift, Views/Reader/ReaderView.swift, Views/Settings/SettingsView.swift, App/TextMouthApp.swift.
- Audiobook playback, and its failures.
  - Owner: each reader's AudioPlaybackService, which plays files with an AVQueuePlayer at a speed held to the steps AudioSpeed.normalized(_:) allows. setFileAfterCurrent(_:) names the file that plays after the loaded one, so that at the loaded file's end the player rolls straight on into it rather than starting a new player; the name is forgotten on any load, clip end, stop, or failure, and never queued during a clip chain. A file is to be named only when it certainly plays next: never at a book's last chapter, while a sleep timer stops at the end of a chapter, or for a file only in the cloud. Nothing on main names one yet, so every chapter still starts on a new player. A chapter is a whole file, a time range within one, or, in a segmented book such as a DAISY audiobook, a section (AudioSegment) holding a list of clips, each a time range of a file. playClips(_:fromChapterTime:) plays a section's clips one after another as one chain (AudioClipChain), timed from the chapter's start whichever clip and file are playing. DAISYAudioConverter (Parsers/DAISYParser+Audio.swift) gathers every clip a heading plays, up to the next heading and across files, when the book is imported, and the content index records and validates every clip.
  - Who may write it: the reader (playAudioChapter, setAudioSpeed, retryAudioPlayback).
  - How others observe it: what plays ends once. Every load, play from a time, seek, stop, and finish begins a new play (AudioPlaybackGeneration), and AudioEndNoticePolicy judges each of AVFoundation's end-of-file notices by the generation and the playhead read when it was posted. The notice ends the play under way; or it is held while playback is paused, and finishes the play when it resumes; or it is ignored, when it was posted during an earlier play; or, as the late end of an earlier playthrough of the same file, it is ignored while the play under way starts again on a fresh player. onPlaybackFinished is called once for each play that runs to its end, never while paused. A file that cannot be played is reported through one channel, AudioPlaybackService.failure (an AudioPlaybackFailure naming the file) and onPlaybackFailed, and never also as finished. Playback stops where it was, and the reader publishes audioPlaybackFailure, which shows an alert with Retry.
  - Files: Services/AudioPlaybackService.swift, Models/AudioSegment.swift, ViewModels/ReaderViewModel+Playback.swift, Parsers/AudioBookParser.swift, Parsers/AudioMediaProbe.swift, Parsers/DAISYParser+Audio.swift.
- Now Playing and media keys.
  - Owner: NowPlayingService.shared, the one coordinator of the system's remote commands and Now Playing information for the whole process. It also blocks the play command macOS sends by mistake when Bluetooth headphones disconnect, and feeds the experimental restart-timer gesture (MediaGestureDetector). Each reader talks to it through its own NowPlayingSession.
  - Who may write it: readers, through their sessions.
  - How others observe it: remote commands go to the active owner: the reader that is playing, or else the reader focused most recently.
  - Files: Services/NowPlayingService.swift, Services/MediaGestureDetector.swift.

### Imports

- An import in progress.
  - Owner: LibraryViewModel's SerialImportQueue, which runs one import at a time off the main thread, each as storage work that a data-directory move waits for or holds back (StorageBoundary.perform), and reports activity on the main queue, and ImportCancellation, which the queued imports share and the progress overlay's Cancel button sets.
  - Who may write it: FileImportService does the work. It identifies the source, builds the package under a hidden staging name (ImportStaging, .import- followed by a UUID and .tmb), in this Mac's Import Staging folder while the data directory is on its volume and beside the package's destination otherwise (ImportScratchSpace), copies the content, reads the book as the reader will, writes bookInfo.json and reads it back, and only then publishes the package with one rename. A failure removes whatever was staged and throws an ImportFailure naming the file and the step, and the original file is never touched after a failure. A ZIP is inspected and extracted within an ArchiveBudget into an Archive Extraction folder on the same condition, this Mac's or the data directory's (ArchiveExtraction), and every format reader takes entries out of archives through ArchiveEntryReader, which holds each entry to its limits. A reader that looks up more than a member or two, as the EPUB, Word, and DAISY readers do, finds them in an IndexedArchive, the archive's entries read into an index by path once, since ZIPFoundation finds each by reading the archive's central directory from its start; the index answers exactly as the archive would, the first entry at a path winning. DAISY audio conversion copies each audio file through DAISYFileProvider.copyFile(at:to:): out of a ZIP a megabyte at a time (ArchiveEntryReader.stream), never whole, and from a folder as a clone.
  - How others observe it: LibraryViewModel publishes progress for the overlay and adds the published book to the library, unless the library already holds a copy; every question an import raises waits its turn in one queue (import questions, below).
  - Files: Services/FileImportService.swift, Services/FileImportService+Packages.swift, Services/ImportStaging.swift, Services/ImportScratchSpace.swift, Services/ImportFailure.swift, Services/ArchiveBudget.swift, Services/ArchiveExtraction.swift, Parsers/ArchiveEntryReader.swift, Parsers/DAISYParser.swift, ViewModels/LibraryViewModel+Import.swift, ViewModels/LibraryViewModel+Duplicates.swift.
- Import questions.
  - Owner: LibraryViewModel.importDecisions, an ImportDecisionQueue of the questions imports are waiting to ask (whether to replace or keep a duplicate, whether to delete an original file, and whether to put a ZIP archive's books in a new folder), asked one at a time in the order they arose. Each ImportDecision holds everything its answer acts on, captured when its import finished (a duplicate's new copy and the copy it matched, an original file, or a ZIP archive's books and folder), and the ImportRequest its import was made with: the Library window it started in (ImportOrigin), whether to open the book afterwards, and the cancellation its batch shares.
  - Who may write it: LibraryViewModel+Import and LibraryViewModel+Duplicates. ask(_:) queues a question behind those waiting, and a question an answer raises about the same file, such as whether to delete the original of a duplicate just kept, is asked next. answerImportDecision(_:with:) acts only on the question being asked, named by its ID, so a second press can never answer the next one; an answer that fails, such as a folder name the library refuses, keeps the question open with the reason. cancelImports(), the progress overlay's Cancel, withdraws the questions of its batch, those waiting and those raised later: a duplicate's new copy is discarded, an original file is kept, and a ZIP archive's books stay where they are.
  - How others observe it: each Library window's ImportDecisionPresenter watches the queue, and exactly one window asks the question at its front (ImportDecisionQueue.askingWindow): the window its import started in while that is open, or else the first open Library window, the question waiting while none is open. That window shows ImportDecisionSheet, whose words, the screen's and VoiceOver's alike, come from ImportDecisionWording, with a title that gives the question's place when there is more than one, as in "Duplicate Book Found, 2 of 5". The choice that removes nothing comes first; Return and Escape press the marked choices, and Replace Existing and deleting an original file are never on a key. A question that appears while the user is in another window waits without taking focus or being announced. A book whose import asked to open it, as one opened from Finder does, opens through LibraryViewModel.readerOpener once it is in the library and its questions are answered.
  - Files: Models/ImportDecision.swift, Models/ImportDecisionQueue.swift, ViewModels/LibraryViewModel+Duplicates.swift, ViewModels/LibraryViewModel+Import.swift, Views/Library/ImportDecisionPresenter.swift, Views/Library/ImportDecisionSheet.swift, Views/ContentView.swift.

- During a move: answerImportDecision refuses every answer while dataDirectoryMove is set (DataDirectoryMoveWording.importAnswerRefusal, shown in the sheet and spoken); the question stays until the move ends, since a window asking one when a move begins keeps that sheet instead of the move's.

### Logs

- The diagnostic logs.
  - Owner: DiagnosticLog, the one policy for what a log line may say and which lines are written. It alone calls TextMouthPaths.appendLog, which hands each line, by its log's name (DiagnosticLog.File), to LogWriter.shared. The writer writes on one serial queue, never blocking or crashing the app, opens each file for its line only, and keeps each file to two generations of at most 2 MB: a full log becomes its .previous by one rename(2) that replaces the older generation in the same step; a rename refused twice, as a File Provider folder can refuse one, starts the log over in place with a LOG_ROTATION line; and a log only in the cloud is never downloaded (every write runs inside DatalessFiles.withoutDownloading), but kept as the older generation while a fresh file starts.
  - Where they are: TextMouthPaths.logDestination(for:dataDirectory:thisMacsFolder:isUnavailable:), the one resolution of the logs' folder, which the writer runs for every line (LogWriter.Environment.app) and Storage settings run to show it. Under the default choice (LogLocation.dataDirectory) it is the data directory's Logs folder, in the current storage generation's root; under the other (LogLocation.machine), this Mac's ~/Library/Logs/TextMouth (MachineLocalPaths.logs). While the data directory can't take lines (its gate is closed, its folder or its Logs folder is missing, as FolderState reads them without downloading, or a write there fails), lines go to this Mac's folder with the reason (LogDestination, LogFallback), and back once it can. Each time lines change place, the writer begins the debug log they arrive in with one LOG_LOCATION line saying why, a change of the choice included. It never makes a folder in the data directory: ensureDirectoryStructure makes Logs with the data directory's other folders, so a line never brings back a data directory that is gone. A move copies Logs with the rest, and lines go into the moved folder once the move publishes; a line written during the copy, after Logs was copied, stays in the old folder, which the move leaves where it was.
  - Who may write it: any code, through DiagnosticLog.event, for a line that is always written and echoed to the console, or DiagnosticLog.trace, for routine lines written only while tracing is on and at most 20 a second in each category; DiagnosticLog.log takes the level as an argument. Every call names its category: playback, focus, import, storage, statistics, or app. The app category, for the app as a whole, holds the BUILD_IDENTITY line written at launch (which also goes to the unified log) and LibraryWindowRouter's routing, whose failures are events and whose routine waits are trace. Trace lines are marked with their category. A line goes to the debug log unless it is one of the sleep timer's or speech's own (DiagnosticLog.File). Lines never hold book text or substitution rules, name files by their place inside the data directory or this Mac's own TextMouth folder (ImportScratchSpace.loggablePath), name a data directory by its folder and the one holding it (DataDirectoryPaths.shortName(of:)), and give book titles only in event lines. LogContentPolicyTests scans the source, read through AppSourceFile (TextMouthProductionTests/SourceScanTestSupport.swift) as UncheckedConcurrencyPolicyTests reads it, for calls that break these rules, and fails when any file but DiagnosticLog.swift calls TextMouthPaths.appendLog, or any file but TextMouthPaths.swift calls LogWriter.shared.append; no file is exempt from either check. One gap is out of the scan's sight: a CONTENT_INDEX_REJECTED line carries the reason BookContentIndex gives, which can quote heading labels.
  - How others observe it: by reading textmouth_debug.log, textmouth_timer.log, and textmouth_transition.log in the folder in use. Storage settings' Logs group (LogsSettingsSection, worded by LogsSettingsWording) names that folder, says why while the logs fall back, and opens it in Finder (TextMouthPaths.preparedLogsFolder). The logs' own events and the cloud library's have tags of their own, which LogContentPolicyTests pins with every other event tag:
    - The logs themselves: LOG_LOCATION, each time lines change place, and LOG_ROTATION, for a log started over.
    - The book service's downloads and removals: CLOUD_DOWNLOAD_STARTED, CLOUD_DOWNLOAD_FINISHED, CLOUD_DOWNLOAD_FAILED, CLOUD_DOWNLOAD_STOPPED, CLOUD_DOWNLOAD_REMOVED, and CLOUD_DOWNLOAD_REMOVAL_FAILED.
    - The list's commands: DOWNLOAD_NOW_STARTED, DOWNLOAD_NOW_FINISHED, DOWNLOAD_NOW_FAILED, REMOVE_DOWNLOAD_STARTED, REMOVE_DOWNLOAD_FINISHED, and REMOVE_DOWNLOAD_REFUSED.
    - The reader: READER_DOWNLOAD_STARTED, READER_DOWNLOAD_FINISHED, READER_DOWNLOAD_FAILED, READER_DOWNLOAD_CANCELLED, READER_READ_REFUSED, WORKING_COPY_MADE, WORKING_COPY_SKIPPED, WORKING_COPY_REMOVED, WORKING_COPY_LEFT, and WORKING_COPIES_SWEPT.
    - Maintenance: MAINTENANCE_SKIPPED_IN_CLOUD, one line for each pass that left books in the cloud.
    - Package records: BOOK_RECORD_IN_CLOUD, once for each book whose saves go to library.json alone while its record is only in the cloud.
    - The data directory: DATA_DIRECTORY_FOUND, DATA_DIRECTORY_AVAILABLE, DATA_DIRECTORY_UNAVAILABLE, DATA_DIRECTORY_UNMOUNTED, DATA_DIRECTORY_LOST, DATA_DIRECTORY_MOVE, DATA_DIRECTORY_SWITCH, LIBRARY_IDENTITY, LIBRARY_SESSION, SUBSTITUTIONS_FILE, and READING_STATS_FILE.
  - Files: Services/DiagnosticLog.swift, Services/LogWriter.swift, Services/TextMouthPaths.swift, Services/DataDirectoryAvailability.swift, Models/LogLocation.swift, Models/CloudStorageContract.swift, ViewModels/SettingsViewModel.swift, Views/Settings/LogsSettingsSection.swift, TextMouthProductionTests/LogContentPolicyTests.swift, TextMouthProductionTests/SourceScanTestSupport.swift.

### The hosted-test sandbox

- The process's runtime.
  - Owner: TextMouthRuntime.current, decided once at first use: whether the process hosts the tests (the XCTestConfigurationFilePath environment variable is set), the directory that stands for the user's home, and the preferences store. In a test host they are a TextMouthTests- folder named after the process number, in the temporary directory, and a preferences store inside it, emptied at the start. A new process clears whatever an earlier process with its number left in that folder (clearEarlierSandbox(at:)), moving a kept one aside under its name followed by -kept- and a short suffix.
  - Who may write it: no one; it is immutable. A test that needs the app's behavior builds a runtime value of its own.
  - How others observe it: everything that could reach the user's data follows it: TextMouthPaths.root (which ignores a custom data directory in a test host), this Mac's own folders (MachineLocalPaths), the legacy data locations, AppDelegate's window-restoration setting, and every preference owner. SpeechService's convenience initializer still uses UserDefaults.standard directly. In a test host the cloud refresher never refreshes and TextMouthRelauncher never opens TextMouth again; tests install fake cloud services through CloudServices. The opt-in real-drive tests (CloudDriveIntegrationTests) touch only the folders TEXTMOUTH_CLOUD_TEST_ROOTS names, each named TextMouth Cloud Tests, and never move the app's library out of the sandbox.
  - Files: App/TextMouthRuntime.swift, Services/TextMouthPaths.swift.
- Sandboxes left behind.
  - Owner: HostedSandboxCleanup, which the test bundle's principal class, TextMouthTestBundle, registers. As the bundle starts, it deletes, off the main thread, the sandboxes earlier processes left behind (TextMouthRuntime.removeAbandonedSandboxes): folders named for another process that has ended, as isSandboxMakerRunning judges it. The system reuses process numbers, so a running process with the folder's number counts as its maker only when it started no later than an hour after the folder was made (startDate(ofProcess:), read with sysctl); when either date is unknown, the folder is kept, and so are kept sandboxes and anything that is not a plain folder. As the bundle finishes, it waits for that sweep, at most a minute, and deletes its own sandbox (finishWithSandbox()), unless TEXTMOUTH_KEEP_SANDBOX is 1, which marks it kept with a KEPT-SANDBOX.txt file instead. A run that crashes leaves its sandbox to the next run's sweep.

- Config saves a test leaves waiting.
  - Owner: ConfigSaveFlush, which TextMouthTestBundle registers too. As each test ends, it writes a config.json save the test left waiting (ConfigService.flushScheduledSave()), so the save never lands during the next test.
  - Files: TextMouthProductionTests/ConfigTestSupport.swift, TextMouthProductionTests/HostedTestObservers.swift.
- Redraw counts.
  - Owner: ViewBodyCounter, which each view the hosted tests measure calls on the first line of its body. Debug builds, which the tests run, count each view's body evaluations by name; Release builds compile the calls to nothing.
  - Files: Views/ViewBodyCounter.swift.
- VoiceOver announcements.
  - Owner: VoiceOverAnnouncer, through which the reader, the library and its import questions, the sleep timer, and settings announce. ## Reading a book: the path from library row to spoken audio

A book opens from its row in the Library window: VoiceOver's default action on the row, the row's Open command, or the Open Selected Book shortcut calls ContentView's onOpenBook, which asks SwiftUI for the reader window whose value is the book's ID. A book already open comes forward instead of opening twice. Requests from elsewhere, such as Finder or a finished book continuing to the next, go through LibraryWindowRouter to the same scene. The scene builds a BookReaderWindowView, which looks the book up in LibraryViewModel and creates the window's ReaderViewModel with a copy of it. When the view appears it marks the book opened, and its window accessor gives the reader its window and registers the window with the router.

The new reader loads at once, on a background queue. It first asks the book storage where the library lives. Anywhere but a cloud location it reads the book in the same step, as it always has. In a cloud location it reads the book's cloud state too, and a book with files only in the cloud downloads first, in the reader window; the book is then read with dataless files left in the cloud, an audiobook after it is cloned into its working copy (getting a book from the cloud, above). Reading calls BookContentAnalysisService.load, asking for a fresh text cache when the book records an older cache format than MarkdownCacheService.currentCacheVersion. For a text book, loading writes content.md if it is missing; otherwise it checks the cache against its fingerprints, rebuilding it when the source or the cache has changed, reads it, and uses the content index saved in bookInfo.json when that index validates and lines up with the chapters, or indexes the chapters afresh. For an audiobook, loading uses a validated saved index, or else reads the audio through AudioBookParser, waiting for it through AsyncBridge, into chapters whose placeholder text stands for time at ten characters a second. EPUB metadata and audio tags are read as well. Back on the main actor, the reader publishes the content and its headings, lays the book's own metadata edits over what the files hold, taking them from its copy of the book as it is by then, brings the saved position into range, commits a new or changed index through LibraryViewModel.updateContentIndex, saves the position, and claims a waiting autoplay request, if one is there. If the library moved the book while it loaded, the reader finds its chapter files at the new place, and a load that failed because of the move starts again from there.

Play starts nothing while the book is loading or while Where Am I? is speaking. For a text book, the reader first prepares what it will say, or takes what it prepared before from the same inputs (prepared speech, above). The chapter's text goes through the playback pipeline (ChapterSpeechInputs.prepare()): skipped sections are removed, runs of a repeated symbol are rewritten (RepeatedSymbolRule, which runs before the pauses because their periods and commas would lengthen runs of those symbols), punctuation pauses are added, and the substitution rules are applied, while a ComposedOffsetMap keeps track of where every spoken character came from. A position anywhere inside a rewritten run maps into the words that replaced it, and back. When nothing speakable remains, the book ends at once through its end-of-book behavior. Otherwise the reader claims the media controls through its NowPlayingSession, plays the play sound, records when playback started (for rewind on resume), starts a listening session in ReadingStatsService, resumes the sleep timer's countdown if this book owns a paused one, and starts speaking.

Speaking begins a new play of the chapter (ChapterPlay), which gives the speech service a finish callback made for that play, and hands the spoken text and the starting offset to SpeechService.speak, which starts the synthesizer speaking directly at once, from a short first chunk, and renders the same text into an AudioEngineService in the background, through SpeechRenderCoordinator, for the next natural break. The reader then pre-renders the next speakable chapter, recording what that render was asked for as its signature and carrying that chapter's speech to its start; a chapter too long to render ahead is not rendered, and only its speech is prepared, off the main actor. As each word is spoken, onWordSpoken moves the cursor back through the offset map to the original text. The reader refreshes its view at most every 0.12 seconds, gives the library's rows and summary bar its cursor about once a second, through LiveReadingPositions, and saves a durable checkpoint every 30 seconds, into the book's record at once and into library.json within five minutes.

When a chapter's speech finishes, the callback made for its play ignores the end of a play the reader has already left, a later play having begun. Otherwise it saves the position, tells the sleep timer that this book's document ended, and starts the next speakable chapter after the one that played, as a new play. If the look-ahead holds that chapter's audio, rendered with the signature its speech has now, the engine plays it at once and the chapter after it is pre-rendered; otherwise the chapter is spoken from its current text. When no speakable chapter remains, handleEndOfBook stops, starts the book again, or continues to the next book in the folder, as the book's end-of-book behavior says.

An audiobook takes the other branch at Play: playAudioChapter begins a new play and loads the chapter's file into AudioPlaybackService, from the book's working copy when the reader has one, playing it from the cursor's time, counted from the chapter's start within the file when the chapter is a time range, at the book's speed. A segmented chapter plays its clips as one chain instead, from the clip that holds the cursor's time. In a cloud location without a working copy, a chapter whose file is only in the cloud downloads first (chapterFilesReadyToPlay), and plays once it is here. The service reports the end of each play once, and the reader moves on from the chapter that played, as it does for speech. A file that cannot be played stops playback where it was, and the reader shows an alert with Retry.

Pausing records when playback stopped, pauses the sleep timer's countdown if this book owns the timer, ends the listening session (crediting its last slice), and saves the position. Closing the window unregisters it from the router and closes the reader, which stops waiting for any download, stops playback, saves the position, releases its Now Playing session, stops the sleep timer if this book owns it, deletes its working copy off the main thread, stops watching the library's updates to its book, and lets go of everything that grows with the book (a closed reader, above). The book's library row and its bookInfo.json then hold the last checkpoint, and LibraryPersistenceService writes both within half a second, unregistering the book having brought library.json's write forward from its checkpoint deadline, or at the latest when the app quits.

## Shared helpers

These small types each own one rule that several parts of the app follow; use them rather than writing the rule again.

- LibraryWindowRouter (Services/LibraryWindowRouter.swift): decides which window takes each app-wide action.
- LibraryBookUpdates (ViewModels/LibraryBookUpdates.swift): how open readers learn that the library changed their book or is moving its files.
- TextCacheFingerprint (Models/TextCacheFingerprint.swift): what a text cache was written from, checked by size and date before any file is read.
- PersistenceFailureCenter (Services/PersistenceFailureCenter.swift): where every failed save is reported and settled.
- ImportStaging (Services/ImportStaging.swift): builds a package out of sight and publishes it with one rename.
- DataDirectoryMigrator and DataDirectoryLocation (Services/DataDirectoryMigrator.swift): copy a whole data directory out of sight and publish it with one rename, and take a location as the real folder its links lead to.
- StorageBoundary and StorageGeneration (Services/StorageGeneration.swift): where the data directory is now, and the boundary that keeps the work writing into it from running across a move's publication.
- StorageDestinationAssessment, StorageChoice, and StorageWording (Services/StorageDestinationAssessment.swift): what a folder chosen for the library can become, judged from metadata alone, and the words that offer it.
- DataDirectoryMoveProgress and DataDirectoryMoveWording (ViewModels/DataDirectoryMoveProgress.swift): a move under way, with its Cancel, as every Library window's sheet, Storage settings, and VoiceOver present it.
- OffMainWork (Services/StorageDestinationAssessment.swift): runs blocking work, such as reading or copying a folder that can wait on a drive or the network, on a background dispatch queue, and hands back its result without holding the main actor.
- ArchiveExtraction, ArchiveBudget, ArchiveEntryReader, and IndexedArchive (Services/ArchiveExtraction.swift, Services/ArchiveBudget.swift, Parsers/ArchiveEntryReader.swift): bounded, cancellable ZIP extraction, the one way to read an archive entry, and the one way to find many entries.
- ImportScratchSpace (Services/ImportScratchSpace.swift): where imports stage packages and extract archives, on this Mac or beside the library.
- SettingsPolicy (Models/SettingsPolicy.swift): the table of every validated preference.
- StoredPreference and PreferenceObserver (Models/StoredPreference.swift): one definition of each preference's key and stored form, and notice of its changes.
- VoiceOverAnnouncer (Services/VoiceOverAnnouncer.swift): every VoiceOver announcement, recorded instead under tests.
- TextMouthRuntime (App/TextMouthRuntime.swift): the one switch that keeps hosted tests away from the user's data.
- DatalessFiles (Models/CloudStorageContract.swift): whether a file's content is only in the cloud, and running work that must never download with dataless files left there.
- MachineLocalPaths (Models/CloudStorageContract.swift): this Mac's own folders, which never sync: its Logs folder, the working copies, import staging, and archive extraction.
- NetworkReachability (Services/NetworkReachability.swift): whether this Mac is online, from one NWPathMonitor, or a test's answer.
- MaintenanceFileAccess (Services/MaintenanceFileAccess.swift): how maintenance asks whether a book's files are in the cloud, and reads them without downloading.
- DiagnosticLog (Services/DiagnosticLog.swift): what a log line may say, and which lines are written.
- LogWriter and TextMouthPaths.logDestination (Services/LogWriter.swift, Services/TextMouthPaths.swift): the one writer of log files, and the one place that decides each line's folder.
- AsyncBridge (Services/AsyncBridge.swift): lets synchronous parsing and analysis wait for async work, such as reading audio through AVFoundation.
- AudioSegment and AudioClipChain (Models/AudioSegment.swift, Services/AudioPlaybackService.swift): a segmented chapter's clips, never an empty list, and the one conversion between a time in the chapter and a time in a clip's file.
- CountWording (Models/CountWording.swift): a count with the right singular or plural word, so the screen and VoiceOver say the same thing.
- ManualBookOrder and LibraryBookSorter (ViewModels/LibraryViewModel+SortAndOrder.swift, Models/LibraryBookSorter.swift): the library's orderings. Manual order (by position, then title, then book ID) is the one order the list, Move Book Up and Down, dragging, and Continue to Next Book all follow.
- RemovalWording, OperationOutcome, ReadingStatsTileWording, and ImportDecisionWording (Models/): the wording of removals, operation results, statistics, and import questions, each built once for both the screen and VoiceOver.
- LibraryCloudWording (Models/LibraryCloudWording.swift), ReaderCloudWording (ViewModels/ReaderViewModel+CloudDownload.swift), and DataDirectoryUnavailableText (Views/Library/DataDirectoryUnavailableView.swift): the wording of the list's cloud commands, a reader's download, and the Library Not Available screen, each built once for both the screen and VoiceOver.

## Known duplication

Repeated code that is known and left for now, each with the reason:

- ReaderViewModel (audio metadata when a reader loads) and FileImportService (audio tags during import) keep their own copies of the async-to-sync bridge; both could call AsyncBridge.waitForResult. SpeechService's render wait is a different shape: it waits for a completion callback on the main queue.
- More than a dozen messages still choose singular or plural inline, in FileImportService, LegacyBookMigration, LibraryViewModel+Migration, PersistenceFailureCenter, LibraryViewModel+BookOperations, and AudioBookParser; they could use CountWording. A few sentences deliberately drop the number for one ("Remove Book?", "the book inside") and do not fit it.
- TimeRemainingBar.computeTimeRemaining (Views/Library/LibrarySubviews.swift) repeats LibraryViewModel.totalTimeRemaining(books:wpm:), which nothing calls at all.
- PDFTextParser's two page readers, with and without heading detection, share most of their loop, but record font sizes differently in ways that the paragraph joiner reads, so merging them would change some PDFs' paragraphs.
- VoiceOverFocus.swift repeats its accessibility-tree searches (findElementByIdentifier and findFirstInteractiveElement) and its focus scheduling in StandardVoiceOverFocusTriggerView and VoiceOverFocusTriggerView.
- Several stores configure their own JSON encoder with the same ISO 8601 dates and sorted, pretty output (BookInfo, RemovedFromLibraryMarker, ReadingStatsService, DataDirectoryMigrator, LibraryIdentity, LibrarySessionLease); library.json's encoder alone does not sort its keys, so sharing one would change that file's layout.
- ReaderViewModel.offMain repeats OffMainWork.run: both run blocking work on a global dispatch queue and hand back its result. Two cloud branches written side by side added them; the reader could call OffMainWork.
- Three functions compare two items' volume identifiers: ReaderWorkingCopies.isOnSameVolume, ImportScratchSpace.areOnSameVolume, which first climbs to the nearest folder that exists, and the live areOnOneVolume probe of StorageDestinationAssessment. They could share one.
- ListingFailure (Services/ReaderWorkingCopy.swift) and FolderListingFailure (Services/DataDirectoryMigrator.swift) are the same small class, keeping the first error a folder enumeration's handler meets; one could serve both.
- ContentView opens readers with the literal window ID "book-reader" rather than BookReaderWindowView.windowID, and posts its folder announcement directly rather than through VoiceOverAnnouncer.
- TextMouthPaths.cachedAudioDir names a per-package cachedAudio folder that nothing creates or reads.
