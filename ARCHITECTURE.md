# TextMouth architecture

This document explains how TextMouth is put together and, above all, which part of the app owns each kind of state: who keeps it, who may change it, and how everything else finds out about a change. It describes main as of October 10, 2026. When a change moves the ownership of some state, update its entry here in the same branch.

README.md covers building, testing, the files in the data directory, and keeping the library in the cloud. Paths below are relative to the TextMouth source folder unless they start with the name of another top-level folder, and names in the text are the names of Swift types, functions, and properties.

## The parts of the app

- One SwiftUI application. TextMouthApp (App/TextMouthApp.swift) declares three kinds of window:
  - Library windows (LibraryWindowView, ContentView, and LibraryView). The first opens at launch, and Command-N opens more.
  - Reader windows, one per book, identified by the book's ID (BookReaderWindowView, in the scene whose ID is BookReaderWindowView.windowID). Window restoration is off, so none reopen at launch.
  - The Settings window (SettingsView), with nine tabs.
- Two more kinds of window are AppKit's, so that closing one can ask first. The Record window, titled New Recording (RecordingWindowView, in an NSWindow that RecordingWindowController.shared makes, one at a time, with the identifier "new-recording" and restoration off): TextMouthApp attaches the LibraryViewModel recordings are saved into as a Library window appears, and File > New Recording… and Library > New Recording… show it, as does the first Library window's appearance when recordings were left behind (takes left behind, below). And the audio editor's windows, one for each book being edited, titled "Edit Audio:" and the book's title (AudioEditorView, in NSWindows that AudioEditorWindowController.shared makes, with the identifier "audio-editor" and restoration off), which Edit Audio… opens through AudioEditorLauncher (the editor window, below).
- App-wide objects, created once by TextMouthApp and given to every window as environment objects:
  - LibraryViewModel: the library in memory, and every operation on it.
  - SettingsViewModel: the global settings, and the config.json mirror.
  - KeyboardShortcutManager: every action's keyboard shortcuts.
  - SoundEffectService: the sounds that playback events play.
  - LibraryWindowRouter.shared: which window takes each app-wide action.
- AppDelegate (App/AppDelegate.swift) starts the router before Finder can hand over a file, owns MenuVisibilityManager, turns off window restoration, and holds a quit until nothing would be lost: it stops a data-directory move that is copying, has the Record window ask about a take it holds (RecordingWindowController.holdQuit) and then each audio editor window about its unsaved edits (AudioEditorWindowController.holdQuit), asks when changes are unsaved (UnsavedChangesTerminationGuard), and then lets the feed downloads keep their place, for at most three seconds (FeedQuitHold). At quit it cancels a transcription under way, asking nothing, and ends the session lease.
- Each reader window has its own ReaderViewModel, which has its own SpeechService, AudioPlaybackService, and NowPlayingSession. Readers share SleepTimerService.shared, ReadingStatsService.shared, TextSubstitutionService.shared, ReaderAutoplayRequests.shared, and SpeechRenderCoordinator.shared, and, through ReaderCloudServices, the installed book storage, BookCloudStates.shared, and ReaderWorkingCopies.shared.
- The source folders:
  - App: the entry point, the delegate, the menu commands, the build identity, the process runtime (TextMouthRuntime), and the check made before quitting.
  - Models: value types and small rule tables, such as Book, BookInfo, Library, BookContentIndex, SettingsPolicy, StoredPreference, and the wording helpers.
  - Parsers: one reader per format, each turning a source file into DocumentContent (chapters, headings, and an index), plus shared readers for archives, packages, and text encodings.
  - Services: everything that owns a file, a queue, or a system resource. Services/Feeds holds the feed engine, whose FeedCenter.shared LibraryViewModel starts and offers as feeds, Services/AudioEditing the audio editing engine, which works without a window (audio edits, below), and Services/MP3 the MP3 encoder over the LAME library that project.yml builds from Vendor/lame (an MP3 file TextMouth writes, below).
  - ViewModels: LibraryViewModel and ReaderViewModel, each split into extensions by topic, plus SettingsViewModel, BookSearchModel, and LibraryBookUpdates.
  - Views: the SwiftUI views of the library, the reader, settings, the Record window, the audio editor window (Views/AudioEditor), the Export dialog (Views/Export), transcription's sheets, dialogs, and settings group (Views/Transcription), and the feed reader's interface (Views/Feeds), plus VoiceOverFocus.swift, which places VoiceOver's focus in new windows and sheets, and ViewBodyCounter.swift, which counts body evaluations for the hosted tests.
- Concurrency: the view models, the window router, the settings mirror, the sleep timer, the statistics, the books' cloud states, the books kept on this Mac, the list cache, the live reading positions, and the voice list run on the main actor. Disk work runs on queues that each own their work: serial queues for the library index and for package records (LibraryPersistenceService), for imports (SerialImportQueue), and for logs (LogWriter), and at most two workers for cache updates (TextCacheUpdateQueue). Each import, text extraction, and book analysis on those queues runs through StorageBoundary.perform, which a data-directory move holds back and waits for, so none runs across the move's publication; the move then copies the data directory off the main actor, while every Library window's sheet keeps the library from changing. Rebuild Directory and the folder edits made from the library's sheets hold storage work the same way; a folder edit moves its packages and rewrites their records off the main actor, then publishes the new rows on it, keeping any change made to the library meanwhile (performLibraryTransition). Work that can wait on a drive or the network never runs on the main thread. The list's cloud refreshes and commands call the cloud services from detached tasks, and work that holds its thread for as long as it takes runs on a global dispatch queue (ReaderViewModel.offMain, OffMainWork) rather than on one of Swift's cooperative threads: the reader's requests to the book storage and its reads of a book, the check of a folder chosen for the library, the count of books only in the cloud before a move, a move's copy, and a folder edit's moves. The audio editor's level measurement reads its composition on a Thread of its own for the same reason: a reader may block for as long as CoreMedia takes, and on October 6 a few cancelled measurements blocked there starved the cooperative pool. A read that must never download runs inside DatalessFiles.withoutDownloading, which leaves dataless files in the cloud for its own thread only. Other work leaves the main thread too. The look-ahead prepares the speech of a chapter too long to render ahead on a global queue, which ChapterSpeechInputs allows by being values and prepare() by being pure, and the main actor keeps the result only while the chapter's inputs are unchanged. Rendered speech is fed to the engine's player node from RenderedSpeechFeeder's own serial queue, which every call on the node goes through, so a busy main thread never leaves the node without audio, and a completion handler of the node never waits on the feeder. The installed voices are listed on a detached task (VoiceCatalog), launch finds the books its cache batch must rebuild on a utility queue, where its metadata refresh reads the files of the rows an older reader read too, and Storage settings ask whether the data directory exists off the main thread. Transcription runs on an actor of its own (TranscriptionService), one book at a time, with its blocking reads on a global queue (OffMainWork); the main actor's TranscriptionJobCenter saves each transcript on a global queue too, a window's TranscriptionPresenter deletes one there, and its Clean Up sheet reads the cleanup's rules, cleans a transcript up, and undoes a cleanup there. The Record window's capture backend (CaptureSessionRecordingBackend) is an actor running on a serial queue of its own, since a capture session blocks while it starts and stops. The feed engine runs on the main actor; a feed's fetch, its parse, and a first merge run off it, and its records, this Mac's fetch details, and its imports are written on queues of their own. Audio editing reads, renders (LAME encoding an MP3 within a render), and deletes originals off the main thread, as storage work (StorageWork.audioEditing), each change of a book's edit history under one lock (AudioEditHistoryStore), and an installed ffmpeg runs as a child process, never on the main thread; the editor window's model runs on the main actor, measuring the edited audio's levels off it, and plays through an AVPlayer. Every target builds in the Swift 6 language mode, set once in project.yml (TextMouthTests/Package.swift matches it), so concurrency diagnostics are errors, and `make check` fails on any Swift warning and on a Release app larger than 50 MB (11 MB on October 3, 2026, once `make build` stopped compiling with code coverage and the symbols were stripped into a dSYM that `make install` keeps for the last five installs, and 15.4 MB on October 4, with that day's features and LAME's encoder). The mode adds runtime isolation checks to `@objc` methods of main-actor classes and to main-actor closures handed to Objective-C APIs; each of the app's checks runs on the main thread, and VoiceWarmUp's buffer callback relies on AVSpeechSynthesizer calling back on the thread that called write(). SpeechService handles every callback of its direct synthesizer on the main queue, so its announcement of a text the speech engine refused, made only when no reader listens, asserts the main actor there (endDirectSpeechRefused(at:refusing:spanning:)). A render's RenderCancellationObserver, called on whatever thread the synthesizer uses, only sets a flag in an OSAllocatedUnfairLock and signals the semaphore the render queue waits on; it is Sendable, as the SDK makes every synthesizer delegate (AVSpeechSynthesizerDelegate is NS_SWIFT_SENDABLE), and the compiler checks it, with no `@unchecked`. Speak Info's LibraryInfoSpeechDelegate ends an announcement at once when called on the main thread, and otherwise on the next turn of the main queue, and the reader's WhereAmIDelegateHelper hands each finish and cancel of an announcement to the main queue. UncheckedConcurrencyPolicyTests requires a comment naming a lock, queue, actor, or thread on the three lines above each `@unchecked Sendable` or `nonisolated(unsafe)` declaration and pins their counts (26 and 14, the fourteenth the record of each feed's index on disk, LibraryPersistenceService.feedIndexesOnDisk, confined to the save queue since FR11's branch A1).

## Launch

- TextMouthApp's initializer installs the real cloud services (CloudServices.installSystemServices) before anything else runs: SwiftUI creates LibraryViewModel before applicationWillFinishLaunching, and the library's launch check uses them.
- AppDelegate.applicationWillFinishLaunching starts the router before any window exists, so a book Finder hands over waits for the first Library window instead of opening a second.
- The data directory's first location is decided when anything first asks for it (StorageBoundary.shared): TextMouthPaths.root(for:) names the folder the preferences hold, or the default location. When a custom location is missing but its bookmark leads to a folder holding this library under another path, as after a rename or a remount under another name, that folder is the data directory, and the preferences name it from then on.
- LibraryViewModel's initializer copies a sandboxed release's data on first launch (through DataDirectoryMigrator, keeping the original), starts listening for the data directory's loss, and checks the data directory (checkDataDirectory), reading metadata only. Nothing is created or loaded until the check finds the library: then startLibrary creates the data directory's folders, records the library's identity, removes leftover archive extraction folders, loads the library index (loadLibraryIndex), sweeps away the originals of recordings and edited audiobooks whose time is up (sweepAudioOriginalsInBackground), clears what the audio editor left in this Mac's caches when TextMouth last ended with editors open (removeStaleAudioEditCachesInBackground), starts the background work below, and begins the session lease. Otherwise every Library window shows Library Not Available, and the Try Again that first finds the library runs startLibrary.
- Loading reads library.json and every feed's own index, the feeds' rows onto the library's feed shelf (feed items, below), and repairs the index against the disk (migrateOldBooksIfNeeded): every feed item's row waits on the shelf meanwhile, books removed with Remove from Library Only stay out, the books the checkpoint journal names take the newer reading positions their records hold (adoptNewerRecordedPositions), equivalent folder rows merge, stale file paths are fixed, legacy books move into packages, packages that two books shared are separated, misplaced packages move into their folders, packages missing from the index are adopted, the feed items whose files are here join the books (joinFeedItems), and the result is saved. Every check and read of the repair leaves dataless files in the cloud, and nothing is moved, rewritten, adopted, separated, relocated, or taken out on the strength of a check that met a dataless folder or a read that was refused; one MAINTENANCE_SKIPPED_IN_CLOUD line counts the books left as they were. The look for a removal marker, which is almost always absent, stops at the first folder above it that is there and not dataless, the package itself, rather than asking every folder up to the data directory. An unreadable index skips all of this and enters recovery instead (below).
- LibraryViewModel then brings every book's text cache up to date, and after that its statistics, in the background (updateContentCachesAndStatistics), leaving books whose files are in the cloud as they are. The batch finds the books whose caches need work off the main thread (booksNeedingCacheUpdate, on a utility queue), and starts on the main actor once it has them.
- startLibrary also starts the feed engine in the background (startFeeds, FeedCenter.start(library:)): it reads every feed's record and this Mac's fetch details off the main thread and sweeps away what interrupted downloads left; then, outside a process hosting tests, it asks again for the downloads under way or waiting when TextMouth last quit (resumeDownloadsSavedAtQuit), deletes the played downloads that are due, refreshes every feed when feedRefreshAtLaunch is on, and refreshes them again every feedRefreshIntervalHours, never holding the library back. Once the records have loaded, the library moves the downloads made before FR11 into their feeds' own folders and marks downloaded again the items an older TextMouth marked otherwise (moveFeedDownloadsOnceRecordsLoad(); feed items, below).
- SettingsViewModel's initializer applies config.json, reconciles it with the preferences, and starts ConfigService watching the file. Before it applies the file (applyFileAtLaunch), the first launch whose preferences hold no record of the shortcuts the user edited makes one from the shortcuts saved before (KeyboardShortcutManager.moveSavedShortcutsIfNeeded; keyboard shortcuts, below). While the data directory is unavailable, ConfigService reads, writes, and watches nothing, and it reconciles the file once the library is back.

## Who owns each kind of state

Each entry names a kind of state, then its owner, who may write it, how others observe it, and the files involved.

### The library index

- The library: every book's row, the folders, each location's sort, and the reading list (below).
  - Owner: LibraryViewModel.library, published on the main actor. It is the live copy; library.json, with each feed's own index (feed items, below), is its saved form. Each location's sort is kept in folderSortSettings under the location's key (LibraryLocation.sortSettingsKey): a folder's path in Folders, and in every other category a reserved key (LibraryCategory.sortSettingsKey: __allItems__, __unopened__, __recent__, and __readingList__, under which nothing is saved), which no folder may take as its name (BookFolder.reservedNames, made from those keys and the former No Folder category's __noFolder__).
  - Who may write it: LibraryViewModel and its extensions, on the main actor. Each change is followed by save(), which hands a snapshot to LibraryPersistenceService.save(_:). That waits half a second on the service's serial queue, and only the newest snapshot is written, so an older snapshot never lands after a newer one. A reading checkpoint goes through saveReadingCheckpoint(_:of:writingWithin:) instead, which lets its snapshot wait up to five minutes (readingCheckpointDelay), since the book's record holds the checkpoint meanwhile: any ordinary save writes it sooner, and writePendingIndexSoon() brings it forward when a reader closes (unregisterOpenBook) and when a record cannot take its checkpoint, being only in the cloud or failing to be written. Until an index write holds every checkpoint, ReadingCheckpointJournal names the books whose records are ahead in reading-checkpoints.json, noting each before its record is written, and launch's repair gives each book it names its record's newer position and last-opened date (booksWithCheckpointsAhead() and adoptNewerRecordedPositions). flushPendingSave() writes a waiting snapshot before the app quits. Every write replaces library.json atomically, as compact JSON (encodedIndex(_:)), after writing each feed's index whose bytes changed (feed items, below).
  - How others observe it: SwiftUI views observe LibraryViewModel. A reader takes a copy of its book when it opens and reports back through LibraryViewModel: updateLiveReadingPosition (live reading positions, below, which change nothing in the library), persistReadingPosition (the row and the package record at once, library.json within five minutes), and updateContentIndex. Every change of library is offered first to LibraryViewModel.listCache (the lists Library windows show, below), then to LibraryViewModel.bookUpdates, which keeps the copies of open readers current (a reader's copy of its book, below). No timer republishes the library: nothing a Library window shows depends on the clock, and a value that ever does should use a TimelineView rather than a tick that redraws every window. Every window, menu, and list reads a location's sort through Library.sortState(at:), from Library.sortSetting(at:) (Models/LibrarySortState.swift). At the Reading List, which shows an order of its own (LibraryLocation.keepsItsOwnOrder), that is always FolderSortSetting.readingListOrder, shown as manual order, and userChangedSort(_:at:) saves nothing there. Anywhere else it is the first of these that exists: the setting saved under the location's key; in Unopened alone, which took No Folder's place on October 7, 2026, the setting saved under No Folder's key, __noFolder__, unless its field is manual order, which was the arrangement of the root's books alone; and the category's default (title ascending; last opened descending in Recently Opened; date added descending in Unopened, FolderSortSetting.unopenedDefault, since no unopened book has been opened). Nothing is written under __noFolder__ again, so a sort chosen in Unopened, saved under __unopened__, takes that one's place for good.
  - Files: Models/Library.swift, Models/LibrarySortState.swift, Models/BookFolder.swift, ViewModels/LibraryViewModel.swift and its extensions, Services/LibraryPersistenceService.swift, Services/LibraryLoadResult.swift.
- Live reading positions: where readers are in their books between checkpoints, for the rows and the summary bar.
  - Owner: LibraryViewModel.livePositions, a LiveReadingPositions on the main actor, holding one LiveReadingPosition for each book, kept for the session.
  - Who may write it: readers, about once a second while they play, through LibraryViewModel.updateLiveReadingPosition; a book no longer in the library changes nothing. When openBookIDs changes, a book no reader has open drops its entry (keepOnly), its reader having saved its position to the library as it closed.
  - How others observe it: a book's row (BookRow) observes its own book's entry, so a live position redraws that row alone, and the summary bar (TimeRemainingBar) observes the store; the library model publishes nothing. A live position is shown in place of the row's own only while it is the newer (ReadingPosition.lastUpdated), so a checkpoint, or a position another window saved, takes over at once.
  - Files: ViewModels/LiveReadingPositions.swift, ViewModels/LibraryViewModel.swift, ViewModels/LibraryViewModel+BookOperations.swift, Views/Library/LibrarySubviews.swift.
- The lists Library windows show: each location's books in its sort, narrowed by a search, and the book counts of folder trees.
  - Owner: LibraryViewModel.listCache, a LibraryListCache on the main actor, which derives each list once and keeps it, at most LibraryListCache.entryLimit lists, until a change it depends on. It publishes nothing, so a window may derive and store a list while SwiftUI draws.
  - Who may write it: the library itself, which offers every change of library to listCache.libraryDidChange(from:to:) before anything reads it. A change of membership (which books there are, their order in the library, their folders, and their feed links), of the reading list's books or their order (LibraryListCache.readingListMayDiffer, which its options never change), or of a field a sort or a search reads (the title, the author, the dates added and last opened, the manual order, and the book's file) drops every list; any other change, such as a word count or a voice setting, keeps every list's order and refreshes only its books' values. A reading checkpoint stamps the book's last-opened date, so it sorts the lists again. Folder trees are counted in one pass whenever the lists are dropped, from the library's own books, and the sizes a File Size sort reads are measured once per book, until its file changes. A list's key (LibraryListCache.Key) holds, for a feed's folder in Folders, the feed whose items it lists, so the list is derived again when that changes although no book did.
  - How others observe it: a Library window reads its list through displayedBooks(at:matching:) and bookCount(inFolderTree:) as often as it draws: the first read after the lists were dropped derives its list again, and the first after any other change refreshes the list's books. Before sorting, a location lists LibraryViewModel.booksForCategory's books: a folder's in Folders, with its feed's items for a feed's folder (feedItems(listedIn:)); every book of the library's own in All Items (Library.libraryBooks); in Unopened every book of its own never opened, from every folder (Library.unopenedBooks(), the books whose lastOpened is nil, as a record's BookState.isNew says too); in Recently Opened the ten books opened last, and of each feed's items only the one opened last (LibraryBookSorter.recent(_:limit:)); and at the Reading List the list's books in its order (readingListBooks), which displayedBooks(at:matching:) never sorts, a search narrowing that order. A feed's items are listed nowhere else (feed items, above). Opening a book stamps its lastOpened, which the lists depend on, so the book leaves Unopened as the list is derived again. LibraryLocation.manualOrderFolder is nil in All Items, Unopened, Recently Opened, and the Reading List, whose books come from many folders that share no one order. What dragging and Move Book Up and Move Book Down rearrange is LibraryLocation.reorderTarget(sortedBy:), a LibraryReorderTarget: a folder's manual order in Folders, the root included, while the list shows it, or the reading list at the Reading List, always. LibraryViewModel.moveBook(_:direction:in:) and reorderBooks(in:from:to:) take a move or a drag there, and each move is announced alike (ManualBookOrder.MoveResult.announcement, as in "Moved Bestiary above Almanac").
  - Files: ViewModels/LibraryListCache.swift, ViewModels/LibraryViewModel+FolderManagement.swift, ViewModels/LibraryViewModel+SortAndOrder.swift, Models/LibraryBookSorter.swift, Models/LibrarySortState.swift.
- The reading list (FR09): books from any folder, in an order the user arranges, and what a book opened from it does when it ends.
  - Owner: Library.readingList, a ReadingList (Models/ReadingList.swift), saved in library.json with the rest of the index: the books' IDs in reading order, each once, and two options, continuation (ReadingList.Continuation: playBookBelow, the default, playBookAbove, or stop, saved by its raw value, never by the words the options bar shows) and skipsFinished (true until cleared). It is read leniently: an ID that can't be read is skipped, one listed twice is kept where it first appears, an option missing or unknown reads as its default, and a list that can't be read at all is left empty, so it never makes the index unreadable.
  - Who may write it: LibraryViewModel+ReadingList, every change through editReadingList(_:), which edits the list as the window shows it, any ID naming no book left out, and makes a change one change of library and one save, and a request that changes nothing no save: addToReadingList and removeFromReadingList, whose announcing forms serve a row's, a selection's, and the Library menu's commands and say what they did, or why nothing changed, in ReadingListWording's words; moveInReadingList and reorderReadingList, for Move Book Up and Down and a drag; and setReadingListContinuation and setReadingListSkipsFinished, for the options bar. Library.removeBook(id:) and removeFolderAndContents(id:) take a removed book off the list, so every way a book leaves the library ends there. The list's order is its own: moving a book in it never touches a folder's manual order.
  - How others observe it: LibraryCategory.readingList, the Library window's fifth category, lists readingListBooks, which a search narrows and nothing sorts. A book row carries ReadingListCommands (Add to Reading List for its books not in the list, Remove from Reading List for those in it, each counting a selection's books), as context menu items and as its last VoiceOver actions, and, outside the Reading List, the accessibility value "In reading list" (ReadingListWording.inReadingListValue), the empty string otherwise, so the row keeps its identity, and VoiceOver its place on it, when its own command changes the book's membership. At the Reading List, ReadingListOptionsBar shows the options, the Sort menu's one item is ReadingListWording.orderName, checked, the window is titled "Library: Reading List", and an empty list shows ReadingListWording.emptyList as a row. LibraryOrderCommandsSupport (Views/Library/LibraryView.swift) takes the Library menu's Move Book Up and Down and Add to and Remove from Reading List, which post addToReadingList and removeFromReadingList, for the Library window that takes the command (WindowCommandRouting); ShortcutAction.addToReadingList and .removeFromReadingList are in the Library group, with no default keys. readingListNeighbor(of:direction:skippingFinished:) and readingListContinuation(after:) answer what a reader of a book from the list asks (reading from the reading list, under the reader, below). A book counts as finished by LibraryViewModel.finishedBookIDs, what Books Finished records (ReadingStats.finishedBookIDs), which tests replace: a deliberate record, unlike a position near the end (P07), kept when the book is read again.
  - Files: Models/ReadingList.swift, Models/ReadingListCommand.swift, Models/ReadingListWording.swift, Models/Library.swift, Models/LibrarySortState.swift, ViewModels/LibraryViewModel+ReadingList.swift, ViewModels/LibraryViewModel+SortAndOrder.swift, ViewModels/LibraryViewModel.swift, ViewModels/LibraryListCache.swift, Views/Library/ReadingListOptionsBar.swift, Views/Library/LibraryView.swift, Views/Library/LibrarySubviews.swift, App/MenuCommands.swift, Models/KeyboardShortcut.swift.
- Feed items (FR11): the episodes and articles a feed downloaded, their packages, and each feed's own index.
  - Owner: the library model, with each feed's index on disk. A feed item's row is a Book whose feedLink (Models/FeedBookLink.swift: the feed's ID and the item's) names the feed and item it came from. The link travels with the row's file location (Book.FileLocation, so a reader following a moved row finds the package) and with the package record (BookMetadata.feedLink, which makeBookInfo() and Book(record:filePath:folderPath:tmbDirectoryName:) carry both ways, a save writing the row's link or else keeping the record's), and it makes tmbDirectory place the package in the feed's own folder, Feeds/<feed ID>/, beside the feed's record (Book.packageDirectory(inDataDirectory:); Services/Feeds/FeedPaths+Items.swift: itemsFolder(of:in:), indexFile(of:in:), packageDirectory(named:of:in:), and feedID(ofItemsFolderNamed:), which takes a folder named by a feed's ID alone, so FeedStore never takes the folder for a record). Each feed's index is Feeds/<feed ID>/library.json (FeedIndex, Services/Feeds/FeedIndex.swift: its layout version, 1, the feed's ID, and a row for each package, as library.json would hold the row, its link included), which FeedIndexFiles.encoded(_:) writes as compact JSON with sorted keys and its rows by date added, so one index is always the same bytes. While TextMouth runs, a feed item's row is in one of two places in the Library: among books while its file is here, so the reader, positions, bookmarks, settings, the reading list, and Stats reach it as they reach any book; or else on Library.feedShelf (FeedShelf, Models/LibraryFeedShelf.swift: the rows held apart, which no list, count, or pass meets, among them, since FR11's branch A2, each row kept after its file went, holding the listener's place; and indexedFeedIDs, the feeds whose indexes the library keeps, so a feed whose last row left gets an empty index and a feed no library named is never written). Library.libraryBooks and libraryBookCount are the library's own books, every row without a link, and Library.feedIndexRows is each feed's rows, wherever they are. Each feed's rows by the identity of the item each came from are FeedItemRows (downloaded, among the books, and kept, on the shelf), which the model's FeedItemRowLookup works out once for each change of the library, keyed by the list cache's content revision, for feedItemRows(of:) and feedBook(withID:), so a feed's counts, an item's state (FeedCenter.state(of:in:) and downloadedRow(of:in:)), whether it is new, and a download restoring a kept row each find a row in one step rather than by a scan.
  - Who may write it: a download publishes its package into the feed's folder (FeedEpisodeImporter.destinationPackageURL, which makes the folder), and LibraryViewModel.addFeedBook(_:) adds its row with its link and no library folder (downloads, under Feeds, below). Every save goes through LibraryPersistenceService.writeIndexFile, the one write path of library.json, which first writes each feed's index from Library.feedIndexRows (writeFeedIndexes(of:), each row placed where its package is by FeedIndexFiles.placed(_:in:of:)), only an index whose bytes differ from what this process last read or wrote of it (feedIndexesOnDisk, confined to the save queue), and then library.json, whose encoding (Library.encode(to:)) writes only libraryBooks, so no writer of library.json, a save, a checkpoint, the quit flush, a retry, Rebuild Library Index, or the data-directory move, can hold a feed item's row. A feed's index that can't be written throws FeedIndexWriteError, naming its file, before library.json is touched, and is reported and retried as a failed library index write. Reading library.json clears any link a row holds (Library's decoder, through Book.placedInLibraryFolder()), as orphan adoption and a package import do for a package found in the Library folder, whose record keeps the link: only a package in its feed's folder is a feed item's. At launch, LibraryPersistenceService.load() reads every feed's folder onto the shelf (loadFeedShelf(fromPackages:), FeedIndexFiles.readAll(in:fromPackages:)), each row placed where its package is, so moving the data directory or opening the library on another Mac rewrites no index first; an index that can't be read is preserved beside itself (SavedFile.preserveUnusable, FEED_INDEX_UNREADABLE) and its rows rebuilt from the packages' records, and a package the index doesn't list is read from its record too (FEED_INDEX). While library.json can't be read, the provisional library takes each feed's rows from its packages' records, and Try Again and the data directory's return keep the session's (carryingRecoverySessionState(from:into:), through feedItems(of:over:), in LibraryViewModel+IndexRecovery.swift). ### Package records

- bookInfo.json and contentIndex.json: each package's record of its book (BookInfo), in two files. bookInfo.json holds the metadata, the reading state, and the bookmarks, about a kilobyte, pretty-printed with sorted keys; contentIndex.json, beside it, holds the content index alone, compact with sorted keys, since it can run to hundreds of kilobytes and changes only when the book is imported or analyzed.
  - Owner: LibraryPersistenceService's metadata queue, for every save the running library makes. The record is built from a Book by Book.bookInfo(replacing:contentIndex:revisionFloor:).
  - Who may write it: saveBookInfo(for:) and saveBookInfo(for:contentIndex:), which hold each book's newest snapshot for half a second and write only it; saveContentAnalysis (below); and flushPendingSave(). A save of a book's state writes over the package's record (BookInfo.saveRecord(to:)): a record carrying an index writes contentIndex.json first, so bookInfo.json never names an index that is not on disk yet, and one without leaves contentIndex.json as it is, so a reading checkpoint writes about a kilobyte. The record such a save replaces is read as a StoredBookRecord, bookInfo.json and whether the package keeps an index, never reading contentIndex.json. A package written whole, by an import or a repair that separates a shared package, replaces both files (BookInfo.save(to:)), removing contentIndex.json when the record has no index; an import writes its new package's record so and reads it back (FileImportService.writeVerifiedRecord). Folder moves, migrations, and data-directory moves write records directly with Book.saveBookInfoThrowing, under the same revision rules but outside the queue's order; a move writes each staged copy's record as a save of its book does (saveBookInfoThrowing(contentIndex:inPackageAt:)), so the contentIndex.json it copied stays as it was, byte for byte. A record that is only in the cloud, or whose package or removal marker is, is neither read nor written by the queue, since reading it would download it: the book's saves go to library.json alone until the record is on this Mac again, with one BOOK_RECORD_IN_CLOUD line, and an analysis result for it is dropped.
  - How others observe it: BookInfo.load(from:) reads bookInfo.json with the index from contentIndex.json. A missing or damaged contentIndex.json leaves the record without an index, which the book's next load builds afresh, and a read refused because either file is only in the cloud is passed up rather than downloading it. - Transcripts (FR05): a transcribed audiobook's transcript.json, and the text written from it.
  - Owner: the package. transcript.json (Transcript, in layout Transcript.currentVersion, 1) is a record, not a cache: only transcribing the book again replaces it, only Edit Text and a cleanup or its undo change it, and only Delete Transcript removes it. ### Cloud state

CLOUD-STORAGE-RESEARCH-2026-10-03.md and CLOUD-STORAGE-PLAN-2026-10-03.md, at the repository's root, explain the design, and CLOUD-STORAGE-MANUAL-TESTS-2026-10-03.md says what real drives have verified and what remains to check by hand.

- Where the library lives, and each book's cloud state.
  - Owner: nothing stores either. Both are read fresh from file-system metadata, with downloading switched off, by the two services CloudServices holds.     - UbiquitousItemStatusProvider reads single items, files and folders: Foundation's ubiquitous-item keys and the file system's dataless flag, which overrules a key that disagrees, and, from the same read, whether the item carries sync flags of its own (SyncFlagReporting.flaggedStatus(of:), a FlaggedItemStatus). It tells where a folder lives from its path (iCloud Drive's Mobile Documents, or a File Provider drive in CloudStorage, named for its service), from iCloud Drive managing it elsewhere, as it does Desktop and Documents, or from its volume, and it asks the sync service to download a file or remove its local copy (FileManager's startDownloadingUbiquitousItem and evictUbiquitousItem).
    - BookCloudStorageService reads whole books: each look at a package lists it and reads the state of each file and of the package folder itself (a Survey), and decides once which items the sync service syncs (Survey.packageItem). The package is the one item when it carries sync flags and none of its listed files does, as on iCloud Drive, whose files inside a package carry none and are refused, as items that don't exist, when a download or a removal is asked for one of them; otherwise each file is, as on Google Drive and Dropbox, whose files carry flags of their own (as their package folders do too). For a package synced as one item, the book's state comes from the package's flags, Downloading while the sync service fetches it whole; the refusal of a book with changes not uploaded reads the package's upload flag; a download asks for the package and ends on its download error; and a removal evicts it. Nothing inside such a package can be looked up while it is evicted without downloading the whole package, so every check of a file inside a package runs with downloading off, as the reader's and Book Info's do (LocalBookFiles.availability(of:isDataless:)); Book Info looks at the package first and then the file (LibraryBookInfoReader).
    - It downloads by asking the sync service for every missing item and checking every half second until all are here, failing at once while this Mac is offline (NetworkReachability), when an item reports a download error, or when the package disappears, and after a minute in which nothing arrives or downloads. Meanwhile it listens, through PublishedFileProgress (Progress.addSubscriber), for the progress the sync service publishes for the package as a whole, as iCloud Drive publishes it for a package it syncs whole, and for each file still to come, as Google Drive and Dropbox publish it. The listener hands on only a download of the item it listens to (isDownload(_:of:)): an upload, or the progress the system also hands a folder's listener for each item inside the folder, is not, which it tells from the operation and the URL the published progress carries in its user info, since the proxy's own properties can still read nil then. The parts it hears fold into BookDownloadProgress (completedBytes by size, partialFiles by files), in whole percent per file, never going back, forgotten once the file is here, and a growing part keeps a stall away.
    - It removes downloads, refusing while changes wait to upload, and reporting a removal the sync service refuses as BookCloudError.removalFailed.
  - Who may write it: BookCloudStates.shared, on the main actor, records what the library list and the readers learn: where the library lives, and each book's latest state, a download's progress included. LibraryCloudRefresher.shared refreshes it while a Library window is visible: when one appears, when the app becomes active, when a book is added, moved, or removed, and on the cadence LibraryCloudRefreshCadence gives, every minute, or every 2 seconds while any book downloads. Refreshes never overlap, and each reads off the main thread: where the library lives, once (libraryLocation(), then state(of:in:) for each package), stopping there for a library outside a cloud location. ### Media playback

- Speech, for text books.
  - Owner: each reader's SpeechService. speak() starts the text at once with AVSpeechSynthesizer.speak(), the direct mode, and, for a text of at most SpeechRenderCoordinator.maximumTextLength UTF-16 units, renders the same text in the background into an AudioEngineService (AVAudioEngine with a time-pitch unit, for instant seeking and speed changes). The rendered audio takes over only at a natural break: a seek, a pause and resume, a sleep timer's fade, the recovery from a refused text, or the next chapter through the look-ahead. Speech never hands over from direct mode to rendered audio while it runs uninterrupted, because the synthesizer's word callbacks run ahead of the sound by an amount that cannot be known.
    - Direct speech starts with a chunk of at most SpeechService.directModeFirstChunkSize (1,000) UTF-16 units, since the synthesizer reads a whole utterance before its first word, and hands the synthesizer each later chunk of at most directModeChunkSize (5,000) as the one before it starts (queueNextDirectChunk()), so speech goes on after the synthesizer's own pause without waiting for the main thread. A queued chunk becomes the one speaking when the one before it ends or when it starts, whichever the main queue hears first.
    - The engine is made the first time speech needs one, for its first render or the first chapter it plays from audio rendered ahead (SpeechService.audioEngine; hasAudioEngine asks without making one), so an audiobook's reader never makes one. releaseSpeech() stops and lets go of the text and the rendered audio without making an engine, for a reader that closes, and restoreEngineVolume() restores only an engine that exists.
    - Rendered audio is a RenderedSpeechAudio: the synthesizer's pieces converted to 16-bit samples as they arrive, in blocks of 128 KB, then the silence padding every render ends with. It is immutable, so the look-ahead's engine hands it to the speech service's. A play converts back only what it schedules: RenderedSpeechFeeder schedules a few slices on the player node at once, and fills and schedules the next each time the node reports one consumed, on a serial queue of its own, so a busy main thread never leaves the node without audio; a seek schedules from the slice that holds the cursor, copying nothing else.
    - The voice is loaded ahead of the first Play: SpeechRenderCoordinator.warmUp(_:) renders one word with it and drops the audio (VoiceWarmUp), once per voice in a session, on the render queue like any render, giving up its turn after 30 seconds. A text book's reader asks when it opens and when its voice changes (ReaderViewModel.warmUpVoice()).
    - Every utterance made from a book's text is handed to the synthesizer guarded, through SpeechMarkupGuard.neutralized(_:) (Services/SpeechMarkupGuard.swift): the two brackets of each tag-shaped run (tagPattern: a closing tag, even with spaces or no name; a declaration, comment, or processing instruction; an opening tag whose name, any run of characters other than brackets, spaces, and slashes, with spaces around it or not, is followed by nothing but name=value attributes; or an empty tag, <> or < >) become U+2039 and U+203A, one UTF-16 unit for one, so the guarded text keeps the original's length, and every word range the synthesizer reports, every chunk boundary, and every offset of the rendered audio's frame map still counts in the original. Direct chunks and the sleep timer's fade segments (makeDirectUtterance(speaking:at:), which also replaces every bracket of the part of an utterance that lies in strictlyGuardedRange, through SpeechMarkupGuard.neutralized(_:strictlyWithin:)), the engine's render (AudioEngineService.render, whose SpeechRenderRequest keeps its text unguarded), Where Am I?, and Speak Info (LibraryInfoSpeaker), which speaks titles, go through it; the warm-up's one word and the voice previews are constants. The speech engine of macOS 26.3.1 scans a plain AVSpeechUtterance for tags: it refuses an utterance holding a closing tag with no opening tag, as a chunk that begins after a book's opening tag can, and the synthesizer that refused never speaks again; it swallows everything after an opening tag with no closing one; and it speaks a bracket that is not part of a tag as a word. The October 7 probes in Scripts/agents/probes/ (speech-markup-probe-shapes.swift and speech-refusal-probe-queue.swift, in Samantha's compact voice and in Alex alike) found that any bracketed name without spaces swallows what follows, an emoji alone excepted, which the guard takes all the same, only silencing its brackets; that the ampersand, bare or in an entity, is never refused, so the guard leaves it alone; that an utterance queued behind another is refused only once the one ahead of it finishes; and that whatever is queued behind a refused utterance is dropped without a callback. All of this was measured offline with write(_:toBufferCallback:), which plays nothing, as SpeechMarkupGuardTests render too. neutralized(_:) also turns each NUL (U+0000) into a space, one unit for one, after guarding brackets (since October 10, 2026, #1542): a NUL ends the text for the engine, which drops the rest of the utterance without a cancel, so neither a recovery nor the report of a refusal hears it. Every other control character passes: the offline probe Scripts/agents/probes/speech-control-character-probe.swift found the 64 others, C0, DEL, and C1, spoken in full in Samantha, and nothing lost at all in Alex.
  - Who may write it: the reader, through speak, pause, resume, seek, and stop, and releaseSpeech() as it closes.
  - How others observe it: the reader sets onWordSpoken, which moves its cursor through the offset map, and, for each play, onUtteranceFinished (the playback generation, above), and mirrors whether speech is playing or paused and its speed. Every utterance a synthesizer callback reports (a word, a start, a pause, a continue, a finish, or a cancel) is held until the callback is handled on the main queue (ReportedUtterance), so a new utterance made at a reused address can never take that callback for its own; there the service reads the synthesizer's state from its own synthesizer, never the callback's. Switches between the modes are logged in textmouth_transition.log, and switchToRenderedAudio(at:) is the one way direct speech hands over to rendered audio: at a seek, a resume, the watchdog's recovery, the start of a sleep fade, the one switch made while speech is heard, and a refusal's recovery. A cancel the service did not ask for (DIRECT_CANCEL_UNEXPECTED), of the live direct utterance, playing or paused, or of a sleep fade's segment the fade still holds (every stop of the service's lets go of both before it stops the synthesizer), comes from the engine's refusal of a text, which it raises before the first word, so the watchdog the utterance's start would arm never looks. It replaces directSynth first, whatever follows (replaceDirectSynthesizer(), DIRECT_SYNTH_REPLACED), since a synthesizer that refused never speaks again. For the live chunk, recoverFromCancelledDirectUtterance(_:) then plays the engine's audio of this speech, when renderedAudioMatchesSpeech, from the last word reported within the chunk or from its start (switchToRenderedAudio(at:), DIRECT_RETRY_ENGINE); otherwise, or when the engine does not start (DIRECT_RETRY_ENGINE_FAILED), it speaks again from there with the rest of the chunk strictly guarded (takeRetry(from:to:), which sets strictlyGuardedRange, kept until stop(), and lastDirectRetryOffset; DIRECT_RETRY), once for each place. Paused, the retry waits for Play, through pendingDirectSeekOffset, and counts as the place's one retry (retryCancelledDirectUtteranceAtResume(_:), DIRECT_RETRY_AT_RESUME). ### Logs

- The diagnostic logs.
  - Owner: DiagnosticLog, the one policy for what a log line may say and which lines are written. It alone calls TextMouthPaths.appendLog, which hands each line, by its log's name (DiagnosticLog.File), to LogWriter.shared. The writer writes on one serial queue, never blocking or crashing the app, opens each file for its line only, and keeps each file to two generations of at most 2 MB: a full log becomes its .previous by one rename(2) that replaces the older generation in the same step; a rename refused twice, as a File Provider folder can refuse one, starts the log over in place with a LOG_ROTATION line; and a log only in the cloud is never downloaded (every write runs inside DatalessFiles.withoutDownloading), but kept as the older generation while a fresh file starts.
  - Where they are: TextMouthPaths.logDestination(for:dataDirectory:thisMacsFolder:isUnavailable:), the one resolution of the logs' folder, which the writer runs for every line (LogWriter.Environment.app) and Storage settings run to show it. ## Reading a book: the path from library row to spoken audio

A book opens from its row in the Library window: VoiceOver's default action on the row, the row's Open command, or the Open Selected Book shortcut calls LibraryView.openBook(_:), which, at the Reading List, first asks the book's reader to read it from the list (reading from the reading list, above), and then ContentView's onOpenBook, which asks SwiftUI for the reader window whose value is the book's ID. A book already open comes forward instead of opening twice. Requests from elsewhere, such as Finder or a finished book continuing to the next, go through LibraryWindowRouter to the same scene. The scene builds a BookReaderWindowView, which looks the book up in LibraryViewModel and creates the window's ReaderViewModel with a copy of it. When the view appears it marks the book opened, and its window accessor gives the reader its window and registers the window with the router.

The new reader loads at once, on a background queue. It first asks the book storage where the library lives. Anywhere but a cloud location it reads the book in the same step, as it always has. In a cloud location it reads the book's cloud state too, and a book with files only in the cloud downloads first, in the reader window; the book is then read with dataless files left in the cloud, an audiobook after it is cloned into its working copy (getting a book from the cloud, above). A book being edited in the user's own editor, a text book or a transcribed audiobook, first has any edit saved there checked (settlePendingEdit(of:): edited text, above): one taken is read as the book's text, and one that can't be taken stops a text book's load, which says why, and leaves out an audiobook's transcript text. Reading calls BookContentAnalysisService.load, asking for a fresh text cache when the book records an older cache format than MarkdownCacheService.currentCacheVersion, and passes this Mac's ReadingTextCache: a large book whose kept text matches is read from it instead of content.md, and a parsed one is kept in the background. For a text book, loading writes content.md if it is missing; otherwise it checks the cache against its fingerprints, rebuilding it when the source or the cache has changed, reads it, and uses the content index saved in bookInfo.json when that index validates and lines up with the chapters, or indexes the chapters afresh. For an audiobook, loading uses a validated saved index, or else reads the audio through AudioBookParser, waiting for it through AsyncBridge, into chapters whose placeholder text stands for time at ten characters a second. A transcribed audiobook then has its transcript text laid over those chapters, for the text area to show while the audio plays (TranscriptTextLoader.load: transcripts, above). An audiobook's tags are read as well, but not an EPUB's package metadata: showEPUBMetadata() shows it from the book's row (Book.keptEPUBMetadata) when the row keeps every field, and otherwise reads it off the main thread once the book shows, through LibraryBookInfoReader.system's read, which never downloads, laying the book's edits over it as the book is when the read ends, and keeps it on the row and in the book's record (Book.keepEPUBMetadata(readFromFile:)), giving only the fields the row lacks the file's values, so an edit stands and later opens read nothing. Back on the main actor, the reader publishes the content and its headings, lays the book's own metadata edits over what the files hold, taking them from its copy of the book as it is by then, brings the saved position into range, commits a new or changed index through LibraryViewModel.updateContentIndex, saves the position, and claims a waiting autoplay request, if one is there. If the library moved the book while it loaded, the reader finds its chapter files at the new place, and a load that failed because of the move starts again from there. After claiming a waiting autoplay request, the reader prepares the opened chapter's speech off the main thread (prepareOpenedChapterSpeech).

Play starts nothing while the book is loading or while Where Am I? is speaking. For a text book, the reader first prepares what it will say, or takes what it prepared before from the same inputs (prepared speech, above). The chapter's text goes through the playback pipeline (ChapterSpeechInputs.prepare()): skipped sections are removed, runs of a repeated symbol are rewritten (RepeatedSymbolRule, which runs before the pauses because their periods and commas would lengthen runs of those symbols), punctuation pauses are added, and the substitution rules are applied, while a ComposedOffsetMap keeps track of where every spoken character came from. A position anywhere inside a rewritten run maps into the words that replaced it, and back. When nothing speakable remains, the book ends at once through its end-of-book behavior. Otherwise the reader claims the media controls through its NowPlayingSession, plays the play sound, records when playback started (for rewind on resume), starts a listening session in ReadingStatsService, resumes the sleep timer's countdown if this reader owns a paused one, and starts speaking.

Speaking begins a new play of the chapter (ChapterPlay), which gives the speech service a finish callback made for that play, and hands the spoken text and the starting offset to SpeechService.speak, which starts the synthesizer speaking directly at once, from a short first chunk, and renders the same text into an AudioEngineService in the background, through SpeechRenderCoordinator, for the next natural break. The reader then pre-renders the next speakable chapter, recording what that render was asked for as its signature and carrying that chapter's speech to its start; a chapter too long to render ahead is not rendered, and only its speech is prepared, off the main actor. As each word is spoken, onWordSpoken moves the cursor back through the offset map to the original text. The reader refreshes its view at most every 0.12 seconds, gives the library's rows and summary bar its cursor about once a second, through LiveReadingPositions, and saves a durable checkpoint every 30 seconds, into the book's record at once and into library.json within five minutes.

When a chapter's speech finishes, the callback made for its play ignores the end of a play the reader has already left, a later play having begun. Otherwise it saves the position and starts the next speakable chapter after the one that played, as a new play, unless the reader's own sleep timer stops playback at this chapter's end, where the next chapter begins the next heading, or the book ends (expireAtChapterEnd(endingTheHeading:endingTheBook:by:)): then the reader stops there instead, its cursor waiting at the next chapter's start. If the look-ahead holds that chapter's audio, rendered with the signature its speech has now, the engine plays it at once and the chapter after it is pre-rendered; otherwise the chapter is spoken from its current text. When no speakable chapter remains, handleEndOfBook stops, starts the book again, or continues to the next book in the folder, as the book's end-of-book behavior says and the reader's sleep timer allows, or, for a book read from the reading list, goes where the list's options say (finishBookReadFromReadingList). A book that neither loops back to its beginning nor hands over to the next book rests finished at its end (hasFinishedBook) and keeps its Now Playing session, so a backward skip that reaches its reader, from the AirPods, the media keys, or the keyboard, plays it again from where the skip lands, while no other book plays (Now Playing and media keys, above).

An audiobook takes the other branch at Play: playAudioChapter begins a new play and loads the chapter's file into AudioPlaybackService, from the book's working copy when the reader has one, playing it from the cursor's time, counted from the chapter's start within the file when the chapter is a time range, at the book's speed. A segmented chapter plays its clips as one chain instead, from the clip that holds the cursor's time. In a cloud location without a working copy, a chapter whose file is only in the cloud downloads first (chapterFilesReadyToPlay), and plays once it is here. The service reports the end of each play once, and the reader moves on from the chapter that played, as it does for speech. A file that cannot be played stops playback where it was, and the reader shows an alert with Retry.

Pausing records when playback stopped, pauses the sleep timer's countdown if this reader owns the timer, ends the listening session (crediting its last slice), and saves the position. Closing the window unregisters it from the router and closes the reader, which stops waiting for any download, stops playback, saves the position, releases its Now Playing session, stops the sleep timer if this reader owns it, deletes its working copy off the main thread, stops watching the library's updates to its book, and lets go of everything that grows with the book (a closed reader, above). The book's library row and its bookInfo.json then hold the last checkpoint, and LibraryPersistenceService writes both within half a second, library.json too, since unregistering the book brought its write forward from the checkpoint's deadline, or at the latest when the app quits.

## Shared helpers

These small types each own one rule that several parts of the app follow; use them rather than writing the rule again.

- LibraryWindowRouter (Services/LibraryWindowRouter.swift): decides which window takes each app-wide action.
- WindowCommandRouting (Views/Library/LibraryView.swift): decides which of several open windows takes a menu command or keyboard shortcut posted as a notification: a shortcut goes to the window it was pressed in, a menu command to the key window, and a window not attached yet takes either. Every Library window asks it through LibraryView's takesCommand(_:), and a reader, which counts its own sheets as itself, asks it too, as does an audio editor window's model for the editor's own shortcuts.
- LibraryBookUpdates (ViewModels/LibraryBookUpdates.swift): how open readers learn that the library changed their book or is moving its files.
- LiveReadingPositions (ViewModels/LiveReadingPositions.swift): where readers are between checkpoints. A live position goes there, never into the library, which takes a reader's position only at its checkpoints.
- ReaderSnapshot and SheetOverOneReader (Views/Reader/ReaderSnapshot.swift): what a view shows of its reader, republished only when it changes, and sheets that compare equal while they show the same reader. A view over a playing reader observes a snapshot, never the whole reader.
- TextCacheFingerprint (Models/TextCacheFingerprint.swift): what a text cache was written from, checked by size and date before any file is read.

- TranscriptText (Models/TranscriptTextIndex.swift): a transcribed audiobook's text with its timing, sentence by sentence: the sentence heard at a time, the place in the text for a time and the time for a place, and so the reader's audio cursor converted both ways. Search in Book, Where Am I?, and anything else that follows the narration in the text should use it rather than converting time again.

An edit in the user's editor (TranscriptEditing.apply) and a cleanup (TranscriptCleanup) both rewrite sentences through it.
- TranscriptAccuracy (Services/TranscriptAccuracy.swift): a transcript aligned word by word with the text that was read aloud, its words compared as the edit alignment compares them (TranscriptEditAlignment.key(of:)), with every apostrophe read as one; the differences sorted into the kinds of mistake a recognizer makes, its confidence weighed against them, and the corrections that would have been right in every place they apply. It is in the app rather than the tests so that later work, such as learning rules from the user's own edits, can use it.
- RowNoteBadge (Views/Library/BookCloudNote.swift): the outlined badge a library row's notes are drawn in, its cloud notes and its transcription note, with a picture hidden from VoiceOver, which only repeats the words.
- PersistenceFailureCenter (Services/PersistenceFailureCenter.swift): where every failed save is reported and settled.
- ImportStaging (Services/ImportStaging.swift): builds a package out of sight and publishes it with one rename.
- AudioEditHistoryStore and AudioEditPackage (Services/AudioEditing/): the one way to change a book's audio edit history, under one lock for the whole process, and where a package keeps that history, its originals, and its takes, with the one check that a path a history records stays inside the package.

## Known duplication

Repeated code that is known and left for now, each with the reason:

- More than a dozen messages still choose singular or plural inline, in FileImportService, LegacyBookMigration, LibraryViewModel+Migration, PersistenceFailureCenter, LibraryViewModel+BookOperations, and AudioBookParser; they could use CountWording. A few sentences deliberately drop the number for one ("Remove Book?", "the book inside") and do not fit it.
- TimeRemainingBar.computeTimeRemaining (Views/Library/LibrarySubviews.swift) repeats LibraryViewModel.totalTimeRemaining(books:wpm:) (ViewModels/LibraryViewModel+Migration.swift), which nothing calls at all, applying each book's live reading position first.
- PDFTextParser's two page readers, with and without heading detection, share most of their loop, but record font sizes differently in ways that the paragraph joiner reads, so merging them would change some PDFs' paragraphs.
- VoiceOverFocus.swift repeats its accessibility-tree searches (findElementByIdentifier and findFirstInteractiveElement) and its focus scheduling in StandardVoiceOverFocusTriggerView and VoiceOverFocusTriggerView.
- Several stores configure their own JSON encoder with the same ISO 8601 dates and sorted, pretty output (bookInfo.json in BookInfo, RemovedFromLibraryMarker, ReadingStatsService, DataDirectoryMigrator, LibraryIdentity, LibrarySessionLease, and AudioEditHistoryStore, which also leaves slashes unescaped), while library.json is written compact with its keys unsorted (LibraryPersistenceService.encodedIndex(_:)), and contentIndex.json and reading-checkpoints.json compact with sorted keys, so sharing one encoder would change those files' layouts. DataDirectoryMigrator writes a moved library's library.json with its own pretty, sorted encoder rather than encodedIndex(_:), so the index stays pretty-printed after a move until the library is next saved.
- ReaderViewModel.offMain repeats OffMainWork.run: both run blocking work on a global dispatch queue and hand back its result. Two cloud branches written side by side added them; the reader could call OffMainWork.
- Three functions compare two items' volume identifiers: ReaderWorkingCopies.isOnSameVolume, ImportScratchSpace.areOnSameVolume, which first climbs to the nearest folder that exists, and the live areOnOneVolume probe of StorageDestinationAssessment. They could share one.
- ListingFailure (Services/ReaderWorkingCopy.swift) and FolderListingFailure (Services/DataDirectoryMigrator.swift) are the same small class, keeping the first error a folder enumeration's handler meets; one could serve both.
- ContentView opens readers with the literal window ID "book-reader" rather than BookReaderWindowView.windowID, and posts its folder announcement directly rather than through VoiceOverAnnouncer.
- ContentFileWatcher (Services/BookTextEditor.swift) repeats ConfigService's file watcher: a DispatchSource on a descriptor opened for events only, armed again when a save replaces the file.

- The performance tests keep, verbatim, the code each change of October 3 replaced, as the oracle and the baseline the new code is compared with: each speech-preparation test file keeps its own privately (legacyTransform, legacyPauses, legacyRuns, legacyPreparedSpeech), and the text pipeline's are kept once, in TextPipelineBefore (TextMouthProductionTests/TextPipelineFixtures.swift), for the golden tests and the benchmarks.
